Consistent Hashing

Servers and keys are hashed onto the same ring. Each key belongs to the first server clockwise from it. When a server joins or leaves, only the keys in its slice of the ring move. With plain hash(key) mod N, almost every key moves.

Worked example

Six keys, three servers, one new server

Real hashes are 32-bit numbers. To keep the arithmetic readable, this example uses a ring numbered 0 to 99, so every hash is a number in that range.

  1. Place the servers on the ring

    Hash each server's name and put it at that point. Say A lands at 20, B at 55 and C at 85.

  2. Place each key, then walk clockwise

    A key belongs to the first server at or after its position. If you pass 99, wrap around to 0. So A owns 86–20, B owns 21–55, and C owns 56–85.

    KeyHashWalk clockwise toOwner
    cat1220A
    dog4055B
    yak5055B
    emu6085C
    fox7085C
    gnu90wraps past 99 → 20A

  3. Add server D at position 65

    D takes over only the arc from 56 to 65, which used to belong to C. The only key in that arc is emu (60). Every other key keeps its owner. 1 of 6 keys moves.

  4. Compare with hash mod N

    The simple approach picks server number hash % N. Going from 3 to 4 servers changes the divisor for every key at once:

    KeyHash% 3 (A, B, C)% 4 (A, B, C, D)Moved?
    cat120 → A0 → Ano
    dog401 → B0 → Ayes
    yak502 → C2 → Cno
    emu600 → A0 → Ano
    fox701 → B2 → Cyes
    gnu900 → A2 → Cyes

    3 of 6 keys move. With thousands of keys the gap grows: mod N moves about 3/4 of them when going from 3 to 4 servers, while consistent hashing moves about 1/4 on average. The simulation above measures this on 120 real hashes.

  5. Why a move is expensive

    If the servers are caches, a moved key is a cache miss that falls through to the database. If they are databases, a moved key is data that has to be copied across the network. Moving 75% of keys at once can take a whole site down, which is exactly what consistent hashing was invented to prevent.

The story

A fix for the 1990s web getting crushed by its own success

In the mid-1990s a popular site could be knocked offline simply by being popular. When a big news site linked to a small server, thousands of browsers arrived at once and the server fell over. The paper called these "hot spots". A few years later the same effect got the nickname "slashdotting", after the tech news site whose links caused it so often.

The obvious fix was caching: keep copies of popular pages on many machines and spread the requests. But which cache should hold which page? If each browser picked a cache by hash(url) mod N, every cache added or lost would reshuffle nearly every page, and all those caches would miss at once. Worse, different browsers might know about different sets of caches, so they would disagree about where a page lives.

At MIT, David Karger, Eric Lehman, Tom Leighton, Rina Panigrahy, Matthew Levine and Daniel Lewin worked on this problem. Their 1997 paper introduced consistent hashing: put caches and URLs on the same circle and give each URL to the next cache clockwise. A change in the set of caches only disturbs the neighbours of the cache that changed.

The idea did not stay in a paper. Leighton and Lewin founded Akamai in 1998 to run it as a business.
  1. 1997

    Karger and colleagues present "Consistent Hashing and Random Trees" at STOC, the ACM Symposium on Theory of Computing, as a way to relieve hot spots on the web.

  2. 1998

    Tom Leighton and Daniel Lewin found Akamai, a content delivery network built on the technique.

  3. 2007

    Amazon's Dynamo paper uses a consistent hashing ring with virtual nodes to partition its key-value store. This brings the idea from web caches into databases.

  4. Today

    Cassandra, Riak, ScyllaDB, OpenStack Swift, Discord and many load balancers and caches use a ring or a close relative of it.

From first principles

Rebuilding the idea from the problem

What

A way to assign keys to servers so that when the set of servers changes, only about K/N of K keys move to a new server.

Why

Servers join and fail all the time. With mod N, changing N changes the answer for almost every key, because the divisor is shared by all of them.

When

1997, when web traffic was growing faster than any single server could handle and caching had to span many machines.

Where

MIT's theory group. The authors published it at a theory conference, and it went into production at Akamai within a year.

How

Remove the shared divisor. Hash servers and keys into the same space, and let each key find its owner by position alone. Adding a server then only cuts one arc of the circle.

The one-line insight: make a key's owner depend only on its nearby neighbours on the ring, never on the total number of servers.

The follow-up problem: a few random points give uneven arcs. Virtual nodes place each server at many points, which averages the arc sizes out. Try the slider in the simulation.

What to notice

  • Adding a 5th server moves about 1/5 of keys with consistent hashing. With mod N it moves about 4/5.
  • With 1 virtual node, servers get very uneven slices. Push the slider to 30+ and the bars even out.
  • Removing a server hands its keys only to its clockwise neighbours. Everyone else is untouched.

Interview angle

Why virtual nodes? A few random points on a ring give high variance in arc length. Many points per server average it out, and a server that leaves spreads its load across many neighbours instead of one.

Trade-off: more virtual nodes means a bigger ring to search (O(log V·N) lookup) and more metadata to gossip.
