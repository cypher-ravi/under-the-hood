Collaborative Editing (OT and CRDTs)

Alice and Bob edit the same text at the same moment, each on their own copy, and each edit travels over the network to the other copy. An edit that only says "insert h at index 1" can land in the wrong place, because the other copy has changed in the meantime. Two fixes are used in practice. Operational transformation (OT) rewrites an incoming edit to account for the edits it raced with. A CRDT gives every character a permanent id, so edits never mention positions at all and can be applied in any order.

      CRDT (RGA). Every letter gets an id (counter, site) when it is typed, and keeps it forever. An insert says "new id right after id X"; a delete only marks the letter as a tombstone. Edits name ids, never positions, so the order they arrive in stops mattering.

      The story

      From GROVE to Google Docs

      In 1989 Clarence Ellis and Simon Gibbs, working at MCC in Austin, presented "Concurrency Control in Groupware Systems" at ACM SIGMOD. Their outline editor, GROVE, let several people edit at once with no locks: each person's edits showed up on their own screen straight away, and edits arriving from others were transformed before they were applied. That is the idea of operational transformation, and their algorithm was called dOPT.

      It was harder than it looked. During the 1990s researchers found sequences of edits among three or more sites where dOPT left copies different, and a long line of papers followed, each adding conditions a transform has to satisfy and each finding new corner cases.

      In 1995 David Nichols, Pavel Curtis, Michael Dixon and John Lamping at Xerox PARC described the Jupiter collaboration system at UIST. Their shortcut was to put a server in the middle. Every client talks only to the server, so any transform involves just two parties, the case that is easy to get right. The simulation on this page uses Jupiter's two-party scheme.

      Google Wave, announced at Google I/O in May 2009, built its live editing on Jupiter-style OT. Wave did not last, but the approach did: in 2010 Google rebuilt the Docs editor around a server that puts all edits in one order and clients that transform against it, and explained the design in a blog series that September. Most OT editors still work this way.

      OT is easy with two parties and hard with many. Production systems make it two parties by putting a server in the middle.
      The story, continued

      Give every letter a name

      A different line of work asked: what if edits never mentioned positions? WOOT (Oster, Urso, Molli and Imine, 2006) gave each character a permanent id and described inserts as "between these two ids". Treedoc and Logoot followed in 2009, and RGA (Roh, Jeon, Kim and Lee, 2011) used the "insert after this id, larger ids first" rule shown above.

      In 2011 Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski named the whole family conflict-free replicated data types and defined strong eventual consistency: replicas that have received the same updates are in the same state, in any order, with no coordination. Counters, sets, maps and text can all be built this way.

      Libraries followed. Kevin Jahns's Yjs (its YATA algorithm was published at GROUP in 2016) and Automerge, which grew out of Martin Kleppmann and Alastair Beresford's 2017 JSON CRDT paper, made CRDTs practical in the browser. Figma, writing in 2019, took a middle path: its multiplayer system borrows CRDT ideas but keeps a central server as the authority, because it has one anyway.

      From first principles

      Rebuilding the idea from the problem

      What

      Ways to let several people edit one document at once, each seeing their own typing instantly, and still end with identical copies that keep everyone's edits.

      Why

      Waiting for a server before showing a keystroke feels laggy, and locking a paragraph blocks your co-authors. So every copy edits first and reconciles later. An edit described by position goes stale the moment someone else edits earlier in the text.

      When

      Shared documents, code editors with live sharing, design tools, whiteboards, notes apps that sync between your own devices, and anything that must work offline and merge later.

      Where

      OT where there is always a server to put edits in one order (Google Docs). CRDTs where peers sync directly or stay offline for a long time (Yjs, Automerge, local-first apps), and inside servers that want merges that never fail.

      How

      OT: send (operation, what I had seen); the receiver transforms it past every concurrent operation, then applies it. CRDT: give each element a unique id (counter, site), describe inserts relative to ids, keep deleted elements as tombstones, and break ties with a fixed order on ids so every copy makes the same choice.

      The one-line insight: a position is only meaningful against one exact version of the text. Either translate positions between versions (OT) or stop using positions (CRDT).

      Convergence is not enough: naive indexes can converge on text nobody wanted (try "Both delete one letter"). The goal has two parts: every copy ends the same, and every edit keeps its author's intent.

      What to notice

      • Preset "cat" in mode 1, then Reconnect: Alice ends with "hat", Bob with "aht". Switch to mode 2 or 3 and the same history gives "hat" on both.
      • "Both delete one letter" starts from "cart" and both remove the r. Naive converges on "ca": the second delete, still pointing at index 2, removes the t that nobody touched. OT turns the second delete into a no-op and the CRDT finds the r already tombstoned; both end with "cat".
      • "Both type at one spot": Alice types XY and Bob types uv right after the a. Naive ends with "auvXYbc" against "aXYuvbc". OT and the CRDT keep each word together: "aXYuvbc" on both.
      • Set the delay to manual and deliver to one side only. The copies differ for a while, which is allowed; they only have to match once every edit has arrived.
      • In mode 3, type and delete a few words. The visible text stays short while the element list keeps growing: every deleted letter is still stored as a tombstone.

      Interview angle

      Pick by topology. If every edit goes through your servers anyway (a Google Docs design), OT with a server-assigned revision number per document is the proven choice: the server orders edits, clients transform against what they missed. If clients sync peer to peer or stay offline for days, use a CRDT.

      OT's cost is the server. One ordering point per document, so route all editors of a document to the same server (consistent hashing on the doc id) and keep an operation log plus periodic snapshots.

      CRDT's cost is metadata. An id per character and tombstones that cannot simply be dropped: a late edit may still refer to a deleted letter. You can only collect a tombstone once every replica has seen the delete, which is hard when some replicas are offline. Real libraries shrink this by storing runs of letters typed together as one item.

      Neither needs consensus for text. Unlike Raft or quorum writes, nobody waits for agreement before showing a keystroke. Copies may differ for a while and are guaranteed to converge once all edits arrive.

      Also mention: cursors and presence go on a separate, lossy channel; undo must undo your own edits, not the last edit; and rich text adds formatting ranges that need the same care.
