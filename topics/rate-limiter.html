Rate Limiters

Four common ways to enforce "at most L requests per W seconds", all fed the same traffic at once. They agree on steady traffic and disagree sharply on bursts, especially a burst that straddles a window boundary.

Worked example

Ten requests in two seconds, against a limit of 5 per 10 seconds

The limit is L = 5 requests per W = 10 seconds. A client sends 5 requests at 0:09 and 5 more at 0:11, right across the 0:10 boundary. (The simulation uses W = 4 s so you don't have to wait as long.)

  1. Fixed window: count per clock window

    Keep one counter per window, [0:00, 0:10), [0:10, 0:20) and so on, and reject once it reaches 5. The first five land in window one, the next five in window two, and both counters are fresh. All 10 are allowed, twice the limit inside two seconds.

  2. Sliding window log: remember every timestamp

    Store the time of every allowed request. For a new request, drop timestamps older than 10 seconds and count what's left. At 0:11, all five timestamps from 0:09 are still inside the last 10 seconds, so the count is already 5. 5 allowed, 5 rejected. Exact, but it stores up to L timestamps per client.

  3. Sliding window counter: estimate from two counters

    Keep only the previous and current fixed-window counts. Assume the previous window's requests were spread evenly, and count the part of it that still overlaps the last 10 seconds.

    estimate = prev × (time left in overlap ÷ W) + current = 5 × 0.9 + 0 = 4.5

    4.5 is under 5, so the first request at 0:11 is allowed. Then the estimate is 5 × 0.9 + 1 = 5.5, so the other four are rejected. 6 allowed in total. Nearly exact, with just two numbers of state.

  4. Token bucket: spend tokens, refill steadily

    The bucket holds at most 5 tokens and refills at 5 per 10 s, so 0.5 per second. Each request spends one token. At 0:09 the bucket is full, so all five pass and it is empty. Two seconds later it has refilled 1 token. 6 allowed in total. It stores two numbers: the token count and the last refill time.

The story

From telephone networks to every public API

Rate limiting started in networking, not in web APIs. In the 1980s, telephone companies were designing networks that would carry voice, video and data over shared links. A network can only promise quality to everyone if no single sender can flood a link. It needed a way to check, packet by packet, whether each connection was keeping to the rate it had agreed to.

In 1986 Jonathan Turner described the leaky bucket. Picture a bucket with a hole in the bottom. Each packet pours some water in, and water drains out at a fixed rate. If a packet would overflow the bucket, the sender is over its limit. The bucket's size decides how big a burst is tolerated, and the drain rate decides the long-term average.

The token bucket is the same idea seen from the other side. Tokens drip in at a fixed rate and each packet takes one out. Given the same parameters, the two make identical decisions. The standard for ATM networks formalized this as the Generic Cell Rate Algorithm (GCRA), and routers still use token buckets to shape traffic.

When web APIs went public in the 2000s, the same problem came back. One buggy script or scraper could use up a service built for thousands of users. The simplest fix was a counter per clock minute, but its boundary flaw was quickly noticed. Engineers borrowed the token bucket from networking and invented the sliding window variants to get accuracy without storing every request.

  1. 1986

    Jonathan Turner describes the leaky bucket as a way to police traffic in packet networks.

  2. 1990s

    The ITU-T (Recommendation I.371) and the ATM Forum standardize the leaky bucket as the Generic Cell Rate Algorithm for ATM networks.

  3. 2000s

    Public web APIs adopt per-key limits, often a simple counter per hour or minute.

  4. 2017

    Stripe and Cloudflare publish how they rate limit at scale. Stripe uses token buckets in Redis, and Cloudflare uses a sliding window counter built from two fixed windows.

  5. Today

    AWS API Gateway documents that it throttles with a token bucket. Nginx, Envoy and most API gateways ship one or more of these algorithms.

From first principles

Rebuilding the idea from the problem

What

A check in front of a service that rejects requests from a client once it exceeds a rate, such as 100 requests per minute.

Why

Capacity is shared. Without limits, one heavy or broken client degrades the service for everyone, and abuse like credential stuffing becomes cheap.

When

The mid-1980s for network traffic, and again in the 2000s when APIs opened to the public.

Where

Born in telecom research (Turner, then the ITU and ATM Forum). Today it runs in API gateways, load balancers and services, usually with state kept in Redis.

How

Keep a small amount of state per client (a counter, timestamps or a token balance), update it on each request, and compare it with the limit.

The core trade-off: accuracy against memory. Exact sliding windows need a timestamp per request. Counters and buckets need O(1) state, and either approximate or allow a deliberate burst.

At scale: the state lives in a shared store so every server sees the same count. The read and update must be atomic, or two servers can both see "4 of 5" and both allow.

What to notice

  • Press "Burst across a boundary". Fixed window's peak jumps to 2L. The sliding log never goes above L, because it counts exactly.
  • The sliding counter can overshoot L a little. It assumes the previous window's requests were spread evenly, and a burst at the end of that window breaks the assumption.
  • The token bucket can also pass more than L in W seconds: a full bucket of L, plus up to L more refilled during the window. That is its burst allowance, not a bug. Its long-run average still stays at L per W.
  • Press "Burst now" after a quiet stretch. The token bucket lets exactly L through at once, then about one request every W/L seconds as it refills.
  • Watch the sliding counter's estimate fall smoothly as the previous window slides out of view.

Interview angle

Which would you pick? Token bucket for most APIs: O(1) state, a controlled burst allowance, and two intuitive knobs (bucket size and refill rate). Sliding window counter when you want a smooth limit with no burst allowance.

Where does it run? Usually at the API gateway, keyed by user ID, API key or IP address, with counters in Redis and a Lua script for atomicity.

What does the client see? HTTP 429 Too Many Requests, ideally with a Retry-After header and rate-limit headers showing the remaining quota.
