Quorum Replication and CAP

Keep N copies of every value. A write counts as done once W copies have it, and a read asks R copies and keeps the newest answer. If R + W > N, every read group overlaps every write group, so a read always meets the latest write. Cut the network in two and you must choose: refuse requests to stay correct, or answer them and risk being wrong. That choice is CAP.

Worked example

Three replicas, traced by hand

N = 3 replicas called A, B and C. Each copy stores a value and a timestamp. A read returns the value with the highest timestamp among the copies it hears from.

  1. Start: everyone agrees

    A, B and C all hold x = red @1.

  2. Write with W = 2

    A client writes x = blue @2. The coordinator sends it to all three, and A and B reply first. Two acks meet W = 2, so the client hears "done". C hasn't got it yet: A = blue@2, B = blue@2, C = red@1.

  3. Read with R = 2

    The reader happens to ask B and C. It gets blue@2 and red@1, keeps the higher timestamp, and returns blue. Correct. It had to be: there are only 3 copies, the write touched 2 and the read touched 2, and 2 + 2 = 4 > 3, so at least one copy is in both groups.

  4. Same write, but R = 1 and W = 1

    Now the write finishes after A alone acks. A read that asks only C gets red@1, an old value, even though the write was acknowledged. With R + W = 2 ≤ 3, the groups don't have to overlap.

    P(stale) = C(N−W, R) / C(N, R) = C(2, 1) / C(3, 1) = 2/3

    Two of the three copies the reader could pick missed the write. Background sync shrinks this window, but doesn't close it.

  5. A partition: C is cut off with a second client

    Back to R = W = 2. The client on C's side wants to write. Only one replica is reachable, and W is 2. A CP system refuses: the client gets an error, but no copy ever disagrees. An AP system accepts the write on C alone: C = green@3, while the other side writes A, B = yellow@4.

  6. The partition heals

    Sync compares timestamps, and yellow@4 wins on every copy. Green was acknowledged to its client and is now gone. Last-write-wins quietly drops concurrent writes. Systems that can't afford that keep both versions and let the application merge them, using version vectors to tell "newer" apart from "concurrent".

The two rules from 1979: R + W > N makes every read see the latest write. W > N/2 makes every two writes overlap, so they can't both succeed without one seeing the other. Majorities (W = R = ⌊N/2⌋ + 1) satisfy both.

The story

Votes, a conjecture, and a shopping cart

In 1979, David Gifford at Xerox PARC asked how a file stored on several machines could stay correct when some machines were slow or down. His answer was to give each copy votes. A read needs r votes and a write needs w, and as long as r + w is more than the total, every read group shares a copy with every write group. Version numbers then tell the reader which copy is current. The paper, "Weighted Voting for Replicated Data", appeared at SOSP that year.

Twenty years later the web had made availability the thing everyone cared about. In his keynote at PODC in 2000, Eric Brewer argued that a shared-data system can't have all three of consistency, availability and partition tolerance. Two years later Seth Gilbert and Nancy Lynch at MIT proved a precise version of it, and the conjecture became the CAP theorem.

In 2007 Amazon's Dynamo paper turned Gifford's votes into three knobs anyone could set: N, R and W. Its common setting was (3, 2, 2). Dynamo chose availability on purpose: a customer should always be able to add an item to their shopping cart. During failures it used a "sloppy" quorum, writing to the next healthy nodes and handing data back later. Cassandra, Riak and Voldemort copied the same knobs.

Partitions are rare, so CAP is really about what you do in the rare moment when they happen.

From first principles

Rebuilding the idea from the problem

What

Store each value on N machines. Count a write as done after W acks, and a read as done after R replies, keeping the newest version.

Why

Waiting for all N copies is slow and fails whenever any one machine is down. Waiting for one is fast but can return old data. Quorums let you pick the point in between.

When

1979 for quorums, 2000 to 2002 for CAP, and 2007 onwards for the tunable stores that made both everyday tools.

Where

Xerox PARC (Gifford), UC Berkeley and Inktomi (Brewer), MIT (Gilbert and Lynch), and Amazon (Dynamo).

How

Overlap does the work. If R + W > N, any R copies include at least one of any W copies, so the newest version is always in the read group.

The one-line insight: you don't need every copy to agree. You need every reader to meet at least one copy that saw the latest write.

The trade-off: bigger R or W means more consistency, more latency (you wait for the slowest of the group) and less tolerance for failed machines.

What to notice

  • Set R = 1 and W = 1 with N = 5, write once, then read a few times. Most reads come back stale. Press Test: the measured rate lands near the predicted 80%.
  • Raise R until R + W > N. The predicted stale rate drops to exactly 0%, and no read in Test is stale.
  • Split the network with CP selected. Client 2's side can't reach a quorum, so its requests fail, while Client 1's majority side keeps working.
  • Switch to AP, let both clients write, then heal and sync. One acknowledged write disappears. Same thing without a partition when W ≤ N/2: two writes can miss each other.

Interview angle

"Is your database CP or AP?" Answer per operation, not per product. A payment ledger or seat booking should refuse rather than double-sell. A shopping cart, like counter or feed should stay up and reconcile later.

Does R + W > N give linearizability? Not on its own. Sloppy quorums, clock-based last-write-wins and concurrent writes can still surprise you. Strong guarantees need consensus, such as Raft, or careful read repair.

Typical choices: N = 3 with R = W = 2 tolerates one failure on both paths. For read-heavy data, W = N and R = 1 makes reads cheap, but any one slow replica blocks writes.
