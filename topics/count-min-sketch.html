Count-Min Sketch and Top K

A few rows of counters, one hash function per row, that count how often each item appears in a stream without keeping a counter per item. An estimate can be too high but never too low, and the width of the grid sets how far off it can be. Put a small min-heap on top and you have a running list of the most viewed videos.

Worked example

Two rows, four counters, two wrong answers

Here d = 2 rows and w = 4 columns (numbered 0–3). The hash outputs below are chosen by hand to keep the trace short. In the simulation they come from mixing the bytes of the video ID with a different seed per row.

  1. The hash table

    Videoh1 (row 1)h2 (row 2)
    A01
    B22
    C03
    D23
    E10

  2. Stream A, B, A, C, A, D

    Each view adds 1 to one counter in each row. A lands in row 1 column 0 and row 2 column 1, three times. B, C and D land once each.

    row 1: 4 0 2 0row 2: 0 3 1 2

    Row 1 column 0 holds A's 3 plus C's 1. Row 1 column 2 holds B and D. Row 2 column 3 holds C and D. Six views went in, and every row still sums to 6.

  3. Query A: exact, thanks to row 2

    Row 1 says 4, because C shares that counter. Row 2 says 3, and nobody else hashed there. The estimate is min(4, 3) = 3, the true count. One clean row is enough.

  4. Query C: overestimated

    Row 1 column 0 is 4 (A's views), row 2 column 3 is 2 (D's view). The estimate is min(4, 2) = 2, but C was viewed once. C collided in every row, so the minimum cannot remove the extra.

  5. Query D and E

    D reads row 1 column 2 = 2 (with B) and row 2 column 3 = 2 (with C): estimate 2, true 1. E was never viewed: row 1 column 1 = 0, row 2 column 0 = 0, estimate 0. A counter only ever holds the item's own views plus other items' views, so no estimate is ever below the truth.

  6. What the bound promised

    ε = e / w = 2.718 / 4 ≈ 0.68 · εN = 0.68 × 6 ≈ 4.1 · δ = e−2 ≈ 0.135

    So each estimate should be at most about 4 too high, with at least 86% probability. The real errors were 0 and 1. The bound is a worst-case guarantee, and with a skewed stream the typical error is much smaller.

  7. Sizing a real one

    Pick the error you can accept as a share of the stream, ε, and the failure chance δ. Then w = ⌈e / ε⌉ and d = ⌈ln(1/δ)⌉.

    ε = 1%, δ = 1% → w = 272, d = 5 → 1,360 counters × 4 B ≈ 5.4 KB

    ε = 0.1%, δ = 0.1% → w = 2,719, d = 7 → 19,033 counters × 4 B ≈ 76 KB

    Neither size depends on how many distinct videos there are. An exact map with a hundred million videos at around 16 bytes an entry would be more than a gigabyte.

  8. Check it against the simulation

Conservative update on the same stream. Instead of adding 1 to every row, raise each of the item's counters only up to (current minimum + 1). When C arrives, row 1 column 0 already holds 2, which is more than C's minimum of 0 + 1, so it is left alone. Row 1 column 0 ends at 3 instead of 4. Estimates stay at or above the truth, and are often lower than with the plain update, but the sketch can no longer handle deletions or negative updates.

The story

Counting a stream you can't store

Around 2000, routers and telephone switches were producing more records per second than anyone could keep. Network operators wanted simple answers anyway: which flows are using the most bandwidth, which destinations get the most packets. Researchers began to treat this as a problem in its own right, the data stream model: see each item once, in order, and keep a summary far smaller than the input.

Two ideas from 2002 came close to what we use now. Moses Charikar, Kevin Chen and Martin Farach-Colton described the Count Sketch at ICALP: rows of counters, where each item adds +1 or −1 to one counter per row and the median of the rows estimates its count. The same year, Cristian Estan and George Varghese's SIGCOMM paper on traffic measurement used several parallel arrays of counters (multistage filters) to catch the largest flows, and introduced "conservative update" to make them more accurate.

Graham Cormode and S. Muthukrishnan simplified the design. In their 2003 technical report, presented at LATIN in 2004 and published in the Journal of Algorithms in 2005, every update only adds, and the estimate is the minimum across rows. Because counts never go below the truth, the analysis is short, and the space needed for error ε drops from a factor of 1/ε² for earlier sketches to 1/ε. The name is the whole recipe: count, then take the min.

Every counter is the item's own count plus some noise from other items. The noise is never negative, so the quietest counter is the closest to the truth.

From first principles

Rebuilding the idea from the problem

What

A d × w grid of counters and d hash functions. Adding an item increments one counter per row. Its estimate is the smallest of those d counters.

Why

An exact count per item needs memory for every distinct item, and a stream of video IDs, search terms or IP addresses has hundreds of millions. Most of those items are rare, and for "what is popular" you only need the big counts to be right.

When

2003 to 2005, as streaming algorithms grew out of network monitoring and database research.

Where

Graham Cormode and S. Muthukrishnan: a DIMACS technical report (DIMACS is a research center hosted at Rutgers University), then LATIN 2004, then the Journal of Algorithms.

How

Collisions only ever add to a counter, so every row overestimates or is exact. Taking the minimum keeps the least-polluted row. A wider grid means less pollution per counter (error about N/w), and more rows make it unlikely that every row is badly polluted at once.

The one-line insight: you can afford to be wrong about rare items, because a rare item's count is small and the error is a share of the whole stream.

The sibling: a Bloom filter hashes an item into bits and answers "seen it?". A Count-Min Sketch hashes into counters and answers "how many times?". Both can be wrong in only one direction.

What to notice

  • The estimate is never below the true count, whatever you do. The verdict box shows "over by" or "exact", never "under".
  • Popular videos are almost always exact or close in relative terms. Rare videos that share cells with popular ones get the largest relative error.
  • Drag w from 16 down to 4. The bound εN and the measured errors climb, and junk videos start to appear in the heap's top K.
  • Set d = 1 and then 3 at the same width. One row has nothing to compare against; extra rows let the minimum dodge bad collisions.
  • Turn on conservative update. With the defaults the average overestimate falls from 13.22 to 7.47. With d = 1 it changes nothing, because there is only one counter to raise.
  • Pick a cold video and press "Viral burst". It enters the heap as soon as its estimate passes the heap's root.

Interview angle

Why a heap on top? The sketch can only answer "how many for this ID?". It cannot list items. So on each arrival, estimate the item and keep a min-heap of the K best estimates: replace the root when a new estimate beats it. That is O(d + log K) per event.

Can you merge sketches? Yes, if they share w, d and hash seeds: add the grids cell by cell. That is how per-shard or per-minute sketches roll up into one, as in the YouTube Top K design.

When not to use one: when exact counts matter (billing), or when the distinct set fits in memory anyway. A common pattern: the sketch picks candidates, then those few hundred are counted exactly or reconciled by a batch job.

Alternatives: Misra-Gries and Space-Saving keep K explicit counters and list the heavy hitters directly; the Count Sketch gives unbiased estimates that can be low as well as high.
