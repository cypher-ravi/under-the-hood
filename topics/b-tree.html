B-Tree Index

A B-tree is a search tree built for storage that reads in pages, not bytes. Each node is one page and holds many sorted keys, so the tree is very wide and very short: a few hundred children per node means a billion rows sit only four levels deep. Nodes that overflow split in half and push a key up to their parent, which keeps every leaf at the same depth without any rebalancing rotations. This page simulates the B+ tree variant used by most databases, where all keys live in linked leaves.

Worked example

Seven inserts and a lookup, traced by hand

Each node holds at most 3 keys. To follow along, set the slider to 3, press Reset, and insert 10, 20, 30, 40, 50, 60 and 25 one at a time.

  1. The root starts as a leaf

    Insert 10, 20, 30. The tree is a single page, kept sorted: [10 20 30]. It's full, but not over.

  2. Insert 40: the first split

    The leaf would hold [10 20 30 40], one too many. Split it into [10 20] and [30 40], link the left leaf to the right one, and copy the right leaf's first key, 30, up as a separator. There is no parent, so a new root [30] is made. Height goes from 1 to 2. The tree grows at the top, never at the bottom, which is why every leaf stays at the same depth.

  3. Insert 50 and 60

    Both are ≥ 30, so they go right. 50 fits: [30 40 50]. 60 overflows it, so it splits into [30 40] and [50 60], and 50 is copied up. The root becomes [30 50] with three children.

  4. Insert 25

    At the root, 25 < 30, so take the first child: [10 20 25]. No split. Most inserts are like this: one leaf page written, nothing else touched.

  5. Search 40

    Root [30 50]: 40 is ≥ 30 and < 50, so follow the middle pointer. Leaf [30 40]: found. Two pages read, one per level.

    pages read per lookup = height = 2 (for 7 keys)

  6. Range scan 20 to 50

    Descend once to the leaf that would hold 20, then walk right along the leaf links: [10 20 25] → [30 40] → [50 60], stopping once a key passes 50. Result: 20, 25, 30, 40, 50 from four page reads. This leaf chain is why B+ trees are so good at ORDER BY and BETWEEN.

Internal splits work slightly differently. When an internal node overflows, its middle key moves up (it isn't copied), because internal keys are only signposts. Insert 70, 80, 90 and 95 in the simulation after the steps above: the root fills up to [30 50 70 90], splits, and 70 moves up into a new root. The height reaches 3.

The story

An index for disks that read in blocks

In the late 1960s, Rudolf Bayer and Edward McCreight were working at Boeing Research Labs on a practical problem: how to keep a large index on disk that supports fast lookups, inserts and deletes all at once. Binary trees were fine in memory, but on a disk each node visited could cost a separate seek, and a balanced binary tree over a million keys is twenty levels deep. Their answer was to make each node as big as a disk block and let it hold many keys, so one read narrows the search by a factor of hundreds instead of two.

Their paper, "Organization and Maintenance of Large Ordered Indices", first circulated in July 1970 and was published in Acta Informatica in 1972. Nobody ever settled what the "B" stands for. McCreight later said it could be Boeing, balanced, or Bayer, and that they never decided which made the most sense.

By June 1979, Douglas Comer could title his survey in ACM Computing Surveys "The Ubiquitous B-Tree". The variant that took over, the B+ tree, keeps every record in the leaves and links the leaves together for range scans. Today it's the default index in PostgreSQL, MySQL's InnoDB, SQLite and Oracle, and file systems such as NTFS, HFS+ and APFS use B-trees for their metadata.

Make each node exactly as big as one read from the disk, and the tree becomes short enough that its height almost doesn't matter.

From first principles

Rebuilding the idea from the problem

What

A balanced search tree whose nodes are pages holding many sorted keys. Internal nodes hold separator keys and child pointers; leaves hold the keys (and row pointers or rows) and link to their neighbours.

Why

Storage is read a page at a time, and reading one byte costs about as much as reading the whole page. So pack as many keys into each page as fit. With fanout f, a lookup reads logf(n) pages instead of log2(n).

When

Read-heavy data that needs point lookups, range scans and sorted order, with updates in place: most OLTP tables and their secondary indexes.

Where

PostgreSQL, MySQL InnoDB, SQLite, Oracle, SQL Server, MongoDB's WiredTiger, and file systems like NTFS, HFS+ and APFS.

How

Insert into the right leaf. If it overflows, split it in two and add a separator to the parent; if that overflows, split again, up to the root. A root split adds a level on top, so all leaves stay at equal depth. Deletes do the reverse, borrowing from or merging with a sibling when a node gets too empty (not simulated here).

The one-line insight: balance by splitting full nodes upward, not by rotating, and size each node to one page.

The trade-off: every write updates a page in place, so random inserts mean random page writes, plus a write-ahead log for crash safety. That's the cost an LSM tree avoids, at the price of slower reads and background compaction.

What to notice

  • Press Insert 8 random keys a few times and watch the height. It grows by one only when the root splits, and every leaf is always on the bottom row.
  • Press Reset, then Insert 8 in ascending order several times. Every split happens at the right edge and leaves the left half behind half full, so average leaf fill drifts toward 50%. Random inserts settle closer to 70%. That's why many databases special-case appends at the right edge.
  • Search any key and compare "pages touched" with the height: always equal. Then raise max keys per node; the tree gets flatter and the count drops.
  • Run a Range scan: one descent, then the leaf links. In "At real page sizes", set a billion rows and an 8 KB page. The tree is 4 levels tall; a balanced binary tree would be 30.

Interview angle

"Why do databases use B-trees, not binary trees or hash tables?" Page-sized nodes make the tree 3 or 4 levels deep, and the top levels stay cached, so a lookup is about one disk read. A hash index can't do range queries or ORDER BY; a B+ tree's linked leaves give both.

Why are auto-increment or time-ordered keys good for inserts? They always land in the rightmost leaf, so the same few pages stay hot in memory. Random keys like UUIDv4 touch a random leaf each time and cause more splits and cache misses.

B-tree or LSM tree? B-tree for read-heavy workloads that need predictable point and range reads. LSM for write-heavy, append-like data where sequential writes matter more than read cost.
