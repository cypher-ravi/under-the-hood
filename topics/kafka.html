Kafka Partitions

A Kafka topic is not one queue. It is split into partitions, and each partition is an append-only log where every message gets the next number, its offset. Producers pick the partition by hashing the message key, so one key always lands in the same log and stays in order. Consumers in a group divide the partitions between them, and each one remembers how far it got by committing an offset. When a consumer dies, the group rebalances and someone else picks up from the last committed offset, which may mean reading a few messages twice.

    Worked example

    Seven messages, a crash and one duplicate

    A topic with 3 partitions. The group billing has two consumers, C1 and C2, using the range assignor, and commits offsets every 2 seconds. The partition numbers below are the real ones: the simulation uses the same murmur2 hash as Kafka's Java producer, so set it to 3 partitions and the same users land in the same places.

    1. Hash the key, pick the partition

      For a message with a key, the producer computes murmur2(key bytes), clears the sign bit, and takes the remainder by the number of partitions.

      murmur2("alice") = 1951417749 → 1951417749 mod 3 = 0 → P0
      murmur2("carol") = 271431602 → mod 3 = 2 → P2
      murmur2("dave") = 1727131798 → mod 3 = 1 → P1

      The other three users work out the same way: bob → P0, erin → P2, frank → P1. The hash knows nothing about load. It just spreads keys, and with six keys and three partitions it happens to give two each.

    2. Seven messages are appended

      In order: alice, carol, dave, alice, erin, carol, bob. Each goes to the end of its partition's log and gets that log's next offset. Offsets are per partition, so three different messages all have offset 0.

      PartitionOffset 0Offset 1Offset 2Log end
      P0alice #1alice #4bob #73
      P1dave #31
      P2carol #2erin #5carol #63

      alice's two messages sit at P0 offsets 0 and 1, so whoever reads P0 sees #1 before #4. Nothing promises that dave #3 is read before alice #4: they are in different logs.

    3. Range assignment

      The range assignor sorts partitions and consumers, then hands out runs: 3 partitions ÷ 2 consumers = 1 each, with 1 left over for the first consumer. So C1 gets P0 and P1, C2 gets P2. Round-robin would deal them like cards instead: C1 gets P0 and P2, C2 gets P1.

    4. C2 reads, commits, reads one more, then crashes

      C2 processes P2 offsets 0 and 1, and its 2-second timer commits offset 2 for P2. A committed offset means "the next one I need", not "the last one I read". C2 then processes offset 2 (carol #6) and crashes before the next commit.

      lag(P2) = log end − committed = 3 − 2 = 1

    5. Detection, then a rebalance

      C2 stops sending heartbeats. The group coordinator (a broker) waits out the session timeout, removes C2 and starts a rebalance. In the classic protocol every member stops, gives up its partitions (C1 commits what it has read first) and rejoins. Only C1 is left, so it now owns P0, P1 and P2.

    6. The duplicate

      C1 starts P2 at the committed offset, 2. That is carol #6, which C2 had already processed. It gets processed a second time. This is at-least-once delivery: nothing is lost, but anything between the last commit and the crash is repeated. Committing more often shrinks the window; it never closes it, because the crash can land between "process" and "commit".

    7. Adding a partition moves keys

      Go from 3 to 4 partitions and the remainders change: alice 0 → 1, bob 0 → 2, dave 1 → 2, erin 2 → 0, frank 1 → 3. Only carol stays put. alice's new messages go to P1 while her older ones may still be waiting in P0, so for a while her events can be read out of order. To see it, set 3 partitions, turn on the hot key so alice's partition builds a backlog, then press Add partition live and watch the out-of-order counter.

    The rule to remember: Kafka orders messages within a partition and nowhere else. If two events must be processed in order, give them the same key.

    The story

    A log that LinkedIn needed and everyone else wanted

    Around 2010 LinkedIn had a plumbing problem. Every page view, search and click produced activity events, and servers produced a constant stream of metrics. Some teams wanted that data within seconds, for things like news feed relevance, and others wanted all of it loaded into Hadoop overnight. The message queues of the day, such as ActiveMQ and RabbitMQ, tracked every message's delivery state on the broker and struggled at that volume. Log collectors such as Facebook's Scribe and Flume were built for shipping files to batch systems.

    Jay Kreps, Neha Narkhede and Jun Rao built Kafka to do both jobs. Their design was deliberately simple: a topic is split into partitions, each partition is an append-only log on disk, and the broker does not track who has read what. Each consumer keeps its own offset. That one choice removed per-message acknowledgements and let many readers share the same data. Their 2011 paper at the NetDB workshop reported producer and consumer throughput several times higher than ActiveMQ and RabbitMQ in their tests, with LinkedIn already moving close to a billion messages a day through it.

    Kreps named it after Franz Kafka. He has said that a system optimized for writing should be named after a writer, and that he had liked Kafka's books in college.

    LinkedIn open-sourced Kafka in early 2011, and it graduated from the Apache Incubator in October 2012. In 2014 the three creators left to found Confluent, a company built around it. For most of its life Kafka relied on ZooKeeper to store cluster metadata and, originally, consumer offsets. Offsets later moved into an internal Kafka topic, and the KRaft project replaced ZooKeeper with a Raft-based controller quorum inside Kafka itself. KRaft was declared production-ready for new clusters in Kafka 3.3 (2022), and Kafka 4.0 (2025) removed ZooKeeper entirely.

    Don't track who has read each message. Keep the log, and let each reader remember a number.

    From first principles

    Rebuilding the idea from the problem

    What

    A topic split into partitions. Each partition is an append-only log with numbered offsets. Consumer groups split the partitions among their members, and each group stores its own committed offset per partition.

    Why

    One log on one machine has a ceiling on throughput and a single reader. Partitions spread the log across brokers and let many consumers read in parallel, while a key-to-partition rule keeps each key's events in order.

    When

    High-volume event streams that several systems need to read independently: activity tracking, logs and metrics, change data capture, order and payment events, feeding search indexes and caches.

    Where

    Inside Kafka itself, and in systems built on the same model: Amazon Kinesis (shards), Apache Pulsar, Redpanda, Azure Event Hubs.

    How

    partition = hash(key) mod N. Brokers append and never track readers. A group coordinator assigns partitions to live consumers and rebalances when one joins or stops heartbeating. Consumers commit "next offset to read"; after a rebalance the new owner resumes from it.

    The one-line insight: parallelism comes from partitions, and ordering is only promised inside one.

    The trade-off: more partitions mean more parallel consumers and more throughput, but more files and leaders per broker, longer rebalances, and every key moves if you change the count. A group can never use more consumers than there are partitions; extras sit idle.

    What to notice

    • Press Add consumer until there are more consumers than partitions. The extras get nothing and show as idle: a partition has exactly one owner per group.
    • Set commits to every 5 s, then kill a busy consumer. Its partitions stall during the session timeout, every consumer pauses for the rebalance, and "messages read twice" jumps by however many it read since its last commit. Set commits to "every message" and repeat.
    • Switch to no key: round-robin. Load spreads perfectly, but the same user's events now sit in different partitions and the out-of-order counter starts climbing. With keys it stays at zero.
    • Turn on the hot key. One partition gets half the traffic and its lag grows while the others are idle. Adding consumers doesn't help, because one key can only live in one partition. Press Add partition live now and alice's new messages go to a new, empty partition and get read before her backlog: the out-of-order counter jumps even with keys.
    • Tick the second consumer group. It starts at offset 0 and reads the whole log at its own pace, with its own offsets (amber marks). The billing group is unaffected.

    Interview angle

    How many partitions? Work back from throughput: if one consumer handles 5,000 msg/s and you need 50,000, you need at least 10 partitions, plus headroom, because adding partitions later moves keys (the same problem consistent hashing solves for caches). Too many cost broker memory, open files and slower failover.

    Hot keys: one celebrity or one big customer can overload a single partition. Fixes: add a suffix to spread that key over several partitions (and merge downstream), or pre-aggregate before producing.

    Ordering: only within a partition. Key by the entity whose events must stay ordered (user, order, account), and accept that there is no order across keys.

    At-least-once vs exactly-once: commit after processing and you may reprocess after a crash, so make the handler idempotent (dedupe by an event ID). Commit before processing and you may lose messages. Kafka's idempotent producer and transactions give exactly-once for read-process-write pipelines that stay inside Kafka.

    Rebalance pauses: in the classic "eager" protocol every consumer stops during a rebalance. Cooperative sticky assignment moves only the partitions that must move, static membership avoids rebalances on quick restarts, and Kafka 4.0's new consumer protocol moves assignment to the broker.

    Durability: each partition is replicated to several brokers and a write is acknowledged once the in-sync replicas have it, a cousin of quorum replication. The log itself is sequential appends, the same reason LSM trees write fast.
