Contention and Distributed Locks

Two buyers press "buy" on the last ticket in the same instant. Each one reads "1 left", each one writes "0 left", and the venue has sold one seat twice. Every fix makes the read and the write behave as one step: lock the row, check a version number when you write, or take a lock from a separate lock service. That last option has a catch. A lock that expires on its own (a lease) can expire while its holder is frozen, and then two clients both think they hold it. A fencing token lets the storage itself turn the stale one away.

    Worked example

    Tokens 33 and 34: a frozen buyer and the store that says no

    Two buyers, one seat, a 100 ms lease, and buyer A freezes for 150 ms after charging the card. These are the default sliders in mode 5, and every time below is what the simulation computes. The lock service starts its counter at 33 so the numbers match the classic version of this example.

    1. A takes the lock (t = 5 ms)

      A asks the lock service for the lock. In Redis that is one command, and the token comes from a counter that only goes up:

      SET lock:seat-C12 A NX PX 100 → OK, token 33, expires at 105 ms

      NX means "only if nobody holds it", PX 100 means "delete it after 100 ms". B arrives at 10 ms, asks at 15 ms, is refused, and starts polling every 20 ms.

    2. A reads, works, then freezes (t = 15 to 205 ms)

      A reads the seat count with token 33. The store sees 1 seat and remembers that the highest token it has seen is 33. A spends 40 ms charging the card, and at 55 ms its process stops for a 150 ms garbage-collection pause. Nothing in A runs, so it cannot notice anything.

    3. The lease runs out (t = 105 ms)

      The lock service has no idea A is frozen. It only knows 100 ms have passed without a release, so it deletes the key. This is exactly what a lease is for: if A had crashed, the seat would otherwise be locked forever.

    4. B gets the lock with token 34 (t = 115 ms)

      B's next poll succeeds. B reads with token 34, sees 1 seat, and the store raises its highest-seen token to 34. B charges the card and writes "0 seats left, sold to B" with token 34 at 175 ms. 34 ≥ 34, so the write is accepted. B releases the lock at 180 ms.

    5. A wakes up and writes (t = 215 ms)

      A resumes at 205 ms believing it still holds the lock, and sends "0 seats left, sold to A" with token 33. Here the two modes differ:

      ModeStore's checkResult
      4 · lease onlynoneaccepted: 2 sold, 1 seat
      5 · fencing33 < 34rejected: A is stale

      With fencing, A learns it lost the lock, starts over, gets token 35 at 220 ms, reads 0 seats and stops. One seat, one sale.

    6. Why the store checks reads too

      Set the pause to 80 ms and untick "checks the token on reads". A now wakes at 135 ms and writes with token 33 while B (token 34) has already read but not yet written. The store has only seen token 33, so A's write passes, and B's write at 175 ms passes too: two sales. B decided to sell on a read that A's write made out of date. When the store also records the token on reads, B's read at 125 ms raises it to 34 first and A's write is rejected. The general rule: every request made under the lock carries the token, and the store refuses anything older than the newest token it has seen.

    7. Release only what you own

      When B finishes, it deletes the key only if the value is still its own, in one atomic step (a small Lua script in Redis). A plain DEL from a client whose lease already expired would delete someone else's lock.

      if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end

    The rule to remember: a lease protects you from a holder that died, and does nothing about a holder that is merely slow. Only the resource can tell an old holder from a new one, so the resource has to check.

    The story

    From Chubby to the Redlock argument

    Large systems at Google kept needing the same thing: pick one master out of many machines and make sure everyone agrees who it is. Mike Burrows described Google's answer, Chubby, at OSDI in 2006. Chubby is a small replicated service that hands out locks and stores small files, kept consistent with Paxos. GFS used a Chubby lock to choose its master, and Bigtable used it to elect a master and to let clients find it. Clients held their locks through sessions with leases (12 seconds by default), and the paper already faced the frozen-holder problem. A lock holder could ask for a sequencer, an opaque string describing the lock at the moment it was taken, and pass it to the servers it talked to so they could reject requests from a holder that had lost the lock. For servers that did not check sequencers, Chubby offered a lock-delay: when a holder failed, the lock could not be taken again for a while (up to a minute).

    In 2010 Patrick Hunt, Mahadev Konar, Flavio Junqueira and Benjamin Reed of Yahoo! presented ZooKeeper at USENIX ATC. Instead of locks it offers a small tree of data nodes with ordered writes and watches, and leaves locks to recipes built on top: each contender creates an ephemeral, sequential node, and the lowest number holds the lock. When a client's session dies, its ephemeral node is deleted and the next in line is told.

    Redis users wanted something lighter. In 2014 Salvatore Sanfilippo (antirez), Redis's creator, proposed an algorithm later called Redlock: take the same lock on a majority of independent Redis servers, each with an expiry, and count the lock as held only if a majority answered within the lease time. In February 2016 Martin Kleppmann published "How to do distributed locking". He argued that Redlock's safety depends on timing assumptions (bounded network delay, bounded pauses, clocks that drift little) that real systems break, and that no lease, however it is acquired, protects you from a client that pauses past its expiry. His fix was the fencing token, a number that goes up with every grant and that the storage checks. He also split locks into two kinds: locks for efficiency, where an occasional double run only wastes work, and locks for correctness, where it corrupts data. Sanfilippo replied within days with "Is Redlock safe?", and the debate is still the standard reading on the subject.

    A lease ends when the lock service's clock says so, not when the holder notices. Anything that matters has to be checked where the data lives.

    From first principles

    Rebuilding the idea from the problem

    What

    Ways to make "read the value, decide, write the value" safe when several clients do it at once: an exclusive lock (pessimistic), a version check on the write (optimistic), or a lock from a separate service with an expiry (a lease), made safe with a fencing token.

    Why

    Between your read and your write, someone else can write. Your write is then based on an old value and silently erases theirs: a lost update. With tickets or money that means selling or spending the same thing twice.

    When

    Any time many clients compete for the same few things: the last seat, a username, an inventory count, a job that should run once, the right to be leader.

    Where

    Inside one database, use its row locks, conditional updates or unique constraints. Across services, use a coordination service built on consensus (ZooKeeper, etcd, Chubby) for correctness, or a single Redis key when a rare double run only costs some wasted work.

    How

    Pessimistic: hold the row lock from read to write, others queue. Optimistic: write only WHERE version = v, retry on failure. Lease: SET NX PX, release with compare-and-delete. Fencing: every grant gets a larger number, and the store refuses any request carrying a number below the largest it has seen.

    The one-line insight: a lock outside the data can only make collisions rare. Making them impossible takes a check at the data: a row lock, a version, a constraint or a token.

    Where the consensus comes in: a lock service that must stay correct when its own servers fail is a replicated state machine. ZooKeeper and etcd keep the lock table on a majority of nodes, the same idea as Raft and quorums. A single Redis node is fast, but if it fails over to a replica that missed the last write, two clients can hold the "same" lock.

    What to notice

    • In mode 1, set the pause to 0. Both buyers still sell the seat: B reads before A writes, so the window is the 40 ms of work, not the pause. With 5 buyers and 1 seat, all 5 buy.
    • Mode 2 is always correct, but look at the waiting time. With 5 buyers and a 150 ms pause, B to E each sit 200 ms behind A's frozen transaction (800 ms of waiting in total) just to learn the seat is gone. In mode 3 they all know by 110 ms.
    • Mode 3 never waits. The losers find out at write time that the version moved, retry, read 0 seats and stop. Under heavy contention for a single row, retries pile up, which is why hot rows often use a lock or a queue instead.
    • In mode 4, drag the pause down. At 30 ms or less, A writes inside its 100 ms lease. From 40 to 60 ms A's write is already unsafe (the counter says so) but lands before B reads, so the count comes out right by luck. From 70 ms on, the seat is sold twice. Raise the TTL to 300 ms and the 150 ms pause is harmless again: a longer lease only moves the cliff.
    • Mode 5, with tokens checked on reads, never oversells for any pause or TTL. The stale write shows up as "rejected" instead of as a second sale. Set the TTL to 40 ms (shorter than the 60 ms a buyer needs from lock to write) and the pause to 20 ms: it stays safe but thrashes. Each holder's lease expires before it can write, the store rejects 7 stale requests, and one buyer gives up.

    Interview angle

    First, avoid the distributed lock. If the data lives in one database, use it: UPDATE seats SET status = 'held' WHERE id = ? AND status = 'available' and check the row count, or a version column, or a unique constraint on (event, seat). That is one atomic step and needs no extra service. The Ticketmaster design does seat holds this way or with a Redis key that expires.

    Pessimistic or optimistic? Locks suit high contention and long critical sections you can't redo; version checks suit low contention, short work and reads that vastly outnumber writes. Never hold a database lock across a slow external call such as a payment.

    Efficiency or correctness? If running twice only wastes work (sending a report, rebuilding a cache), a single Redis SET NX PX is fine. If running twice corrupts data, the lock alone is not enough.

    Lease vs correctness: the TTL must be longer than the work, and nothing bounds a GC pause, a swapped-out page or a stalled network. Say this out loud, then add fencing tokens checked by the resource, or make the write itself conditional.

    Which lock service? ZooKeeper or etcd (consensus, sessions, monotonic revision numbers usable as tokens) for correctness; Redis for speed when an occasional overlap is acceptable. Expect a question on what happens when the lock server fails over.
