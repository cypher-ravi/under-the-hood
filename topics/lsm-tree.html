LSM Tree

A log-structured merge tree never updates data in place. Writes go to a sorted table in memory (and a log, so a crash loses nothing). When that table fills, it is written to disk in one go as an immutable sorted file. Reads check the newest data first and work back. In the background, files are merged so reads don't have to look through too many of them. Writes become fast, sequential appends; reads and background merging pay for it.

Worked example

Seven writes, traced by hand

Memtable holds 3 entries, level 0 is compacted when it reaches 2 files, and every entry carries a sequence number so newer beats older. To follow along, set the sliders to 3 and 2, untick Compact automatically, press Reset, and press Compact now at step 5.

  1. Three writes fill the memtable

    put 20, put 05, put 12. Each is appended to the log on disk (a sequential write) and inserted into the memtable, which keeps keys sorted: 05:v2, 12:v3, 20:v1. Nothing else on disk changes.

  2. Flush: file A in level 0

    The memtable is full, so it is written out as one sorted, immutable file, A = [05, 12, 20], with a key range (05–20) and a small Bloom filter. The log can now be thrown away. 3 entries written to disk for 3 writes: write amplification 1.0 so far.

  3. An update and a delete

    put 12 again (v4), delete 05, put 30. A delete can't erase 05 from file A, because files never change. It writes a tombstone, a marker that says "05 is gone as of v5". Flush gives B = [05:×, 12:v4, 30:v6]. Disk now holds 6 entries for only 3 live keys (12, 20 and 30): space amplification 2.0.

  4. Read 12 before compaction

    Not in the memtable. Check level 0 newest first: B covers 05–30 and its Bloom filter says "maybe", so open it, binary search, find 12:v4. Stop. The older v3 in A is never looked at. One file opened.

  5. Compaction

    Level 0 has 2 files, so merge A and B like the merge step of merge sort. Where both have a key, the higher sequence number wins: 12 keeps v4. 05's newest entry is a tombstone, and there is no older level below, so 05 is dropped entirely. Output, level 1: [12:v4, 20:v1, 30:v6].

    entries written to disk = 3 + 3 (flushes) + 3 (compaction) = 9 for 6 writes → write amplification 1.5

    Space amplification falls back to 1.0: every entry on disk is now a live key. Real systems with several levels rewrite each entry once per level, which is why write amplification of 10 or more is normal.

  6. Read a key that was never written

    get 15: the level 1 file covers 12–30, so the key range can't rule it out. The Bloom filter checks a few bits; if any is 0, the file is skipped without a disk read. Turn the filters off in the simulation and every lookup like this costs a file read.

The rule that keeps reads correct: always search from newest to oldest (memtable, then level 0 newest first, then level 1) and stop at the first entry for the key, whether it's a value or a tombstone.

The story

From bank history tables to every phone

In 1996 Patrick O'Neil, Edward Cheng, Dieter Gawlick and Elizabeth O'Neil published "The Log-Structured Merge-Tree (LSM-Tree)" in Acta Informatica. Their motivating problem was a history table that gets a new row for every transaction. A B-tree index on it does a random disk read and write for each insert, and disks of the day could only do so many of those a second. Their answer was to batch inserts in a small tree in memory and merge them into a larger tree on disk in long sequential passes, which disks did far faster.

A decade later Google's Bigtable paper (OSDI 2006) brought the design to the mainstream. Writes went to a commit log and an in-memory memtable; full memtables became immutable SSTable files; "minor" and "major" compactions merged them. Facebook's Cassandra, built for inbox search and open-sourced in July 2008, adopted the same write path, and HBase did the same as an open-source Bigtable.

In 2011 Jeff Dean and Sanjay Ghemawat open-sourced LevelDB, a small library modeled on Bigtable's tablet storage, with the "leveled" compaction scheme that this page simulates. Facebook forked it into RocksDB, tuned for flash storage, and open-sourced that in 2013. RocksDB now sits under many databases, and LevelDB stored data in Chrome's IndexedDB.

Turn many small random writes into a few large sequential ones, and pay the bill later, in the background.

From first principles

Rebuilding the idea from the problem

What

A sorted table in memory plus a stack of immutable sorted files on disk. Writes go to memory; reads search newest to oldest; background merges keep the stack short.

Why

Updating a B-tree in place means a random read and write per insert. Batching writes in memory and writing whole sorted files turns them into sequential I/O, which is much faster on disks and gentler on flash.

When

Write-heavy workloads: logs, metrics, messages, event streams, time series, anything where inserts outnumber reads or arrive in bursts.

Where

Bigtable, HBase, Cassandra, ScyllaDB, LevelDB, RocksDB and the many databases built on RocksDB.

How

Sequence numbers decide which version is newest. Tombstones mark deletes. Bloom filters and key ranges let reads skip files. Compaction merges files, drops old versions and tombstones, and keeps the number of files a read must check small.

The one-line insight: never modify a file; write new ones and merge them later.

The trade-off: three amplifications pull against each other. Compact eagerly and reads are cheap but each entry is rewritten many times (write amplification). Compact lazily and writes are cheap but reads open more files (read amplification) and dead versions pile up (space amplification).

What to notice

  • Press Write 10 random keys a few times. Each compaction rewrites everything in level 1, so "entries written to disk" grows faster than your writes. Raise the level 0 trigger and write amplification drops.
  • Turn off Compact automatically, flush several times, then Get a key that sits in the oldest file. The read opens one file per overlapping level 0 file on the way.
  • Turn off Bloom filters and Get a key you never wrote. Every file whose range covers it gets opened. With filters on, most are skipped; now and then a false positive slips through and is counted.
  • Delete a key and look for the tombstone (×). Space amplification rises until a compaction into level 1 drops both the tombstone and the old value.

Interview angle

"Why does Cassandra write so fast?" A write is an append to the commit log plus an insert into memory. No disk seek, no read-before-write. The cost moves to compaction, which runs in the background.

LSM tree or B-tree? LSM for write-heavy, append-like data, and when space efficiency matters (compressed immutable files). B-tree for read-heavy workloads that need predictable point reads and range scans, like most OLTP databases.

Leveled vs size-tiered compaction: leveled keeps one sorted run per level, so reads are cheap but writes are amplified. Size-tiered merges similar-sized files, cutting write cost but leaving more files for reads and needing spare disk during merges.
