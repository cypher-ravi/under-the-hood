LRU Cache

A cache has room for only a few items. When it is full and a new item arrives, the Least Recently Used item is thrown out. A hash map finds any item in O(1), and a doubly linked list keeps items in order of use, so every get and every eviction is also O(1).

LRU gets 1 hit out of 8. Now replay the same reads with a cache that can see the future. At read 5 it evicts C instead of B, because C is never read again. At read 7 it evicts D for the same reason. It gets 3 hits (reads 4, 6 and 8), which is the best any policy can do here.

The lesson: LRU is a guess. It bets that what you used recently you will use again soon. When the bet is right, as with a hot set of popular items, it does very well. When access is a loop slightly larger than the cache, every guess is wrong. Try the "Loop over 5 keys" pattern: LRU scores 0%.

The data structure, step by step

  1. Find: map.get(key) returns the node, or nothing. A hash map does this in O(1) on average. A list alone would need O(n) to search.

  2. Move to front on a hit: unlink the node with node.prev.next = node.next and node.next.prev = node.prev, then splice it in after the head. That is four pointer writes, O(1). A singly linked list can't do this, because it doesn't know the node's predecessor without a scan.

  3. Evict on a miss when full: the least recently used node is always tail.prev. Unlink it and delete its key from the map. Both are O(1). The node stores its own key so you know which map entry to delete.

  4. Sentinels: the dummy HEAD and TAIL nodes mean every real node always has a neighbour on both sides, so there are no special cases for an empty list or the first and last node.

The story

How early computers decided what to forget

In the early 1960s, fast memory was tiny and expensive, while slower drum or disk storage was much larger. Programmers spent a lot of effort manually shuffling pieces of their program between the two. The Atlas computer, built at the University of Manchester, changed that in 1962. It gave programs the illusion of one large memory and moved fixed-size pages between fast core memory and the slower drum by itself. This was the first virtual memory.

That created a new question the machine had to answer thousands of times a second: when memory is full and a new page is needed, which page do you throw out? A bad answer means the page you just removed is needed again right away, and the machine spends its time copying pages instead of computing.

In 1966 László Bélády at IBM published a study comparing replacement algorithms. He described the best possible one, now called MIN or Bélády's algorithm: evict the page that will not be needed for the longest time. It is provably optimal, and impossible to run for real, since the computer cannot see the future. Its value is as a yardstick. You can run it after the fact on a recorded trace and see how close a practical policy gets.

The practical answer came from observing real programs. In 1968 Peter Denning at MIT described the working set model: over any short period a program uses a fairly small group of pages, and that group changes slowly. This behaviour, called locality of reference, is why looking backward works. If a page was used a moment ago, it will probably be used again soon. Least Recently Used is that idea turned directly into a rule.

Exact LRU turned out to be too costly for hardware to track on every memory access, so operating systems use cheaper approximations such as the clock algorithm. In software, where a hash map plus a linked list makes exact LRU cheap, it became the default cache policy, and a standard interview question.

  1. 1962

    The Atlas computer at Manchester introduces virtual memory with automatic paging.

  2. 1966

    Bélády publishes "A study of replacement algorithms for a virtual-storage computer" in the IBM Systems Journal, including the optimal MIN policy.

  3. 1968

    Denning publishes the working set model, explaining why recent use predicts future use.

  4. 1969

    Bélády and colleagues show that FIFO can get more misses with more memory (Bélády's anomaly). LRU never does this.

  5. Today

    Redis evicts using approximate LRU: it samples a few keys (5 by default) and evicts the oldest of those. Linux keeps active and inactive page lists. CPU caches use pseudo-LRU in hardware. Memcached, browsers and CDNs use LRU variants.

From first principles

Rebuilding the idea from the problem

What

A fixed-size store that, when full, evicts the item whose last use is furthest in the past.

Why

Fast storage is small and slow storage is large. The ideal rule needs knowledge of the future, so we use the recent past as the best available predictor.

When

The 1960s, when virtual memory made page replacement an automatic, constant decision.

Where

Manchester (Atlas), IBM Research (Bélády's comparison) and MIT (Denning's working set model).

How

Keep items ordered by last use. A hash map gives O(1) lookup, and a doubly linked list gives O(1) move-to-front and evict-from-back.

The one-line insight: programs have locality. What was used recently is likely to be used again soon.

Where it breaks: a single large scan (a backup, a full table read) touches many items once and pushes the genuinely hot ones out. Variants like LRU-K, 2Q and ARC exist to resist this.

What to notice

  • On a hit only the pointers change. The node itself never moves in memory, and the map entry stays the same.
  • "Hot set" gets a high hit rate close to optimal, because the popular keys keep getting refreshed.
  • "Loop over 5 keys" with room for 4 gets 0% with LRU. Each key is evicted just before it is needed again. Optimal still gets hits.
  • "Hot pair, then a scan" shows scan pollution. The one-time keys C to H push A and B out, and then A and B miss.

Interview angle

Why doubly linked? To unlink a node in O(1) you need its predecessor. A singly linked list would need an O(n) scan to find it.

Why store the key in the node? On eviction you only have the tail node, and you need its key to delete the map entry.

Follow-ups: make it thread-safe (one lock, or sharded caches), add expiry times, and explain why Redis only approximates LRU (a linked list across millions of keys costs memory and pointer updates on every read).
