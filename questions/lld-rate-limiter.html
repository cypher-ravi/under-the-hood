Design a Rate Limiter (classes)

One process, one library: before a request reaches its handler, ask "may this client do this right now?" and get back yes, or no with a time to come back. The four classic algorithms are each a dozen lines. What the interviewer is really looking for is the shape around them: rules that differ per endpoint and per plan, an algorithm you can swap without touching the caller, a clock you can fake in tests, state that lives behind an interface so it can move to Redis later, and a check that stays correct when eight threads ask about the same client at once.

The interview flow is adapted from Hello Interview's delivery framework for a 45-minute round. The breakdown, diagram and code on this page are our own. For the algorithms on their own, see the Rate Limiters concept page; for many servers sharing one limit, the high-level design.

1

Requirements

about 5 minutes

Say early that this is the in-process version. Sharing a limit across a fleet of servers, Redis sharding and failing open are the high-level question; here they show up only as a seam (a pluggable store) you leave for later.

Functional: the limiter should

  • Limit each client (user ID, API key or IP) separately: one noisy client never uses up another's quota.
  • Apply rules per endpoint and per tier: /search allows 3 requests per 10 s on the free plan and 6 on pro; /login has its own rule; anything else falls back to a default.
  • Support several algorithms: token bucket, fixed window, sliding log and sliding counter, chosen per rule.
  • Answer allow or deny, with how many requests are left and, on a deny, how many seconds to wait (the Retry-After header).

Non-functional: the code should

  • Be thread-safe: concurrent requests from one client never get more than the limit between them.
  • Be fast: O(1) work per check for every algorithm except the log, and no global lock that makes unrelated clients queue.
  • Be testable: time comes from an injected clock, so a test can say "now it's 10.5 s" instead of sleeping.
  • Keep state behind a store interface: in memory today, a shared store such as Redis later, with no change for the limiter's callers.

Ask this early: is the limit per server or global? If the answer is "global across 50 gateways", the in-memory store below is wrong on its own and the conversation becomes the high-level design. Pinning it down decides whether the store is a dictionary or a network call.

2

Core entities and their responsibilities

about 3 minutes

The trap is one RateLimiter class with a dictionary of counters and an if algorithm == ... chain. Pull apart the three things that change for different reasons: which rule applies, how a rule is enforced, and where the counts live.

RateLimiter

the facade: check(client, endpoint, tier) → Decision; wires rule, algorithm, store and clock together

Rule

name, limit, window and algorithm name; plain immutable data

RuleProvider

finds the rule for an (endpoint, tier), with fallbacks to a default

LimiterStrategy

interface: given a client's old state and the time, return new state + verdict

TokenBucket and co.

the four algorithms; each knows its own state shape, none stores it

LimiterFactory

turns "token_bucket" in a rule into the class

StateStore

per-key state; runs one read-modify-write per key atomically

Clock

now(); the system clock in production, a fake one in tests

Decision

allowed, remaining, retry_after, rule name

The key split: a strategy object holds the rule's numbers (limit, window), not any client's numbers. So one TokenBucket serves a million clients, and their buckets are just small tuples in the store. That is what lets the store move out of the process later.

4

Interfaces of the main classes

about 5 minutes

The strategy interface is the one to get right. It takes the client's old state and the time, and returns new state plus a verdict. It never reads a clock, never touches a dictionary and never takes a lock, which makes each algorithm a pure function you can test with three lines.

class RateLimiter:
    __init__(rules: RuleProvider, store: StateStore, clock: Clock)
    check(client: str, endpoint: str, tier: str) -> Decision
    subscribe(listener: DecisionListener) -> None

interface LimiterStrategy:                # built once per Rule, shared by all clients
    acquire(state | None, now: float) -> (new_state, allowed, remaining, retry_after)

interface StateStore:
    atomic(key: str, fn: state -> (state, result)) -> result
                                           # no other update to key runs in between
interface Clock:
    now() -> float                         # seconds; must never go backwards

class RuleProvider:
    resolve(endpoint, tier) -> Rule        # exact, then (endpoint, "*"), then default

record Decision(allowed: bool, remaining: int, retry_after: float, rule: str)

Why atomic(key, fn) and not get plus set: a get-then-set pair invites every caller to forget the lock between them. Passing the whole read-modify-write as one function puts the atomicity where the data lives, so an in-memory store can use a lock and a Redis store can use a transaction, and the limiter can't tell the difference. Why deny is not an exception: being over the limit is a normal answer, so it comes back as a Decision; exceptions stay for bugs like an unknown algorithm name.

5

Design patterns, and why

about 5 minutes

Each pattern below answers a line in the requirements. The last card is the one people reach for and shouldn't.

Strategy: the algorithm

"Several algorithms, chosen per rule" is the textbook case. RateLimiter calls acquire on whatever LimiterStrategy the rule names, so login can use a strict sliding log while search uses a forgiving token bucket. The walkthrough swaps all four with one dropdown.

Not worth it if the product only ever wants a token bucket. One class is clearer; extract the interface when a second algorithm is asked for.

Factory: rule to algorithm

Rules come from config as data: algorithm: "sliding_log". One dictionary maps that name to a class, so a new algorithm is one class and one entry, and a rule that names an algorithm that doesn't exist fails loudly instead of silently allowing everything.

Not worth it as a hierarchy of factory classes. The dictionary is the whole pattern.

Decorator: the middleware

RateLimitedHandler wraps any handler and has the same call shape, so it can sit in front of an endpoint without the endpoint knowing. It turns a deny into 429 with Retry-After. Some call this a proxy; the point is the same: limiting is added around the handler, not inside it.

Watch out: put it after authentication (identify the client first, then limit), or every anonymous request counts against one "unknown" bucket.

Observer: metrics and alerts

Dashboards want deny rates per rule; security wants an alert when one IP keeps hitting login. DecisionListeners hear about every decision without the limiter knowing who listens.

Watch out: listeners run on the request path, after the lock is released. Keep them to a counter bump; anything slow goes on a queue.

Singleton: resist it

"One limiter per process" tempts a global RateLimiter.instance(). That hard-wires the real clock and the in-memory store, and tests start sleeping. Build one at startup and pass it in: the demo builds a fresh limiter per algorithm because nothing is global.

    import math, threading, time
from abc import ABC, abstractmethod
from collections import Counter, deque
from dataclasses import dataclass

class Clock(ABC):
    @abstractmethod
    def now(self): ...
class SystemClock(Clock):
    def now(self): return time.monotonic()   # never jumps back, unlike time.time()
class FakeClock(Clock):                      # tests and the demo move time by hand
    def __init__(self, t=0.0): self.t = t
    def now(self): return self.t

@dataclass(frozen=True)
class Rule:
    name: str
    limit: int                               # this many requests ...
    window: float                            # ... per this many seconds
    algorithm: str                           # a LimiterFactory key

@dataclass(frozen=True)
class Decision:
    allowed: bool
    remaining: int
    retry_after: float                       # seconds; 0 when allowed
    rule: str

class RuleProvider:
    def __init__(self, default): self.rules, self.default = {}, default
    def add(self, endpoint, tier, rule): self.rules[(endpoint, tier)] = rule
    def resolve(self, endpoint, tier):       # most specific match wins
        return (self.rules.get((endpoint, tier)) or self.rules.get((endpoint, "*"))
                or self.default)

class LimiterStrategy(ABC):                  # Strategy: one algorithm, no per-client state
    def __init__(self, rule): self.L, self.W = rule.limit, rule.window
    @abstractmethod
    def acquire(self, state, now): ...       # -> (new_state, allowed, remaining, retry_after)
    @abstractmethod
    def describe(self, state, now): ...

class TokenBucket(LimiterStrategy):          # state: (tokens, last_refill)
    def acquire(self, s, now):
        tokens, last = s if s else (self.L, now)
        tokens = min(self.L, tokens + (now - last) * self.L / self.W)
        if tokens >= 1:
            return (tokens - 1, now), True, math.floor(tokens - 1), 0.0
        return (tokens, now), False, 0, (1 - tokens) * self.W / self.L
    def describe(self, s, now): return f"tokens={s[0]:.2f}"

class FixedWindow(LimiterStrategy):          # state: (window_start, count)
    def acquire(self, s, now):
        start = math.floor(now / self.W) * self.W
        count = s[1] if s and s[0] == start else 0
        if count < self.L:
            return (start, count + 1), True, self.L - count - 1, 0.0
        return (start, count), False, 0, start + self.W - now
    def describe(self, s, now): return f"window {s[0]:g}-{s[0] + self.W:g}s count={s[1]}"

class SlidingLog(LimiterStrategy):           # state: deque of allowed times
    def acquire(self, log, now):
        log = log if log is not None else deque()
        while log and log[0] <= now - self.W: log.popleft()
        if len(log) < self.L:
            log.append(now)
            return log, True, self.L - len(log), 0.0
        return log, False, 0, log[0] + self.W - now
    def describe(self, log, now): return "log=[" + " ".join(f"{t:g}" for t in log) + "]"

class SlidingCounter(LimiterStrategy):       # state: (window_start, prev, curr)
    def roll(self, s, now):
        start = math.floor(now / self.W) * self.W
        old, prev, curr = s if s else (start, 0, 0)
        if start != old:                     # moved into a new window
            prev, curr = (curr if start - old == self.W else 0), 0
        weight = (self.W - (now - start)) / self.W   # share of prev still in view
        return start, prev, curr, prev * weight + curr
    def acquire(self, s, now):
        start, prev, curr, est = self.roll(s, now)
        if est < self.L:
            return (start, prev, curr + 1), True, max(0, math.ceil(self.L - est - 1)), 0.0
        if curr < self.L:                    # wait until prev's share fades enough
            wait = start + self.W * (1 - (self.L - curr) / prev) - now
        else:                                # wait for the next window
            wait = start + self.W * (2 - self.L / curr) - now
        return (start, prev, curr), False, 0, wait
    def describe(self, s, now):
        start, prev, curr, est = self.roll(s, now)
        return f"prev={prev} curr={curr} est={est:.2f}"

class LimiterFactory:                        # Factory: rule.algorithm -> class
    kinds = {"token_bucket": TokenBucket, "fixed_window": FixedWindow,
             "sliding_log": SlidingLog, "sliding_counter": SlidingCounter}
    @classmethod
    def create(cls, rule): return cls.kinds[rule.algorithm](rule)

class StateStore(ABC):
    @abstractmethod
    def atomic(self, key, fn): ...           # run fn(old) -> (new, result) with no other
                                             # update to key in between; return result
class InMemoryStore(StateStore):
    def __init__(self): self.data, self.locks, self.guard = {}, {}, threading.Lock()
    def atomic(self, key, fn):
        with self.guard:                     # held only to find or make the key's lock
            lock = self.locks.setdefault(key, threading.Lock())
        with lock:                           # two clients never wait on each other
            self.data[key], result = fn(self.data.get(key))
            return result

class DecisionListener(ABC):                 # Observer: metrics, logs, alerts
    @abstractmethod
    def on_decision(self, client, decision): ...

class RateLimiter:
    def __init__(self, rules, store, clock):
        self.rules, self.store, self.clock = rules, store, clock
        self.limiters, self.listeners = {}, []
    def subscribe(self, listener): self.listeners.append(listener)
    def check(self, client, endpoint, tier):
        rule = self.rules.resolve(endpoint, tier)
        if rule not in self.limiters:        # strategies hold no client state,
            self.limiters[rule] = LimiterFactory.create(rule)   # so a racing duplicate is harmless
        limiter = self.limiters[rule]
        def step(state):
            now = self.clock.now()           # read time inside the critical section
            new, ok, left, wait = limiter.acquire(state, now)
            return new, Decision(ok, left, wait, rule.name)
        decision = self.store.atomic(f"{rule.name}:{client}", step)
        for listener in self.listeners: listener.on_decision(client, decision)
        return decision

class RateLimitedHandler:                    # Decorator: same call shape as the handler
    def __init__(self, inner, limiter, endpoint):
        self.inner, self.limiter, self.endpoint = inner, limiter, endpoint
    def __call__(self, client, tier):
        d = self.limiter.check(client, self.endpoint, tier)
        if not d.allowed:
            return 429, f"Retry-After: {max(1, math.ceil(d.retry_after))}"
        return self.inner(client, tier)

# ---------------- demo ----------------
class Metrics(DecisionListener):
    def __init__(self): self.counts, self.lock = Counter(), threading.Lock()
    def on_decision(self, client, d):
        with self.lock: self.counts["allow" if d.allowed else "deny"] += 1

TIER = {"ann": "free", "bob": "pro"}
EVENTS = [(2, "ann"), (5, "bob"), (8, "ann"), (9, "ann"), (10.5, "ann"),
          (10.5, "ann"), (11, "ann"), (14, "ann"), (17, "ann")]

def build(algorithm, clock):
    rules = RuleProvider(default=Rule("default", 100, 60, "token_bucket"))
    rules.add("/search", "free", Rule("search-free", 3, 10, algorithm))
    rules.add("/search", "pro", Rule("search-pro", 6, 10, algorithm))
    return RateLimiter(rules, InMemoryStore(), clock)

def run(algorithm):
    clock, metrics = FakeClock(), Metrics()
    lim = build(algorithm, clock)
    lim.subscribe(metrics)
    print(f"== {algorithm}: free 3 per 10 s, pro 6 per 10 s ==")
    for t, client in EVENTS:
        clock.t = t
        d = lim.check(client, "/search", TIER[client])
        rule = lim.rules.resolve("/search", TIER[client])
        state = lim.store.data[f"{rule.name}:{client}"]     # a peek, for printing only
        verdict = f"ALLOW left={d.remaining}" if d.allowed else f"DENY  retry={d.retry_after:.2f}s"
        print(f"t={t:>4} {client}  {verdict:<19} {lim.limiters[rule].describe(state, t)}")
    print(f"metrics: {metrics.counts['allow']} allowed, {metrics.counts['deny']} denied")

for algorithm in LimiterFactory.kinds:
    run(algorithm)

    8a
    Deep dive: one token, two threads
    about 4 minutes
    
    
    Every algorithm is read-modify-write: read the state, decide, write it back. Two threads checking the same client can both read "1 token left" before either writes. Below, threads T1 and T2 check one client whose bucket holds exactly 1 token. The schedule says which thread runs its next line. Try no protection, a lock, and compare-and-set.
    
    
    
    
    Ways to make it safe
    
    
      
      
    • One global lock. Correct and two lines long, but every client now queues behind every other client. With thousands of requests a second across cores, that one lock becomes the bottleneck the limiter was supposed to prevent.
      • 
      
    • A lock per key (what InMemoryStore does). Requests for different clients never wait for each other; only one client's own concurrent requests line up, and each holds the lock for microseconds. A small guard lock protects the dictionary of locks itself. With millions of keys, use a fixed array of, say, 64 locks picked by hash(key) % 64 (lock striping) so the lock table doesn't grow forever.
      • 
      
    • Compare-and-set. Keep a version with the state; write only if the version is still the one you read, otherwise re-read and decide again. No lock is held while deciding, and it works across processes: it is what Redis WATCH/MULTI does. Under heavy contention on one key, retries pile up.
      • 
      
    • Do it where the data is. A Lua script in Redis runs read, decide and write as one command, which no other command can interleave with. That's the high-level design's answer, and it fits behind the same atomic method.
      • 
    
    
    
    A subtle one: read the clock inside the lock. If thread A reads now = 10.0, then thread B reads 10.1 and updates first, A then refills with a negative elapsed time and moves last_refill backwards. Reading time inside atomic (as check does) keeps updates in time order. And use a monotonic clock: wall-clock time can jump back when it is synchronised.

    The Redis store is the honest stress test. It has to keep the atomic(key, fn) promise across processes. The direct way is optimistic: watch the key, read, run fn locally, and commit only if nobody wrote in between, otherwise retry.
    

    class RedisStore(StateStore):              # sketch, using redis-py
    def atomic(self, key, fn):
        while True:
            with self.redis.pipeline() as p:
                try:
                    p.watch(key)                 # EXEC fails if key changes
                    new, result = fn(decode(p.get(key)))
                    p.multi()
                    p.set(key, encode(new), ex=self.ttl)
                    p.execute()
                    return result
                except WatchError:
                    continue                 # someone wrote first: retry
    
    
    That costs two or three round trips per check, and each server reads its own clock, so clocks that disagree skew the refill. The faster version moves the algorithm into a Lua script per strategy, which runs in one round trip and can use Redis's own clock. Then each strategy gains a script next to acquire. That is the one honest edit: the in-memory design let the algorithm run anywhere; a shared store wants it to run in the store.
    
    
    Idle clients: the in-memory store never forgets a key. Give each entry an expiry of one window after its last use (Redis does this with ex=), or sweep keys whose state has fully refilled: a full bucket and a missing bucket behave the same.
    
  
    

  
    
    
    8c
    Deep dive: SOLID, and where to stop
    about 2 minutes
    
    
    
      
    Single responsibility
    The provider picks a rule, a strategy does arithmetic, the store does atomicity, the limiter wires them. The limiter also caches strategies; splitting that into a StrategyRegistry would be a class with one dictionary in it.
    
      
    Open/closed
    New algorithms, stores and listeners arrive as new classes (see 8b). Weighted costs and multiple rules per request do edit the core, because they change the question being asked.
    
      
    Liskov
    Every strategy must accept None as "new client" and return a non-negative retry_after. A store that runs fn twice after a conflict is fine; one that writes a stale result would break the limit while keeping the same signature.
    
      
    Interface segregation
    Listeners see a client and a decision, never state. Strategies never see the store. The decorator sees only check.
    
      
    Dependency inversion
    The limiter depends on Clock and StateStore, not on time or a dictionary. That is why the demo can set the time to 10.5 and why the store can become Redis.
    
      
    Where to stop
    No interface for Rule or Decision: plain records. Per-client state is a tuple, not a BucketState class hierarchy; it has to be serialisable for Redis anyway.
    
    
    
  
    

  
    
    Worked example
    
    Ann across the 10-second boundary, by hand
    
    
    Free plan: 3 requests per 10 s. Ann's requests arrive at 2, 8, 9, 10.5, 10.5 and 11 seconds (bob's single request at 5 s uses a different key, search-pro:bob, and never touches her state). These match the Python output.
    
    
      
      
    1. 2, 8 and 9 s: everyone agrees
      Three requests, limit three: all four algorithms allow all three. The fixed window's count is 3 in window 0–10; the log holds [2 8 9]; the counter's curr is 3.
      2. 
      
    2. Token bucket at 10.5 s
      The bucket starts full at 3 and is 2 after the first request. By 8 s it has refilled to the cap of 3 (it can't hold more), and spending leaves 2; by 9 s it gains 0.3 to 2.30, and spending leaves 1.30. At 10.5 s: 1.30 + 1.5 × 3/10 = 1.75. That's at least 1, so spend: 0.75 left, allowed. The second request at 10.5 finds 0.75 and is denied with retry (1 − 0.75) × 10/3 = 0.83 s.
      3. 
      
    3. Fixed window at 10.5 s
      floor(10.5 / 10) × 10 = 10, a new window, so the count restarts at 0. 10.5, 10.5 and 11 are all allowed. Ann made 6 requests between 2 and 11 seconds against a limit of 3 per 10 s: the boundary burst.
      4. 
      
    4. Sliding log at 10.5 s
      Drop times ≤ 10.5 − 10 = 0.5: none. Three remain, so deny; the oldest, 2, leaves the window at 12, so retry = 1.50 s. At 14 s, 2 is dropped and ann gets in again.
      5. 
      
    5. Sliding counter at 10.5 s
      New window: prev = 3, curr = 0. Half a second in, 95% of the previous window still overlaps the last 10 s: est = 3 × 0.95 + 0 = 2.85 < 3, allowed. Now est = 3.85, so the next one is denied until 3 × weight + 1 < 3, which means weight < 2/3, reached at 13.33 s: retry 2.83 s.
      6. 
    
    
  
    

  
    
    From first principles
    
    What the problem really is
    
    
    
      
    What
    A tiny state machine per (rule, client), advanced by time and by requests, answering yes or no.
    
      
    Why it's hard
    Not the arithmetic. It's that the state is shared by concurrent requests, and that time is an input you must control to test anything.
    
      
    Key insight
    Make each algorithm a pure function of (old state, now). Then the clock, the storage and the locking are separate pieces you can swap, and the same function runs in memory, in a test, or inside Redis.
    
      
    Same shape elsewhere
    Login lockouts after N failures, per-user quotas, circuit breakers counting recent errors, debouncing a button: a counter over a time window, keyed by who.
    
    
    
  
    

  
    
    
    
      
    Follow-up questions to expect
    
      
      
        
    • Burst plus steady rate: a token bucket with capacity 20 and refill 5 a second allows a burst of 20, then 5 a second. That needs two numbers in Rule (capacity and rate), not one limit.
      • 
        
    • Per second and per day together: resolve a list of rules and deny if any denies. Decide whether a denied request still spends from the rules that allowed it (usually: check all, then spend only if all allow).
      • 
        
    • Response headers: Decision.remaining and retry_after become RateLimit-Remaining and Retry-After (rounded up to whole seconds, and at least 1: at an exact window edge the sliding counter can compute a wait of 0).
      • 
        
    • Memory with ten million clients: a token bucket is two floats per key; a sliding log is up to limit timestamps per key. Expire idle keys.
      • 
        
    • Shadow mode for a new rule: decide as usual but never deny, with a listener that logs what would have been blocked.
      • 
        
    • Testing: because time is injected, a test sets the fake clock to 9.999 and then 10.0 and checks the boundary exactly, with no sleeps and no flakiness.
      • 
        
    • Now across 50 servers: that's the high-level question: Redis sharded by key, one atomic script per check, and a decision on failing open or closed.
