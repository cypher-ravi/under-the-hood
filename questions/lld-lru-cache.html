Design an LRU Cache (classes)

A fixed-size key-value store that, when it runs out of room, throws away the entry nobody has touched for the longest time. The algorithm fits on a napkin: a hash map for finding keys, a doubly linked list for remembering the order they were used. The interview is about everything around it: which class owns the list, how a second eviction rule slots in without a rewrite, who hears about evictions, and what happens when eight threads call get at once.

The interview flow is adapted from Hello Interview's delivery framework for a 45-minute round. The breakdown, diagram and code on this page are our own.

1

Requirements

about 5 minutes

Pin down the contract before drawing a box. A cache spread across machines, persistence and cache-aside wiring belong to the high-level version of this question, not this one.

Functional: the cache should

  • get(key): return the value, or report a miss. A hit counts as a use of that key.
  • put(key, value): insert a new key or overwrite an existing one. An overwrite also counts as a use.
  • Hold at most capacity entries, fixed when the cache is built.
  • When a new key arrives and the cache is full, evict the least recently used entry first.
  • Stretch: a per-entry TTL, an eviction listener (log or metrics), and hit/miss counters.

Non-functional: the code should

  • Run get and put in O(1) time, average case, at any size.
  • Be thread-safe: many threads share one cache and its size and order never go wrong.
  • Be extensible: a second eviction rule (LFU, size-based) is a new class, not an edit to the cache.
  • Use O(capacity) memory: one map entry and one list node per key, nothing that grows with traffic.

Ask this early: does get count as a use? In an LRU cache it does, and that single answer decides most of the concurrency story later: a read changes shared state, so reads can't simply run in parallel.

2

Core entities and their responsibilities

about 3 minutes

On the whiteboard most people start with one LRUCache class holding a map and a list. That's fine for the first five minutes. The moment the interviewer says "now support LFU", the list has to move behind an interface, because LFU orders keys differently. Plan for that split from the start.

Cache

owns the key→node map and the capacity; runs get/put; asks the policy who to evict; tells listeners afterwards

Node

one entry: key, value, use count, prev and next links

DoublyLinkedList

sentinel head and tail; push to front, unlink, peek at the back, all O(1)

EvictionPolicy

interface: hears about adds, uses and removals; names the next victim

LRUPolicy / LFUPolicy

one list by recency, or one list per use count plus the lowest count

EvictionListener

interface: told the key and value of each eviction

CacheStats

hits, misses and evictions counters

ThreadSafeCache

wraps any cache, same get/put, one lock around each call

Class diagram

about 6 minutes

The cache owns its policy and its stats (composition, filled diamond): each cache gets its own instances, and they die with it. The policy owns the list, or one list per use count for LFU. The map only points at nodes (association), from zero up to capacity of them. Both the cache and the thread-safe wrapper implement the same small interface, which is what lets one wrap the other.

Reading it: "Cache → 0..capacity Node" is the map: a cache points at up to capacity nodes. "LFUPolicy ◆— 0..* DoublyLinkedList" is one list per use count that currently has keys. 4

Interfaces of the main classes

about 5 minutes

Signatures first. The policy interface is the interesting one: the cache tells it what happened (added, touched, removed) and asks one question (who goes next). It never tells the policy how to store anything.

interface KeyValueCache:
    get(key) -> value | None           # None = miss; a hit also marks the key as just used
    put(key, value) -> None            # insert or overwrite; may evict one entry first

class Cache(KeyValueCache):
    __init__(capacity: int, policy: EvictionPolicy)   # capacity >= 1
    subscribe(listener: EvictionListener) -> None
    stats: CacheStats                  # hits, misses, evictions

interface EvictionPolicy:             # owns whatever structure it needs to order keys
    added(node: Node) -> None
    touched(node: Node) -> None        # on every hit and every overwrite
    removed(node: Node) -> None
    victim() -> Node                   # asked only when the cache is full

interface EvictionListener:
    on_evict(key, value) -> None

class ThreadSafeCache(KeyValueCache):
    __init__(inner: KeyValueCache)     # same methods, each under one lock

class DoublyLinkedList:
    push_front(node), unlink(node), last() -> Node | None   # all O(1)

Why the policy gets Nodes, not keys: moving a key to the front of a list is O(1) only if you already hold its node. If the policy received a key it would have to search for it, which is O(n). The map hands the node over; that hand-off is the whole trick. And a caveat on None: if callers may store None as a value, a miss and a stored None look the same; use a private MISSING sentinel or a get(key, default) form instead.

5

Design patterns, and why

about 5 minutes

Three patterns earn a place here, each tied to a requirement. A fourth card is the shortcut you should mention and then put aside.

Strategy: the eviction policy

"Which key leaves" is the rule most likely to change: LRU today, LFU for a workload with a stable hot set, size-aware eviction for large values. Cache calls four methods on an EvictionPolicy and never looks inside, so a new rule is a new class passed to the constructor. The walkthrough below swaps them with one button.

Not worth it if the interviewer only ever wants LRU. Then one class with a map and a list is clearer; say you'd pull the interface out when a second rule shows up.

Observer: eviction listeners

Metrics, a debug log, or writing a dirty entry back to a database all want to hear "key X just left". The cache keeps a list of EvictionListeners and calls each one after an eviction, without knowing what they do.

Watch out: listeners run on the thread that called put, and in this design inside the lock. A slow listener stalls every caller; have it drop the event on a queue and return.

Decorator: the thread-safe wrapper

ThreadSafeCache implements the same interface as Cache, holds one, and adds a lock around each call. The core stays simple and testable without threads; callers that share a cache wrap it, single-threaded callers don't pay for the lock. The same shape fits a loading cache that calls a loader function on a miss.

Not worth it as a stack of five wrappers (logging, metrics, locking, TTL, loading). Each layer adds a call and hides the order of effects; two is plenty.

The shortcut: library ordered maps

Python's OrderedDict has move_to_end and popitem(last=False); Java's LinkedHashMap takes an access-order flag and a removeEldestEntry hook. Both are a hash map threaded through a linked list, which is exactly this design.

In the interview: name them to show you know, then build the list yourself. The question is testing whether you can, and LFU doesn't fit them anyway.

Code

about 7 minutes

Runnable Python 3, standard library only. In an interview, write DoublyLinkedList, LRUPolicy and Cache in full, then sketch LFU and the wrapper. The demo runs the walkthrough's default operations under both policies, then lets eight threads hammer one wrapped cache and checks that the counts still add up.

import random, threading
from abc import ABC, abstractmethod

class Node:
    __slots__ = ("key", "value", "freq", "prev", "next")
    def __init__(self, key=None, value=None):
        self.key, self.value, self.freq = key, value, 1
        self.prev = self.next = None

class DoublyLinkedList:             # sentinels: no None checks when linking
    def __init__(self):
        self.head, self.tail = Node("HEAD"), Node("TAIL")
        self.head.next, self.tail.prev = self.tail, self.head
        self.size = 0
    def push_front(self, node):     # just after head = most recent
        node.prev, node.next = self.head, self.head.next
        self.head.next.prev = node
        self.head.next = node
        self.size += 1
    def unlink(self, node):
        node.prev.next, node.next.prev = node.next, node.prev
        node.prev = node.next = None
        self.size -= 1
    def last(self):                 # just before tail = least recent
        return self.tail.prev if self.size else None
    def keys(self):
        node, out = self.head.next, []
        while node is not self.tail:
            out.append(node.key)
            node = node.next
        return out

class EvictionPolicy(ABC):          # Strategy: decides who leaves
    @abstractmethod
    def added(self, node): ...
    @abstractmethod
    def touched(self, node): ...
    @abstractmethod
    def removed(self, node): ...
    @abstractmethod
    def victim(self): ...

class LRUPolicy(EvictionPolicy):
    def __init__(self): self.order = DoublyLinkedList()
    def added(self, node): self.order.push_front(node)
    def touched(self, node):        # move to the front: O(1)
        self.order.unlink(node)
        self.order.push_front(node)
    def removed(self, node): self.order.unlink(node)
    def victim(self): return self.order.last()
    def describe(self): return "[" + " ".join(self.order.keys()) + "]"

class LFUPolicy(EvictionPolicy):    # fewest uses leaves; ties go to least recent
    def __init__(self): self.buckets, self.min_freq = {}, 0
    def _take(self, node):
        bucket = self.buckets[node.freq]
        bucket.unlink(node)
        if not bucket.size: del self.buckets[node.freq]
    def _put(self, node):
        self.buckets.setdefault(node.freq, DoublyLinkedList()).push_front(node)
    def added(self, node):
        node.freq, self.min_freq = 1, 1
        self._put(node)
    def touched(self, node):
        self._take(node)
        if self.min_freq == node.freq and node.freq not in self.buckets:
            self.min_freq += 1
        node.freq += 1
        self._put(node)
    def removed(self, node): self._take(node)
    def victim(self): return self.buckets[self.min_freq].last()
    def describe(self):
        return " ".join(f"f{f}[{' '.join(b.keys())}]" for f, b in sorted(self.buckets.items()))

class EvictionListener(ABC):        # Observer: told after a key is evicted
    @abstractmethod
    def on_evict(self, key, value): ...

class CacheStats:
    def __init__(self): self.hits = self.misses = self.evictions = 0
    def __str__(self):
        return f"hits={self.hits} misses={self.misses} evictions={self.evictions}"

class Cache:
    def __init__(self, capacity, policy):
        if capacity < 1: raise ValueError("capacity must be at least 1")
        self.capacity, self.policy = capacity, policy
        self.map, self.stats, self.listeners = {}, CacheStats(), []
    def subscribe(self, listener): self.listeners.append(listener)
    def get(self, key):
        node = self.map.get(key)
        if node is None:
            self.stats.misses += 1
            return None
        self.stats.hits += 1
        self.policy.touched(node)   # a read changes the order too
        return node.value
    def put(self, key, value):
        node = self.map.get(key)
        if node is not None:        # update in place, counts as a use
            node.value = value
            self.policy.touched(node)
            return
        if len(self.map) == self.capacity:
            self._evict()
        node = Node(key, value)
        self.map[key] = node
        self.policy.added(node)
    def _evict(self):
        old = self.policy.victim()
        self.policy.removed(old)
        del self.map[old.key]
        self.stats.evictions += 1
        for listener in self.listeners: listener.on_evict(old.key, old.value)
    def __len__(self): return len(self.map)

class ThreadSafeCache:              # Decorator: same get/put, one lock around each
    def __init__(self, inner):
        self.inner, self.lock = inner, threading.Lock()
    def get(self, key):
        with self.lock: return self.inner.get(key)   # get writes (reorders), so no read lock
    def put(self, key, value):
        with self.lock: self.inner.put(key, value)
    def __len__(self):
        with self.lock: return len(self.inner)

# ---------------- demo ----------------
class EvictionLog(EvictionListener):
    def __init__(self): self.last = None
    def on_evict(self, key, value): self.last = f"{key}={value}"

OPS = "put a 1, put b 2, put c 3, get a, get a, get b, get c, put d 4, get a, get b, put c 30, put e 5"

def run(policy):
    cache, log = Cache(3, policy), EvictionLog()
    cache.subscribe(log)
    print(f"== {type(policy).__name__}, capacity 3 ==")
    for op in OPS.split(", "):
        verb, key, *val = op.split()
        log.last = None
        if verb == "get":
            v = cache.get(key)
            result = "miss" if v is None else f"hit {v}"
        else:
            existed = key in cache.map
            cache.put(key, int(val[0]))
            result = "updated" if existed else "added"
        if log.last: result += f", evicted {log.last}"
        print(f"{op:<9} -> {result:<20} {policy.describe()}")
    print(cache.stats)

run(LRUPolicy())
run(LFUPolicy())

# eight threads hammer one shared cache
shared, gets = ThreadSafeCache(Cache(50, LRUPolicy())), [0] * 8
def worker(n):
    rng = random.Random(n)
    for _ in range(5000):
        key = f"k{rng.randrange(80)}"
        if rng.random() < 0.7:
            shared.get(key)
            gets[n] += 1
        else:
            shared.put(key, n)
threads = [threading.Thread(target=worker, args=(n,)) for n in range(8)]
for t in threads: t.start()
for t in threads: t.join()
inner = shared.inner
s = inner.stats
print(f"8 threads x 5000 ops: size {len(shared)}/{inner.capacity}, "
      f"list {inner.policy.order.size}, gets counted {s.hits + s.misses}/{sum(gets)}")

Why sentinels: with a dummy HEAD and TAIL that never leave, every real node always has a prev and a next. push_front and unlink become four pointer writes each, with no "is this the first node?" branches, which is where hand-written linked lists usually break.

8a

Deep dive: every read is a write

about 4 minutes

Without a lock, two threads that both hit at once each run unlink and push_front: eight pointer writes interleaved. One bad interleaving leaves a node pointing at a neighbour that no longer points back, and the list either loses a node (the map and list disagree on size) or grows a loop (the next eviction never ends).

Options, from simplest

  • One lock around get and put (what ThreadSafeCache does). Correct, easy to reason about, and each call holds it for well under a microsecond. Fine until many cores fight over it.
  • A read-write lock doesn't help. It lets readers run in parallel, but an LRU get moves a node, so it needs the write side. Every call ends up exclusive anyway.
  • Striped (segmented) cache. Split into N independent caches, pick one by hash(key) % N, each with its own lock and capacity / N. Contention drops about N times. The cost: eviction is only LRU within a segment, so a busy segment may evict while a quiet one has room.
  • Make hits cheaper. Record a hit in a small buffer and apply the reordering in batches under the lock (the approach taken by Java's Caffeine library), or drop the list: the CLOCK algorithm sets a "used" bit on a hit and only sweeps at eviction time, and Redis approximates LRU by sampling a few keys and evicting the oldest of the sample. All trade exact LRU order for reads that barely touch shared state.

Keep the lock short: no I/O, no listener work, no value serialisation inside it. Our listeners do run under the wrapper's lock, which is safe only because EvictionLog just stores a string. The demo's thread test checks the two invariants that a race would break first: the list length equals the map size, and every get issued was counted once as a hit or a miss.

Deep dive: what changes when requirements land

about 3 minutes

Count the existing lines each new requirement edits. Most of them should land as new classes.

New requirementAddEdit
LFU instead of LRUclass LFUPolicynothing
Metrics on evictionsa listenernothing
Load from a database on a missLoadingCache decoratornothing
Per-entry TTLexpires_at on Nodeget checks expiry; put takes ttl
Evict by total bytes, not counta weigher function"if full" becomes "while over budget"

TTL is the honest stress test. Pass now in (as the parking lot design passes time) and give each node an expires_at. get treats an expired node as a miss and removes it on the spot (lazy expiry). That alone can leave dead entries taking space until someone asks for them, so the eviction step should prefer an expired node over the policy's victim, and a busy cache may add a periodic sweep of the oldest entries. The policy interface doesn't change; Cache.get and _evict do. Saying where the edit lands, and why, is the point of the question.

Size-based eviction breaks an assumption hidden in if len(self.map) == self.capacity: that one insert needs at most one eviction. A 5 MB value may need ten small ones to leave, so the check becomes a loop on a running weight total, and a value bigger than the whole budget should be refused, not admitted.

8c

Deep dive: SOLID, and where to stop

about 2 minutes
Single responsibility

Cache handles lookup and capacity; the policy handles order; the list handles pointers; the wrapper handles locking. Stats live inside Cache because they're three integers bumped on the same lines; pulling them out would be ceremony.

Open/closed

LFU, listeners and the lock all arrived without editing Cache (see 8b). TTL does edit it, and that's an acceptable cost: it changes what a hit means.

Liskov

Any EvictionPolicy must name a victim that is in the cache whenever it is full. A policy that returned None there would let the cache grow past capacity: same signature, broken contract.

Interface segregation

Listeners see one method and no cache internals. Callers see get and put, never nodes.

Dependency inversion

Cache depends on EvictionPolicy, not LRUPolicy, and ThreadSafeCache depends on KeyValueCache, not Cache.

Where to stop

The policy and the list share Node directly, a deliberate leak: wrapping nodes in a policy-private type would cost an extra object per key for no new freedom. No interface for DoublyLinkedList either; nobody will ship a second one.

Worked example

Twelve operations, traced by hand

Capacity 3, the walkthrough's default input. Lists are written most recent first, so the next LRU victim is always the last key.

  1. put a, put b, put c

    Each is a miss in the map, so a new node is pushed right after HEAD. The list reads [c b a] and the cache is full.

  2. get a, get a, get b, get c

    Four hits. Each one unlinks the node and pushes it back to the front: [a c b], then [a c b] again (a was already first: unlink and re-push leave it in place), then [b a c], then [c b a]. Every key has been used since it arrived, but a least recently.

  3. put d 4: the policies disagree

    Full, so victim() is asked. LRU answers tail.prev = a, even though a was used three times. LFU looks at use counts (a: 3, b: 2, c: 2), takes the lowest bucket f2, and evicts its least recent member, b.

  4. get a, get b

    Under LRU: a misses, b hits. Under LFU: the opposite. Same input, same hit count so far, different keys kept.

  5. put c 30, put e 5

    c exists, so its value is overwritten in place and it counts as a use. Then e is new: LRU's list is [c b d], so d goes; LFU's lowest bucket is f1 = [d], so d goes there too. Final totals for both: hits=5 misses=1 evictions=2.

From first principles

What the problem really is

What

A bounded map with a rule for which entry to drop, where both the lookup and the drop must be constant time.

Why it's hard

Each structure alone fails. A hash map has no order; a list has order but O(n) lookup. Combining them means two structures that must always agree, which is exactly what concurrency threatens.

Key insight

Store list nodes as the map's values. Lookup finds the node; the node knows its neighbours; moving it is four pointer writes.

Same shape elsewhere

Page caches in an OS, a database buffer pool, connection pools that close the idlest connection, a browser's back-forward cache: bounded memory plus a rule for who gets dropped.

Follow-up questions to expect

  • delete(key): look up the node, policy.removed(node), drop it from the map. For LFU, check that min_freq still points at a bucket that exists, or recompute it at the next eviction.
  • Why doubly linked? Unlinking a node needs its predecessor. A singly linked list would have to walk from the head to find it: O(n).
  • Why not a heap of timestamps? Every hit would update a key's timestamp and fix the heap: O(log n) per get instead of O(1).
  • A one-off scan (a report that reads every key once) flushes the whole hot set out of an LRU cache. Answers: LFU, or a two-list scheme where new keys must be used twice before they enter the protected list.
  • peek(key): read without counting as a use, for monitoring. Add it to the interface and skip touched.
  • Memory per entry: a map slot plus a node with four references and a counter. For tiny values the bookkeeping can outweigh the data; say so.
  • Now make it distributed: that's the high-level question: consistent hashing to pick a node, replication for hot keys, and this class running on every node.
