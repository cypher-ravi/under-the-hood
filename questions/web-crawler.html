Design a Web Crawler

Start from a handful of seed URLs, download every page you can reach, pull out the links, and keep going until a large slice of the web is stored for indexing. Fetching one page is easy. The design question is everything around it: which URL to fetch next, how to avoid fetching the same thing twice, how to stay polite to sites that never asked to be crawled, and how to survive machines and servers failing halfway through a crawl that runs for days.

Step order and timings follow Hello Interview's delivery framework. The breakdown on this page is our own.

1

Requirements

about 5 minutes

Scope it to collecting pages. Ranking, building the search index and answering queries are separate systems that read what the crawler stores.

Functional: the crawler should

  • Start from a list of seed URLs and follow links outward.
  • Download each page and store its raw HTML for later processing.
  • Extract the links from each page and add the new ones to the work list.
  • Obey robots.txt and only fetch HTML pages (no images or video in scope).

Non-functional: the system should

  • Be polite: never send a site more requests than it allows, whatever the crawl's total speed.
  • Finish a crawl of billions of pages in days, not months (sized live in 5d).
  • Be fault tolerant: a crashed worker or a dead server must not lose progress or stall the crawl.
  • Not waste work: fetch each URL once and store each distinct page once.

First principles: a crawler is a breadth-first search over a graph you discover while walking it. The graph is enormous, full of cycles and duplicates, and every edge you follow costs a real request to somebody else's server. So the hard parts are the queue (order and politeness), the visited set (dedup), and keeping both durable.

3

System interface

about 5 minutes

A crawler has no end users calling it per request. Its interface is what goes in (seeds and settings) and what comes out (stored pages and the link graph), so describe that instead of a REST API.

// input
POST /crawls   { seeds: [url], max_depth, allowed_domains, user_agent }  → { crawl_id }
GET  /crawls/{id}            → { fetched, queued, failed, pages_per_sec }

// output, consumed by the indexer
blob store:  pages/{content_hash}.html.gz          // one object per distinct page
topic:       crawled-pages { url, fetched_at, status, content_hash, blob_key, out_links }

Why key blobs by content hash? Two URLs that serve the same bytes (mirrors, tracking parameters, http and https) then point at one object, and writing a page you already have becomes a cheap no-op. The event on the topic lets the indexer start without polling the store.

            Worked example

            One link, from discovery to storage

            Using the final design: a durable frontier partitioned by host, a fleet of fetchers, a robots and DNS cache, URL and content dedup, a retry queue with a dead-letter queue, and a blob store.

            1. Discovered

              A parser finds https://Shop.Example/item?id=7&utm_source=mail on a page it just processed. It normalizes it to https://shop.example/item?id=7 and asks the seen set. The Bloom filter says "not seen", so the URL is new for certain, and the parser records it in the URL table as queued.

            2. Queued by host

              The URL is published to the frontier topic keyed by shop.example, so every URL of that host lands on the same frontier partition. The frontier node that owns the partition appends it to the host's back queue. The scheduler's heap says the host may next be contacted at a time set by its crawl delay.

            3. Allowed?

              When the host's turn comes, a fetcher takes the URL. It checks the cached robots.txt rules for shop.example (refetched when the copy is a day old) and resolves the host from its DNS cache, so most fetches skip both round trips.

            4. Fetched, or retried

              The server answers 503. The fetcher puts the URL on the retry queue with a delay that doubles each attempt, plus jitter. The next attempt succeeds. Had it failed every attempt, it would have gone to the dead-letter queue for a person or a later sweep to inspect.

            5. Deduped and stored

              The fetcher hashes the HTML. The hash is new, so the page is compressed into the blob store under its hash and a crawled-pages event goes out. The parser consumes it, extracts links, and the cycle starts again for each of them. Only then does the frontier commit its offset, so a crash anywhere before this point means the URL is simply fetched again.

            From first principles

            What the problem really is

            What

            A breadth-first walk of a graph that is discovered while walking it, where visiting a node means a slow network request to a server you don't own.

            Why it's hard

            The graph is huge, cyclic and full of duplicates, and the edges are unevenly spread: a few hosts own a large share of all URLs, yet each host can only be visited slowly.

            Key insight

            Separate what to crawl from when to crawl it. A queue per host turns politeness into scheduling: the crawl stays fast by interleaving many hosts, never by hitting one host harder.

            Where it bends

            Memory for the visited set. A Bloom filter fits billions of URLs in a few gigabytes; its only error is skipping a URL it never saw, which loses a page rather than wasting a fetch.

            What must be durable

            The frontier and the URL states. Pages can be refetched; a lost queue can't be rebuilt without crawling again from the seeds.

            The story

            From one student's script to a standard

            In June 1993 Matthew Gray, a student at MIT, wrote the World Wide Web Wanderer in Perl. Its job was to measure how big the web had become, and later that year its results fed an index called Wandex. Early crawlers like it had no rules to follow. In February 1994 Martijn Koster, then at Nexor, proposed on the www-talk mailing list that sites publish a robots.txt file telling robots what to leave alone. Charles Stross has said a badly behaved crawler he wrote, which overloaded Koster's server, prompted the idea.

            Also in 1994, Brian Pinkerton at the University of Washington launched WebCrawler, the first search engine to index the full text of the pages it fetched. In 1998 Sergey Brin and Larry Page described Google's early crawler at the WWW7 conference: a URL server handing out work, about three crawlers each holding roughly 300 connections open, a DNS cache per crawler, and a peak of over 100 pages a second. They noted receiving emails from site owners surprised by how many pages had been read.

            In 1999 Allan Heydon and Marc Najork of Compaq's Systems Research Center published Mercator, a crawler built to be scalable and extensible. It assigned URLs to FIFO subqueues by host so that only one thread ever talked to a given server, used 64-bit fingerprints to test whether content had been seen, and averaged 112 documents a second in an 8-day crawl. Its frontier, refined into front queues for priority and back queues for politeness with a heap of next-contact times, is the design used in textbooks and on this page. The robots rules stayed an informal convention for 28 years: Google proposed them to the IETF in July 2019, and they became RFC 9309 in September 2022, with Koster among the authors. The RFC says a cached copy should not be used for more than a day, and that if robots.txt returns a server error, the crawler must assume it may not crawl at all. Crawl-delay, which many crawlers honor, is not part of it.

            Follow-up questions to expect

            • Recrawling for freshness: pages change at different rates. Store each URL's last change and schedule the next visit sooner for pages that changed, later for ones that didn't; the front queues then order by priority and due time.
            • Crawler traps: calendars and generated links can produce endless distinct URLs. Cap depth, cap URLs per host, and flag hosts whose new URLs keep producing near-duplicate content.
            • JavaScript-heavy pages: rendering needs a headless browser and is many times more expensive. Fetch the HTML first, and send only pages that look empty without scripts to a separate rendering pool.
            • Spreading the frontier: assign hosts to frontier nodes with consistent hashing, so adding a node moves only a small share of hosts and every host still has one owner enforcing its delay.
            • Priority: not all pages are worth the same. Score URLs (link popularity, site quality, freshness) into front queues and let the back-queue scheduler pull from high-priority front queues more often.
