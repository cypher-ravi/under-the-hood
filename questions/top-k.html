Design YouTube Top K

Show the K most-viewed videos for the last hour, the last day, the last month and all time, and keep the lists fresh. Each view is a tiny event, but there are billions a day, and the answer must come back in milliseconds. The design question is where the counting happens: inside a database at query time, or in a stream of events before anyone asks.

Step order and timings follow Hello Interview's delivery framework. The breakdown on this page is our own.

1

Requirements

about 5 minutes

Scope it to views. Likes, per-country lists and personalised trending are follow-ups that reuse the same pipeline with a different key.

Functional: users should be able to

  • Get the top K most-viewed videos (K up to about 1,000).
  • Choose the window: last hour, last day, last month, or all time.
  • See counts next to each video.

Non-functional: the system should

  • Answer a top-K request in tens of milliseconds.
  • Reflect a view in the lists within about a minute.
  • Ingest views at peak without dropping any (tens of billions a day).
  • Be close to exact for the published list; small errors deep in the tail are fine.

First principles: reads are tiny (one short list per window) and repeated by everyone, while writes are enormous and each one changes a single counter. So do the counting continuously as views arrive, and make reading a list a lookup, not a computation.

Why return computed_at? The list is a snapshot refreshed every few seconds, not a live query. Saying when it was computed is honest, and lets clients and CDNs cache it until the next refresh. In practice the view event usually rides on the player's existing analytics stream rather than its own request.

5a

Deep dive: sliding vs tumbling windows

about 5 minutes

Aggregators count into small time buckets, one counter per video per minute. A window is a sum of buckets. A tumbling window is a fixed block (9:00–10:00) that is published once it closes. A sliding window is "the last 60 minutes, now": each minute it adds the newest bucket and subtracts the one that fell off the back.     Deep dive: sharding the counts, and when a sketch beats a hash map

    about 5 minutes

    Partition the view log by hash(video_id), so every view of a video lands on the same aggregator. Each aggregator's top K is then exact for its own videos, and the global top K must be among the union of the shard lists. What is left to decide is how many shards, and whether each shard keeps an exact count per video or a fixed-size Count-Min Sketch.

      Try a real sketch

      A fixed stream: The sketch has depth rows of width counters. Each view adds 1 to one counter per row (chosen by that row's hash); a video's estimate is the smallest of its counters, so it can only be too high. A heap keeps the 10 videos with the highest estimates seen so far.

      Worked example

      A trailer drops at 9:00

      Using the final design: a view log partitioned by video, one aggregator per partition with minute buckets, a sketch and a heap, a merger, and a small Top-K store in front of the API.

      1. The view

        Someone in Lisbon watches the new trailer past the "counts as a view" threshold. The player sends {video_id: 8812} on its analytics stream. The view service checks the user hasn't just counted this video (a short-lived set of recent user and video pairs), then appends the event to the views topic and returns.

      2. Into a partition

        The producer picks the partition from hash(8812), so every view of the trailer, from anywhere, lands in the same partition and in order. The log keeps events for days, which makes the whole pipeline replayable.

      3. Counting

        The aggregator that owns that partition adds 1 to the trailer's 9:00 minute bucket and to its sketch counters, then checks the shard's heap: the estimate now beats the smallest entry, so the trailer replaces it. Every few seconds the aggregator commits its consumer offset along with a snapshot of its state, so a restart resumes where it left off.

      4. Merging

        Every 5 seconds each aggregator publishes its top K for the hour, day and month windows. The merger takes the union of those short lists, sorts by count, cuts to K, and writes one list per window to the Top-K store.

      5. Reading

        GET /views/top?window=hour reads one small list from the Top-K store, attaches titles and thumbnails, and is cached at the edge until the next refresh. By 9:01 the trailer is on the hourly list; it reaches the all-time list only if it keeps going for weeks.

      From first principles

      What the problem really is

      What

      A running count per video per time bucket, and a continuously maintained shortlist of the largest sums for a few windows.

      Why it's hard

      The write rate is huge and skewed (a viral video takes a big share of all views), the number of distinct videos is huge, and a window keeps moving, so old views must be subtracted as well as new ones added.

      Key insight

      Count where the events flow, not where they rest. Partitioning by video makes every shard's top K exact for its videos, so the global answer is a merge of a few short lists.

      Where it bends

      Memory per distinct video. A sketch trades exactness for a fixed size: counts may be too high by a bounded amount, never too low, and the bound shrinks as the sketch widens.

      What's derived

      Everything except the view log. Buckets, sketches, heaps and published lists can all be rebuilt by replaying the log from an offset.

      The story

      Counting what you can't afford to store

      Finding the most frequent items in a stream, with less memory than there are distinct items, is an old problem. In 1982 Jayadev Misra and David Gries published "Finding repeated elements", which keeps a small set of counters and decrements them all when a new item finds no free slot. Anything frequent enough is guaranteed to survive.

      In 2004 Graham Cormode and S. Muthukrishnan presented the Count-Min Sketch at the LATIN conference, with the journal version ("An improved data stream summary: the count-min sketch and its applications") following in the Journal of Algorithms in 2005. It is a small grid of counters with one hash function per row; an item's estimate is the minimum of its counters. The width sets the error and the depth sets how likely you are to exceed it. In 2005 Ahmed Metwally, Divyakant Agrawal and Amr El Abbadi published Space-Saving at ICDT, a counter-based method built specifically for frequent and top-k elements: when a new item arrives and the counters are full, it takes over the smallest counter.

      The architecture argument came later. Nathan Marz, who created Storm, described the "lambda architecture" in 2011: a batch layer recomputes exact answers from the full log, while a speed layer gives fast approximate ones, and queries combine the two. On 2 July 2014 Jay Kreps, one of Kafka's creators, published "Questioning the Lambda Architecture" on O'Reilly Radar. Keeping two code paths in sync was painful, he argued; instead, keep the log, run one streaming job, and to recompute, replay the log through a new version of that job. He suggested calling it the Kappa architecture. The final design on this page is that idea.

      Follow-up questions to expect

      • Late and out-of-order events: a phone reconnects and sends views from 10 minutes ago. Bucket by event time, keep recent buckets open for a grace period (a watermark), and correct the published list when a late bucket changes it.
      • Fake views: count only views that pass checks (watch time, rate per user and IP). Filtering happens before the log or in a first stream stage, and a slower batch audit can remove views later.
      • Exactly the right counts: sketch counts overestimate. Use the sketch to choose candidates, then count the few hundred candidates exactly, or reconcile with a nightly batch job over the log.
      • One mega-viral video: all its views hit one partition. Split that key into a few sub-keys (video + random 0..3) and add the parts back when merging.
      • Per country or category: make the key (region, video_id). Same pipeline, more lists, each still short.
