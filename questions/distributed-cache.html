Design a Distributed Cache

Build a fast key-value store that sits in front of a slower database: get, set and delete, with keys that expire. One machine with a hash map does this in a few lines. The design question is what happens when the data no longer fits in one machine's memory, the traffic no longer fits in one machine's CPU, machines die, and a few keys are far more popular than all the rest.

Step order and timings follow Hello Interview's delivery framework. The breakdown on this page is our own.

1

Requirements

about 5 minutes

Scope it to a cache, not a database. Losing an entry is allowed: the database behind it still has the truth, so a lost entry costs one slower read, not lost data.

Functional: clients should be able to

  • get(key): return the value, or say it is a miss.
  • set(key, value, ttl): store a value, optionally with a time to live.
  • delete(key): remove a key, usually because the database row changed.
  • Have keys disappear on their own when their TTL runs out, and have the least useful keys evicted when memory is full.

Non-functional: the system should

  • Hold about 1 TB of cached data, far more than one machine's memory.
  • Serve 1M+ operations a second at peak, mostly reads.
  • Answer in well under a millisecond typically and a few milliseconds at p99.
  • Stay available when a node dies: some extra misses are fine, an outage is not.
  • Accept eventual consistency: a value may be stale for a short, bounded time.

First principles: a cache is worth having only because memory is about a thousand times faster than a database round trip that touches disk, and because traffic is skewed: a small share of keys gets most of the reads. Every design choice below either keeps more of the useful keys in memory, or keeps each request on a single fast hop.

3

API

about 5 minutes
GET    /cache/{key}                  → 200 value | 404 miss
PUT    /cache/{key}?ttl=60   body    → 200
DELETE /cache/{key}                  → 200
POST   /cache/mget  { keys: [...] }   → { key: value | null }

// on the wire: a compact protocol over long-lived TCP connections
// get k  ·  set k ttl v  ·  delete k  ·  mget k1 k2 ...

Why not plain HTTP in practice? At a million operations a second with sub-millisecond targets, parsing headers and opening connections costs more than the lookup itself. Real caches use a small text or binary protocol over pooled TCP connections, and a batch call (mget) so a page that needs 50 keys pays for one round trip per node, not 50.

4

High-level design, then evolve it

10–15 minutes, plus deep dives

5a

Deep dive: eviction and expiry inside one node

about 3 minutes

Each node is a hash map plus a doubly linked list. The map finds an entry in O(1); the list keeps entries in order of last use, so the least recently used one is always at the tail. A hit unlinks the entry and puts it at the head; an insert into a full cache drops the tail. Both are a handful of pointer changes.

Expiry: lazy deletes plus active sampling

A TTL cannot be enforced by a timer per key: a node holds hundreds of millions of keys. Two cheap rules do the job together. Lazy: when a read finds an expired key, delete it and report a miss, so no client ever sees an expired value. Active: about 10 times a second, sample a few keys that have a TTL, delete the expired ones, and sample again straight away if more than a set share of the sample had expired. Redis has documented a loop like this: sample 20 keys, repeat if more than 25% had expired. Lazy alone is correct but leaks memory: keys nobody reads again stay forever.             Delete, don't update. With cache-aside, deleting the key after a DB write is safer than setting the new value: a delete repeated or reordered gives the same result, while two racing sets can leave the older value in the cache. The remaining race (a slow reader puts back a value it read just before the write) is what Facebook's leases close: a miss hands out a token, and a delete cancels it, so the late set is refused.
            
  
            

  
            
    Worked example
    
            One profile read, start to finish
            
    
            Using the final design: clients that route with a cached ring, shards with a primary and an async replica, a config service that handles failover, and a near-cache for hot keys.
            
    
              
      
            1. Route
              A web server needs user:42:profile. Its cache client hashes the key, finds the first ring point at or after the hash, and gets shard 17. The ring came from the config service at startup (version 812) and is refreshed when the service announces a change, so there is no proxy hop in the way.
              2. 
      
            2. Miss
              The client sends get to shard 17's primary. The key isn't there (it was evicted from the tail of the LRU list last night), so the node asks for and gets a lease token along with the miss.
              3. 
      
            3. Fill
              The web server reads the row from the database (8 ms), then sends set user:42:profile ttl=3600±10% token=…. The token is still valid, so the node stores the value at the head of its list and the primary streams the set to its replica a few milliseconds later.
              4. 
      
            4. Write
              The user edits their bio. The profile service updates the database row, then sends delete user:42:profile. The next read misses and loads the new bio. Had a slow reader been about to put the old value back, its lease would now be invalid and its set refused.
              5. 
      
            5. Failure
              Shard 17's primary loses power. The config service misses three heartbeats, promotes the replica, bumps the cluster map to version 813, and clients switch within a second. A delete that hadn't reached the replica yet leaves one stale value, which the TTL bounds at an hour; a stricter system would keep a short log of recent deletes and replay it during failover.

    From first principles
    
            What the problem really is
            
    
            
      
            What
            A hash map spread across machines, holding copies of data whose real home is a slower store, so that the copies may be dropped at any time.
            
      
            Why it's hard
            Memory is limited, so something must be thrown away; machines join and leave, so the map from key to machine must change without throwing everything away; and traffic is skewed, so equal shares of keys do not mean equal shares of load.
            
      
            Key insight
            Because the database holds the truth, the cache can choose availability and speed over consistency. Every loss turns into a miss, and every staleness is bounded by a TTL or fixed by a delete.
            
      
            Where it bends
            The database behind it. A cache that hides 99% of reads means the database is sized for 1%; lose the cache or let a hot key expire, and the database sees up to 100 times its normal load at once.
            
      
            What must stay small
            Every per-request step: one hash, one network hop, O(1) work on the node. Anything that grows with the number of keys (a global lock, a full scan for expired keys, a proxy hop per request) shows up at p99.
            
    
            
  
            

  
            
    The story
    
            A blog site's memory, then the web's
            
    
            In 2003, to take load off LiveJournal's databases, Brad Fitzpatrick, who had founded the site, wrote memcached: a daemon that turns the spare memory of many machines into one big hash table, with clients choosing the server for each key by hashing it. The first release came out on 22 May 2003. It was written in Perl at first and soon rewritten in C by Anatoly Vorobey, then working at LiveJournal. Its rules were simple and stayed: values live in memory only, the least recently used ones are thrown out when memory is full, and clients must treat any value as something that may vanish.
            
    
            In 2009 Salvatore Sanfilippo ("antirez"), working on a real-time web log analyzer called LLOOGG, needed something faster than his database for its workload. He built an in-memory store with a prototype in Tcl, rewrote it in C, and announced Redis ("Remote Dictionary Server") on Hacker News on 25 February 2009. Where memcached stores opaque blobs, Redis stores data structures (lists, sets, sorted sets, hashes) and can persist them and replicate them. VMware hired him in March 2010 to keep working on it.
            
    
            In 2013 Rajesh Nishtala and twelve colleagues at Facebook presented "Scaling Memcache at Facebook" at NSDI. Their memcache handled billions of requests a second and held trillions of items. The paper describes much of this page in production: memcache as a demand-filled look-aside cache; deleting instead of updating on writes, because deletes are idempotent; leases, which reject stale sets and hand out one token per key every 10 seconds to stop thundering herds; a small "gutter" pool, about 1% of servers, that takes over for failed ones; mcrouter, which routes requests; and mcsqueal daemons that pick deletes out of each database's committed transactions and broadcast them to every frontend cluster in the region.

            Follow-up questions to expect
            
      
              
        
            • Keys that don't exist: requests for missing rows always miss and always hit the database (cache penetration). Cache a short-lived "not found" marker, or check a Bloom filter of existing keys before going to the database.
              • 
        
            • Multiple regions: keep one cache cluster per region in front of that region's database replica, and drive invalidations from the database's change log rather than from app code (Facebook's mcsqueal does this within a region), so every cluster hears about every write.
              • 
        
            • Cold start: a new or restarted cluster has a 0% hit rate. Warm it by letting it read from an existing cluster on a miss before falling back to the database, or replay recent hot keys.
              • 
        
            • Big values: a 5 MB value blocks a node's network and evicts thousands of small keys. Cap the value size, compress, or split large objects into chunks under one prefix.
              • 
        
            • Memory fragmentation: after many sets of different sizes, free memory is scattered. memcached groups values into slab classes by size; Redis relies on its allocator and can defragment. Budget about 25–30% headroom.
              • 
        
            • Proxy or smart client: a client library saves a hop; a routing proxy (like mcrouter or Twemproxy) keeps clients simple and pools connections. Both read the same cluster map.
