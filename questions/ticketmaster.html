Design Ticketmaster

Let people find an event, pick a seat and pay for it. Browsing is an ordinary read-heavy website. The hard part is the moment a big show goes on sale: hundreds of thousands of people want the same few thousand seats in the same minute, and no seat may ever be sold twice.

Step order and timings follow Hello Interview's delivery framework. The breakdown on this page is our own.

1

Requirements

about 5 minutes

Pin down the three features that define the product, then find out which parts need to be correct and which parts need to be fast. For ticketing, the answer is different for different parts of the system.

Functional: users should be able to

  • Open an event and see its details and which seats are free.
  • Search for events by name, performer, city or date.
  • Pick seats, hold them while paying, and end up with a ticket.

Out of scope: resale between fans, dynamic pricing, organizers adding events, printing and scanning tickets.

Non-functional: the system should

  • Never sell one seat to two people. Booking needs strong consistency.
  • Stay up for browsing and search. A seat map that is a second out of date is fine.
  • Survive on-sale spikes: a single event can bring millions of visitors in minutes.
  • Return search results in well under a second.
  • Expect many more reads than bookings, roughly 100 to 1 on a normal day.

First principles: say out loud that the system has two halves with opposite needs. Viewing and search should pick availability, so they can be cached and replicated freely. Booking must pick consistency, so it goes through one source of truth. Most of the design follows from drawing that line.

2

Core entities

about 2 minutes

The key modelling choice: create one Ticket row per seat per event when the event is set up. Booking then means changing one row, not inserting a new one.

Event

event_id venue_id, performer_id name, date, description

Venue

venue_id location seat_map (sections, rows, seat numbers)

Performer

performer_id name, description

Ticket

ticket_id event_id, seat, price status: available | reserved | booked user_id?

Booking

booking_id user_id, ticket_ids[] total, status payment_id
3

API

about 5 minutes

One endpoint per requirement, except booking, which splits in two because paying takes minutes.

// Event page, including the seat map
GET /events/{event_id}
→ { event, venue, performer, tickets: [{ id, seat, price, status }] }

// Search
GET /events/search?q=swift&city=chicago&from=2026-10-01&to=2026-12-31

// Step 1: hold seats while the user pays
POST /bookings/reserve
{ "ticket_ids": ["t_c12", "t_c13"] }
→ 200 { "booking_id": "b_81", "held_until": "…+10 min" }
→ 409 if any seat is already taken

// Step 2: pay and confirm
PUT /bookings/{booking_id}/confirm
{ "payment_token": "tok_…" }       // from the payment provider's form
→ 200 { "booking_id": "b_81", "status": "booked" }

Why two calls? A card form, 3-D Secure checks and typing take minutes. If there were no hold, the seat could go while the buyer is paying. If the hold never ended, someone who closed the tab would keep the seat forever. The reserve call makes a hold that ends by itself, and the confirm call turns it into a sale.

The user comes from the session token, never from the request body.

4

High-level design, then evolve it

10–15 minutes, plus deep dives

Start with services that meet the three functional requirements, then add one component per non-functional requirement. Pick a stage and a request type to watch requests flow.

    Buyers arrive, hold a seat and head to checkout. Some pay. Some close the tab. Switch expiry off and watch abandoned holds lock seats that nobody is paying for.

      Deep dive: fast search

      about 4 minutes

      Searching events with a SQL LIKE '%swift%' can't use a normal index, so it scans every row. Put a search index next to the database instead.

      ApproachHow it finds "swift"Cost
      SQL LIKEReads every event nameO(rows) per query
      Database full-text indexBuilt-in inverted indexGood for small scale, shares load with booking
      ElasticsearchLooks up the word in an inverted index: word → event idsFast, fuzzy matching, geo and date filters
      • Keep it in sync with change data capture (CDC): the database's change log streams inserts and updates to the search index. The database stays the source of truth, and search may lag by a second, which the requirements allow.
      • Cache what everyone asks: on a big on-sale day, most searches are the same few queries. Cache results for a short time in Redis or at a CDN.
      • Keep seat status out of search. Search returns events. Live availability comes from the event page, which reads the source of truth plus holds.
      Worked example

      One seat, from 10:00:00 to a ticket

      1. Alice joins the waiting room

        At 9:58 she opens the event. The gateway sees the event is in on-sale mode and sends her to the waiting room. Her place is stored in a Redis sorted set, with the join time as the score. An open server-sent events (SSE) connection pushes her position to the page.

      2. She is let in

        A worker admits the next 5,000 people every minute. At 10:03 Alice gets a signed token that the booking service will accept for the next 15 minutes.

      3. She loads the seat map

        The event service reads ticket rows from the database (or a short-lived cache) and marks any seat with a live hold in Redis as taken. C12 shows as free.

      4. She reserves C12

        The booking service runs SET hold:evt42:C12 alice NX EX 600. NX means "only if the key doesn't exist", and Redis runs each command on its own, so exactly one caller can win. Alice gets OK.

      5. Bob tries the same seat

        Half a second later Bob's identical command returns nil. He gets a 409 and a message that the seat was just taken. His seat map updates over SSE a moment later.

      6. Alice pays

        The payment provider charges her card and calls the booking service's webhook with an idempotency key, so a retried webhook can't book twice.

      7. The sale is written

        In one transaction: UPDATE tickets SET status='booked', user_id='alice' WHERE id='C12' AND status='available', and insert the booking. One row changed, so the sale stands. Then DEL hold:evt42:C12.

      8. What if Alice had left?

        Nobody would call confirm. Ten minutes later Redis deletes the key by itself, C12 shows as free again, and the next person in line can take it. No cleanup job needed.

      From first principles

      What the problem really is

      What

      A catalogue that millions of people browse, attached to a tiny inventory that must be handed out exactly once.

      Why it's hard

      Contention. When demand is 20 times supply, many requests fight over the same row at the same moment, and checkout is slow compared with a click.

      Key insight

      Split "claim" from "pay". A claim is a quick atomic check that ends by itself. Payment can then take minutes without blocking anyone else.

      Safety net

      A hold is a lease, and leases can end at the wrong moment. The final write must still check the database, so a late or expired hold can't cause a double sale.

      Surge

      You can't make the stadium bigger. A queue can't create seats either. What it does is keep the system upright and tell people honestly how likely they are to get one.

      The story

      From box-office software to a Senate hearing

      Ticketmaster started in Phoenix, Arizona in 1976. Peter Gadwa, a programmer, and Albert Leffler, who knew event booking, wrote software that let box offices sell tickets by computer, and they licensed it to venues. Over the following decades it became the default ticket seller for large venues in the United States, and in 2010 it merged with the concert promoter Live Nation.

      The design problem on this page became front-page news on 15 November 2022, when the presale for Taylor Swift's Eras Tour opened. About 3.5 million people had registered through Ticketmaster's Verified Fan program, and roughly 1.5 million were sent codes. The company later said its systems took 3.5 billion requests that day, four times its previous peak, partly from bots and from people without codes. Queues stalled and checkouts failed, and the general public sale planned for later that week was cancelled.

      The fallout went beyond engineering. The Senate Judiciary Committee held a hearing on ticketing competition in January 2023, and in May 2024 the US Justice Department, joined by dozens of states, sued Live Nation and Ticketmaster for monopolizing the live-event market. For interviews, the lesson is narrower. An on-sale is a planned denial-of-service attack by your own customers, and it should be designed for from day one.

      Follow-up questions to expect

      • Several seats at once: hold all or none. Use one Redis MSETNX (or a Lua script) for keys on the same shard, and put the event id in a hash tag so all its seats live together.
      • The hold expires during payment: the conditional update at confirm catches it. If the seat is gone, refund the charge automatically and say so clearly.
      • Redis goes down: new holds fail, but no seat is sold twice, because the database still has the final say. Decide whether to pause sales or fall back to holds in the database.
      • Live seat map: push changes over SSE or WebSockets, batched every second or so, rather than letting clients poll the event page.
      • Bots and scalpers: verified registration before the sale, per-account and per-device rate limits, and a cap on tickets per buyer.
      • Payment retries: an idempotency key per booking, so a retried request or webhook never charges or books twice.
