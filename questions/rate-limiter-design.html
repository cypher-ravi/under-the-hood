Design a Rate Limiter

Build the service that stops any one client from sending more than its share of requests to an API, across dozens of gateway servers, while adding almost no latency and never becoming the reason the API is down. The algorithms (token bucket, sliding window) are the easy part. The hard parts are shared state, races between servers, and what to do when the limiter itself fails.

Step order and timings follow Hello Interview's delivery framework. The breakdown on this page is our own. For the algorithms themselves, see the Rate Limiters concept page.

1

Requirements

about 5 minutes

Pin down who is being limited, by what rule, and what happens when the limiter is unavailable. Those three answers shape the whole design.

Functional: the system should

  • Limit requests per client, identified by user ID, API key or IP address.
  • Support rules per endpoint, such as 100 requests a minute per API key, or 5 login attempts a minute per IP.
  • Reject extra requests with HTTP 429 and tell the client when to retry.
  • Let operators change rules without a deploy.

Non-functional: the system should

  • Add only a few milliseconds per request, because it sits in front of every request.
  • Enforce the limit accurately across every gateway server, not per server.
  • Keep the API up if the limiter fails. Most endpoints fail open; sensitive ones like login fail closed.
  • Handle about 1 million requests a second at peak from tens of millions of clients.

First principles: a rate limiter is a counter that many machines must update at once, on every request, in under a millisecond or two. Almost every decision below is about keeping that shared counter fast, correct and optional.

3

API

about 5 minutes

There are two interfaces: the internal check the gateway calls, and what the client sees when it's limited.

// Internal: called by the gateway on every request
check(client_key, endpoint) → { allowed: true, remaining: 3, reset_at: 1759213260 }

// What a limited client receives
HTTP/1.1 429 Too Many Requests
Retry-After: 12
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 12

Why tell the client? Well-behaved clients read Retry-After and back off instead of retrying immediately, which would add even more load at the worst moment. The remaining-quota headers let them slow down before they hit the wall.

High-level design, then evolve it

10–15 minutes, plus deep dives

One client with a limit of 5 requests per 10 seconds sends traffic through each stage. The counter under the diagram shows how many of its requests actually got through in the last 10 seconds. Anything above 5 means the limit leaked.

5a

Deep dive: two gateways, one counter

about 5 minutes

Two gateway servers handle requests from the same client at the same moment. The count in Redis is 4 and the limit is 5, so only one should get through. Step through three ways of updating the counter.

The rule: the check and the update must happen as one indivisible step on the server that owns the counter. INCR is atomic on its own. For a token bucket, which needs read, refill, compare and write, put all of it in one Lua script. Redis runs each script to completion before the next command, so no other request can sneak in between.

    Worked example

    One request through a token bucket in Redis

    Rule: 100 requests per 60 seconds per API key, as a token bucket holding up to 100 tokens that refills at 100 ÷ 60 ≈ 1.67 tokens a second.

    1. Request arrives at a gateway

      POST /v1/charges with API key key_abc. The gateway looks up the matching rule in its in-memory copy of the rules. There's no network call, since rules change rarely and are pushed to gateways.

    2. Pick the shard

      The counter key is rl:key_abc:/v1/charges. Hashing it picks one of the Redis shards, so the same client always lands on the same shard and its count lives in exactly one place.

    3. Run the script

      One EVALSHA call runs the Lua script atomically. It reads tokens = 0.4 and last_refill 1.8 seconds ago. It refills 1.8 × 1.67 = 3.0 tokens, making 3.4. That's at least 1, so it spends one (2.4 left), writes both values back with a 60-second expiry, and returns allowed.

    4. Forward and annotate

      The gateway forwards the request and adds RateLimit-Remaining: 2 to the response. The whole check cost one round trip to Redis, typically well under a millisecond inside a data center.

    5. Three more requests in the same instant

      They take the bucket to 1.4, then 0.4. The third finds 0.4 tokens, below 1, so the script returns rejected with a wait of (1 − 0.4) ÷ 1.67 ≈ 0.36 s. The client gets 429 with Retry-After: 1.

    From first principles

    What the problem really is

    What

    A shared counter per client and rule, checked and updated on every request, deciding allow or reject.

    Why it's hard

    Many servers see the same client, so the counter must be shared. Sharing adds a network hop and opens the door to races.

    Key insight

    Move the decision to where the data lives. One atomic script on the counter's own shard removes the race and costs a single round trip.

    Where it bends

    Across regions, one global counter is too slow. Give each region its own share of the limit, and accept being approximately right.

    Failure

    A limiter protects the API, so it must never be the cause of an outage. Decide fail open or closed per rule.

    The story

    How rate limiting grew up

    For years, a limited API had no standard way to say so. Services returned 503, 403, or custom errors. In April 2012, RFC 6585 added status code 429 Too Many Requests, and a Retry-After header to say when to come back.

    In March 2017, Stripe engineer Paul Tarjan described how Stripe limits its API. It uses token buckets in Redis, and not one limiter but four: a per-user request rate limit, a limit on concurrent requests, and two load shedders that drop low-priority traffic when the fleet is under strain. The post also urged making limiters fail open, putting them behind feature flags as a kill switch, and dark-launching new rules to see what they would block before turning them on.

    In 2021, GitHub described moving its API rate limiter from Memcached to sharded, replicated Redis with Lua scripts for atomic updates. The move was forced partly because Memcached's cache eviction could silently drop live counters.

    1. 2012

      RFC 6585 defines HTTP 429 Too Many Requests.

    2. 2017

      Stripe publishes "Scaling your API with rate limiters": token buckets in Redis, four limiter types, fail open.

    3. 2021

      GitHub moves its API rate limiter to sharded Redis with Lua scripts.

    4. Today

      API gateways such as AWS API Gateway, Envoy and Nginx ship token-bucket or window limiters out of the box.

    Follow-up questions to expect

    • Limit by IP? Many users can share one IP behind a company NAT or mobile carrier. Prefer API keys or user IDs, and keep IP limits generous.
    • Several regions: split each limit across regions, or sync counts asynchronously and accept a brief overshoot.
    • Hot keys: one huge client can overload one shard. Keep a short-lived local token allowance in the gateway and refill it from Redis in batches.
    • Client behaviour: retry with exponential backoff and jitter, honouring Retry-After, so rejected clients don't retry in lockstep.
    • Rolling out a new rule: run it in shadow mode first and log what it would block.
