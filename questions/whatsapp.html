Design WhatsApp

Build a chat service where a message reaches the other person's phone in well under a second if they're online, waits safely if they're not, and shows one tick when the server has it and two when the recipient does. The hard parts are holding hundreds of millions of open connections, finding which server a user is connected to, and never losing or doubling a message when networks drop packets.

Step order and timings follow Hello Interview's delivery framework. The breakdown on this page is our own.

1

Requirements

about 5 minutes

Scope it to messaging. Calls, stories and payments are separate systems; say so and move on.

Functional: users should be able to

  • Send a text message to one person or a group of up to about 100 people.
  • Receive messages in real time while the app is open.
  • Receive messages sent while they were offline, as soon as they reconnect.
  • See whether a message was sent (✓), delivered (✓✓) and read.
  • Send photos and videos.

Non-functional: the system should

  • Deliver to an online recipient in under about 500 ms.
  • Never lose a message once the sender sees ✓, and never show it twice.
  • Keep messages in order within a conversation.
  • Handle billions of users and hundreds of millions connected at once.
  • Store messages only until they're delivered, not forever.

First principles: chat is a mailbox problem with a twist. The server must push to the recipient the instant a message arrives, which means it needs a live connection to every online phone and must know which machine holds each one.

3

API

about 5 minutes

Messages travel over one long-lived WebSocket per device, in both directions. Plain HTTP is only for things that aren't real time, like uploading media.

// client → server, over the socket
send     { message_id: "c7f3…", chat_id, body }      → ack { message_id }
delivered { message_ids: [...] }                       // recipient's phone has them
read      { chat_id, up_to: message_id }

// server → client, over the socket
message   { message_id, chat_id, sender_id, body, sent_at }
receipt   { message_id, status: "delivered" | "read" }

// HTTP, for media
POST /media/upload-url → { upload_url, media_url }    // presigned, straight to blob storage

Why does the client pick the message ID? If the ack is lost, the phone resends the same message with the same ID. The server sees an ID it already has and just acks again, so the recipient never gets a duplicate. See deep dive 5a.

High-level design, then evolve it

10–15 minutes, plus deep dives

5a

Deep dive: exactly one copy, even when packets drop

about 5 minutes

Networks can lose any message, including the server's ack. The fix has two halves: the sender retries until it hears an ack (at least once), and the server and recipient ignore IDs they've already seen (so retries don't become duplicates). Step through four scenarios.

The rule: "exactly once" over an unreliable network is really "at least once delivery, plus deduplication by a stable ID". The ID must be chosen by the sender, before the first attempt, so every retry carries the same one.

    Worked example

    "Running late" to Bob, who is in a tunnel

    Using the final design: Alice is connected to chat server 1, and Bob's phone has no signal.

    1. Alice taps send

      Her phone creates message_id = c7f3, saves the message in a local outbox, shows it with a clock icon, and sends it over her open socket to server 1.

    2. Server 1 makes it durable, then acks

      It checks that c7f3 is new for this chat, writes the message and an inbox entry for Bob's phone to the replicated message store, and only then sends ack c7f3. Alice now sees ✓. From this point the message can't be lost, even if server 1 crashes.

    3. Find Bob

      Server 1 looks up Bob in the connection registry. No entry: he isn't connected anywhere. Server 1 asks the push service (APNs or FCM) to send a notification to his phone. The message stays in the inbox.

    4. Bob leaves the tunnel

      His phone reconnects, lands on chat server 2, and registers bob → server 2. Server 2 reads Bob's inbox and pushes c7f3 down the new socket.

    5. Two ticks

      Bob's phone shows the message and replies delivered [c7f3]. Server 2 deletes the inbox entry and sends a receipt toward Alice through the same lookup. Alice sees ✓✓. When Bob opens the chat, a read receipt turns them blue.

    From first principles

    What the problem really is

    What

    A store-and-forward mailbox per device, plus a live connection that lets the server push the moment mail arrives.

    Why it's hard

    Phones disconnect constantly, every hop can drop packets, and the recipient's connection lives on one of thousands of servers.

    Key insight

    Ack only after the message is durable, and make every step idempotent by message ID. Then retrying is always safe.

    Where it bends

    Big groups multiply every message by the member count. Past a few hundred members, fan out on read, like a channel, instead of copying into every inbox.

    Ordering

    Order per chat, not globally. A sequence number per chat from the server that owns it is enough.

    The story

    Two million sockets per box

    WhatsApp was started in 2009 by Jan Koum and Brian Acton, two former Yahoo engineers. Its server began as ejabberd, an open-source chat server written in Erlang, a language built at Ericsson for telephone switches that must handle huge numbers of lightweight concurrent tasks and keep running when parts fail. The team ran it on FreeBSD and rewrote much of it over time.

    On 6 January 2012 the company blogged that it had passed 2 million TCP connections on a single server, after tuning both FreeBSD and the Erlang runtime. That density is why the company stayed famously small. When Facebook agreed to buy WhatsApp for $19 billion in 2014, it had about 450 million monthly users and only around 32 engineers, and was handling tens of billions of messages a day.

    Messages were kept on the server only until delivered. In April 2016 WhatsApp finished rolling out end-to-end encryption using the Signal Protocol for over a billion users, so the servers relay messages they can't read. The design on this page works the same way: the server stores and forwards ciphertext.

    Follow-up questions to expect

    • Several devices per user: keep one inbox per device, not per user, and fan each message out to all of a user's devices.
    • Large groups: fan out on write for small groups. For very large ones, store the message once and have members pull it.
    • Online and last-seen: heartbeat on the socket, and send presence only to people who currently have the chat open, or it becomes most of your traffic.
    • A chat server dies: its phones reconnect to another server and re-register. Nothing is lost, because nothing was acked before it was stored.
    • Spam: rate limit messages per account and per new contact.
