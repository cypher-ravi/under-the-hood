Design Google Docs

Several people type into the same document at the same moment, each sees the others' changes within a fraction of a second, nobody's typing ever waits for the network, and every copy ends up with exactly the same text. Saving a file is easy. The design question is how edits made at the same time on different machines get merged into one agreed order, and how to run that for millions of open documents without losing a keystroke.

Step order and timings follow Hello Interview's delivery framework. The breakdown on this page is our own.

1

Requirements

about 5 minutes

Scope it to the text editor: one rich-text document edited by many people. Spreadsheets, slides, search across documents and the file browser are separate systems.

Functional: users should be able to

  • Create a document and share it with others as editor or viewer.
  • Edit it together in real time: everyone sees everyone's changes, in the same final order.
  • See who else is in the document and where their cursors are.
  • Keep typing while offline and have the edits merged on reconnect.
  • Browse the document's history and restore an older version.

Non-functional: the system should

  • Show a local keystroke instantly and a remote one within about 100–200 ms.
  • Converge: once edits stop, every copy holds identical text.
  • Never lose an edit the server has acknowledged.
  • Scale to millions of documents open at once, with up to about 100 people in one document.
  • Stay available: a crashed server costs a reconnect, not data.

First principles: "real time" here does not mean "fast database writes". It means every replica applies the same set of edits, and edits made at the same moment on different copies must be adjusted so they mean what their authors intended. The whole design is about agreeing on an order for those edits, cheaply, for each document.

2

Core entities

about 2 minutes

Document

doc_id, title, owner_id created_at, latest_rev latest_snapshot_rev

Operation

doc_id, rev (its place in the order) author_id, base_rev insert(pos, text) | delete(pos, len) | format(range, style)

Snapshot

doc_id, rev full content at that rev (blob, rebuilt from ops)

Permission

doc_id, user_id role: owner | editor | viewer

Session / presence

user_id, doc_id, color cursor (rev, pos), selection last_seen (memory only)

The operation is the heart of it. The document text is never the source of truth on its own: it is whatever you get by applying operations 1 to N, in order, to an empty page. A snapshot is a saved shortcut to that result.

3

API

about 5 minutes

Ordinary requests for documents and sharing; one long-lived WebSocket per open document for the edits themselves.

POST   /docs  { title }                      → { doc_id }
GET    /docs/{id}                         → { snapshot, rev, ops_since_snapshot }
POST   /docs/{id}/share { user, role }    → 200
GET    /docs/{id}/revisions?before=rev    → [ { rev, author, time } ]

// WebSocket  wss://.../docs/{id}/live   (routed to the doc's owner server)
// client → server
{ type: "op",     base_rev: 1203, op: { insert: "red ", at: 4 } }
{ type: "cursor", rev: 1203, pos: 17, sel_end: 17 }
// server → client
{ type: "ack",    rev: 1204 }                        // your op is now #1204
{ type: "op",     rev: 1205, author: "ben", op: {...} } // someone else's
{ type: "presence", user: "ben", pos: 9, color: "#..." }

Why carry base_rev? It says which version of the document the author was looking at when they typed. The server compares it with its own latest revision: if anything was committed in between, the operation is adjusted against those changes before it is stored. Without it the server could not tell a fresh edit from a stale one.

4

High-level design, then evolve it

10–15 minutes, plus deep dives

5a

Deep dive: OT or CRDT, and why one server per document

about 5 minutes

Two people edit the same text at the same moment. Each applies their own change first and the other's second. If the second change is applied with its original position, the copies disagree. Operational transformation (OT) shifts the incoming change past the one already applied. Try it.

    Why a single owner per document either way: with OT the server is the ordering point, so all editors of a document must talk to the same process. With a CRDT the merge would work without one, but a server per document is still the simplest place to persist ops, check permissions and fan out changes. Interviewers accept either; pick OT with a central server and say why.

    5b

    Deep dive: millions of WebSockets, one owner per document

    about 4 minutes

    Each open editor holds one WebSocket, and every editor of a document must reach the server that owns it. Size the fleet by connections, then route by document id on a consistent-hash ring.

      Deep dive: an op log, snapshots and compaction
      about 4 minutes
      
    
      The op log is append-only and partitioned by document id, so it writes fast and keeps each document's order. Opening a document should not replay its whole life, so a worker periodically folds the log into a snapshot. The snapshot interval trades storage writes against how long an open takes.

        5d
        Deep dive: presence and cursors
        about 3 minutes
        
    
        Cursors move far more often than text changes, and an old cursor position is worthless. So presence is kept apart from edits: held in the doc server's memory, never written to the op log, sent at most every few tens of milliseconds, and dropped when a heartbeat stops.
        
    
        
      
      
      
      
    
        
    
        
    
          
  
          

  
          
    
          5e
          Deep dive: offline editing and reconnecting
          about 4 minutes
          
    
          Offline is just very high latency. The client keeps applying its own ops locally and queues them (in IndexedDB, so a closed tab doesn't lose them). On reconnect it says "my base is revision R": the server sends every op since R, and the client's queue is transformed against them before being sent. The cost grows with both sides' work.

    Worked example
    
              One word typed, start to finish
              
    
              Using the final design: doc servers on a consistent-hash ring, an op log partitioned by document, snapshots every few hundred ops, presence in memory.
              
    
                
      
              1. Open
                Ana opens doc:42. The API checks her permission in the metadata database, then returns the latest snapshot (revision 1,000) and the 203 ops after it from the op log. Her browser applies them and is at revision 1,203. It opens a WebSocket; the gateway hashes doc:42 onto the ring and connects her to doc server 7, which already holds the document in memory because Ben has it open.
                2. 
      
              2. Type
                Ana types "red " at position 4. Her screen shows it at once. The browser sends {op: insert "red " at 4, base_rev: 1203}. At the same moment Ben deletes the character at position 9, also based on 1,203; his op reaches the server first and becomes revision 1,204.
                3. 
      
              3. Transform
                Ana's op arrives with base 1,203, but the server is at 1,204. It transforms her insert against Ben's delete: position 4 comes before 9, so it stays at 4. It appends the op to the log as revision 1,205, waits for the log to confirm the write, then acks Ana ("you are 1,205") and sends the op to Ben.
                4. 
      
              4. Converge
                Meanwhile Ana received Ben's delete. Her own insert was still unacknowledged, so her browser transforms Ben's delete against it: position 9 is after her 4-character insert, so it becomes a delete at 13. Ben's browser applies Ana's insert at 4 unchanged. Both now read the same text at revision 1,205.
                5. 
      
              5. Persist and fail over
                Ops 1,001 to 1,500 accumulate; at 1,500 the snapshot worker writes a new snapshot. If server 7 dies, the gateway reconnects Ana and Ben to the next server on the ring, which loads the snapshot and replays the ops after it. Every acknowledged op is in the log, so nothing is lost; unacknowledged ops are simply resent from each browser's queue.

    From first principles
    
              What the problem really is
              
    
              
      
              What
              A replicated string that many people change at once, where every copy must end the same and every change must keep the meaning its author saw.
              
      
              Why it's hard
              Positions are relative. "Insert at 4" means something different once someone else has inserted or deleted before position 4. Locking would fix it and make typing wait for the network, which nobody accepts.
              
      
              Key insight
              Apply locally first, agree on order later. A single owner per document assigns the order; the transform function rewrites each late op so it means the same thing in the new context.
              
      
              Where it bends
              The one document with many editors: fan-out grows with the square of its editors, which is why products cap simultaneous editors per document.
              
      
              What must be durable
              The ordered op log. The text, the snapshots and the history are all things you can rebuild from it; presence is not worth keeping at all.
              
    
              
  
              

  
              
    The story
    
              From a startup's web word processor to a protocol for everyone
              
    
              The idea that concurrent edits can be repaired rather than locked out is older than the web. In 1989 Clarence Ellis and Simon Gibbs described operational transformation for GROVE, a group outline editor. In 1995 David Nichols and colleagues at Xerox PARC published the Jupiter collaboration system, which simplified the problem by putting a central server between every pair of clients: each client only ever has to reconcile with the server, never with other clients directly. That shape is the one this page uses.
              
    
              Writely, a browser word processor built at the startup Upstartle by Sam Schillace, Steve Newman and Claudia Carpenter, launched in August 2005. Google announced it had acquired Upstartle on 9 March 2006, and the product became Google's online documents later that year. In November 2008 Etherpad, built by David Greenspan, Aaron Iba and J.D. Zamfirescu, showed what keystroke-by-keystroke collaboration could feel like; Google acquired it in December 2009 to fold its team into Google Wave and released Etherpad's code as open source that month. Wave itself, unveiled in May 2009 and built around OT, was stopped as a standalone product in August 2010.
              
    
              In April 2010 Google shipped a rebuilt document editor. In September 2010 its engineer John Day-Richter explained on the Google Docs blog how it collaborates: each change is sent as a small operation, the client keeps at most one change in flight and buffers the rest, and the server transforms late changes against its revision log before storing them. In 2011 Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski formally defined conflict-free replicated data types, the main alternative, which libraries like Yjs and Automerge later brought to editors that can merge without a central server.

              Follow-up questions to expect
              
      
                
        
              • Rich text: formatting is just more op types (format(range, bold)), each needing transform rules against inserts and deletes. Tables and images make the transform matrix grow quickly; that is the real cost of OT.
                • 
        
              • Comments and suggestions: a comment is anchored to a range, and that range is transformed through every later op, exactly like a cursor. A suggestion is a set of ops held aside until someone accepts it.
                • 
        
              • Permissions changing mid-session: the doc server checks the role on connect and subscribes to permission changes for its open documents, closing a socket the moment someone is downgraded to viewer.
                • 
        
              • Hundreds of viewers: viewers don't send ops. Serve them from read-only replicas fed by the op log, or publish the document as a page, so they never load the owner server.
                • 
        
              • Abuse and runaway clients: rate-limit ops per connection and cap op size, so one buggy script can't flood a document's fan-out.
                • 
        
              • Search across documents: a separate indexer consumes the op log (or snapshots) and updates a search index asynchronously.
