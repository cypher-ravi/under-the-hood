Design a URL Shortener

Turn a long link into a short one like sho.rt/15FTGn, and send anyone who opens it to the original page. The core is a key-value lookup. The interesting parts are generating short codes that never collide and serving far more reads than writes with low latency.

Step order and timings follow Hello Interview's delivery framework. The breakdown on this page is our own.

1

Requirements

about 5 minutes

Ask questions until you can write both lists. Keep the functional list to the three or so features that define the product, and give the non-functional list real numbers.

Functional: users should be able to

  • Submit a long URL and get back a short one.
  • Optionally choose a custom alias (sho.rt/my-talk) and an expiry date.
  • Open a short URL and be redirected to the original.

Out of scope: accounts, click analytics dashboards, editing links.

Non-functional: the system should

  • Guarantee every short code maps to exactly one URL.
  • Redirect fast: aim for under 100 ms, since a redirect sits in front of every page load.
  • Favour availability over consistency for redirects. A new link taking a second to work everywhere is fine. Redirects failing is not.
  • Handle about 10 million new links a day and roughly 100 redirects for every link created.

First principles: the ratio of reads to writes is the most important number here. At 100 to 1, every design choice should make the read path cheap, even if it makes writes a little slower.

2

Core entities

about 2 minutes

Name the nouns before drawing boxes. You'll refine their fields during the design.

Link

short_code (primary key) long_url created_at expires_at? creator_id?

User

user_id (only needed for custom aliases and quotas)

Short code

7 characters of [0-9a-zA-Z] the key everything is looked up by
3

API

about 5 minutes

One endpoint per functional requirement is a good default.

// Create a short link
POST /urls
{ "long_url": "https://example.com/blog/2026/09/a-very-long-post-title",
  "custom_alias": "my-talk",      // optional
  "expires_at": "2027-01-01" }    // optional
→ 201 { "short_url": "https://sho.rt/15FTGn" }

// Follow a short link
GET /{short_code}
→ 302 Found
  Location: https://example.com/blog/2026/09/a-very-long-post-title

302 or 301? A 301 (moved permanently) lets browsers cache the redirect and never ask you again. That saves load, but you lose the ability to count clicks, change the target, or expire the link. A 302 (found) sends every click through your servers. Most shorteners choose 302 and absorb the load with caching.

4

High-level design, then evolve it

10–15 minutes, plus deep dives

Start with the simplest design that meets the functional requirements, then add one component at a time, each justified by a non-functional requirement. Pick a stage and a request type to watch requests flow.

5a

Deep dive: making short codes unique

about 5 minutes

This is where most of the interview is won. There are three common ways to produce a code. Try each one.

How long should the code be?

Random and hash codes collide by the birthday effect long before the space is full. Collisions become likely once you have stored about √N codes, where N is the number of possible codes. That is why random and hash codes need a uniqueness check on every insert.

5b

Deep dive: fast redirects at scale

about 5 minutes

Do the math only where it changes a decision. Move the sliders and see which components the numbers call for.

    Worked example

    One link, created and then clicked

    1. Client sends POST /urls

      The body contains the long URL. The load balancer forwards it to a write server.

    2. Write server gets the next ID

      It doesn't call Redis on every request. It reserved the range 1,000,000,001 to 1,000,001,000 earlier with one INCRBY 1000, and its next unused number is 1,000,000,007.

    3. Encode in base62

      Divide by 62 repeatedly and read the remainders from last to first:

      Number÷ 62RemainderCharacter
      1,000,000,00716,129,03223n
      16,129,032260,14542G
      260,1454,19555T
      4,1956741F
      67155
      1011

      Reading upward gives 15FTGn. The alphabet is 0-9, then a-z, then A-Z, so 23 is n and 42 is G.

    4. Store and respond

      Insert (15FTGn → long URL) into the database. The code came from a counter, so there's no collision check. Return https://sho.rt/15FTGn.

    5. Someone clicks it

      GET /15FTGn reaches a read server. It checks Redis first. On the first click that misses, so it reads a database replica (a few milliseconds), stores the result in Redis, and replies 302 Location: ….

    6. Every later click

      The next click hits Redis in about a millisecond. With roughly 20% of links getting most of the traffic, a cache sized for the hot set serves the large majority of redirects.

    From first principles

    What the problem really is

    What

    A giant, read-mostly dictionary from short code to long URL, exposed over HTTP.

    Why it's hard

    Codes must be short and unique across billions of links, created by many servers at once, and looked up in milliseconds.

    Key insight

    Uniqueness is easiest if you never guess. A counter gives every link a distinct number, and base62 just writes that number compactly.

    Where it bends

    A single counter is a bottleneck and makes codes guessable. Hand out ranges to servers, and shuffle the bits if predictability matters.

    Read path

    100 reads per write means the cache is not an optimisation. It is the design.

    The story

    Why short links exist

    In January 2002, Kevin Gilbertson, a web developer in Minnesota, was tired of long web addresses breaking across lines in newsgroup posts. He built TinyURL to turn them into something short enough to paste. It became the first widely used shortener and inspired over a hundred copies.

    Short links took off with Twitter's 140-character limit. Bitly became one of the dominant services, and in November 2009 alone its links were opened about 2.1 billion times. Twitter eventually built its own shortener, t.co, so it could check links for malware and keep click data in-house.

    The history also teaches a design lesson about durability. Google launched goo.gl in 2009, then in 2024 announced that its links would stop working in 2025, and later narrowed that to links with no recent traffic. Millions of links in papers and old posts depended on one company's decision. A shortener's real promise is that a link keeps working for years.

    1. 2002

      TinyURL launches to make newsgroup links shorter.

    2. 2008

      Bitly launches and grows with Twitter.

    3. 2009

      Google launches goo.gl. Bitly links are opened about 2.1 billion times in November.

    4. 2010s

      Twitter wraps every posted link in its own t.co shortener.

    5. 2024

      Google announces the end of goo.gl links, a reminder that short links are only as durable as the service behind them.

    Follow-up questions to expect

    • Custom aliases: check availability with a unique constraint. A Bloom filter in front can answer "definitely free" without a database read.
    • Expiry: store expires_at, check it on read, and clean up with a background job or a database TTL.
    • Abuse: rate limit link creation per user or IP, and scan targets for malware.
    • Analytics: keep 302, and publish click events to a queue such as Kafka rather than writing a counter on the redirect path.
    • Hot links: a viral link can overload one cache node. Replicate hot keys or serve them from a CDN edge.
