Top K and Two Heaps

Many problems never need everything in sorted order. They need the biggest few, the smallest of several candidates, or the value in the middle, and they need it again after every new number arrives. A heap gives you the smallest (or largest) item in O(1) and lets you add or remove one in O(log n). Keep a small heap of size k, or two heaps that split the data in half, and a full sort turns into a cheap running summary.

Pattern-first structure inspired by Codeintuition's curriculum. Problems, explanations and visualizations on this page are our own.

The idea, from first principles

A heap is a tree packed into an array

A binary min-heap is a binary tree with two rules. Its shape is complete: every level is full except maybe the last, which fills from the left. And it is ordered: every parent is no larger than its children. Nothing is said about left versus right, so a heap is far from sorted, but the smallest item is always at the root.

Because the shape has no gaps, the tree fits in a plain array, level by level. The node at index i has children at 2i + 1 and 2i + 2, and its parent is at (i − 1) // 2. No pointers needed.

Two repairs keep the order rule true. Push: put the new item in the next free slot (the end of the array), then sift it up, swapping with its parent while it is smaller. Pop: take the root, move the last item into the root's place, then sift it down, swapping with its smaller child while that child is smaller. A complete tree with n nodes has about log₂ n levels, and each repair walks one path, so both cost O(log n). Peeking at the root is O(1).

A max-heap is the same with the comparison flipped. Python's heapq only gives a min-heap, so the usual trick is to store -x.

Recognizing the pattern

Signals in the problem statement

  • The words k largest, k smallest, kth, top k, k closest, k most frequent. Keep a heap of size k, with the comparison set so that the item you would throw away first sits at the root.
  • You must answer after every new item (a stream), so sorting once at the end is not an option, and sorting again each time is too slow.
  • You repeatedly need the smallest of several candidates that keep changing: the fronts of k sorted lists, the earliest finishing meeting, the cheapest next node in Dijkstra's algorithm.
  • The answer lives in the middle (median, balance point), or you need the largest of one group and the smallest of another at the same time. That is two heaps.
  • k is much smaller than n. A size-k heap costs O(n log k), which beats sorting's O(n log n) and uses only O(k) memory.

Opposite heap for "largest": to keep the k largest, use a min-heap. It sounds backwards, but the root must be the item you would drop next, and among the k largest that is the smallest one. For the k smallest, use a max-heap.

The same idea scales up to a whole system. When the stream is too big for one machine to count exactly, see the design question Top K at scale, and the count-min sketch that estimates counts in a fixed amount of memory.

Template

Two skeletons: a bounded heap and a pair of heaps

Keep the k best (here: largest)

import heapq
heap = []                      # min-heap, size ≤ k
for item in stream:
    heapq.heappush(heap, key(item))
    if len(heap) > k:
        heapq.heappop(heap)    # evict the weakest
# heap holds the k best; heap[0] is the kth best

Two heaps around the middle

low, high = [], []   # low: max-heap via -x
def add(x):
    if not low or x <= -low[0]:
        heapq.heappush(low, -x)
    else:
        heapq.heappush(high, x)
    # rebalance: len(low) is len(high) or one more
    if len(low) > len(high) + 1:
        heapq.heappush(high, -heapq.heappop(low))
    elif len(high) > len(low):
        heapq.heappush(low, -heapq.heappop(high))

In the first skeleton the heap never grows past k + 1, so each push and pop is O(log k). Pick the key so that the item you want to lose is the smallest: the value itself for "largest", the count for "most frequent", minus the distance for "closest". When items carry extra data, push tuples like (count, value): Python compares tuples left to right, so the first field decides and later fields break ties.

In the second, every value in low is at most every value in high, and the sizes differ by at most one. Both roots are then the one or two middle values, readable in O(1).

Problem 1 · Keep the best k

Kth largest element

Question

Given a list of integers and a number k, return the kth largest value in the list, counting duplicates separately (so in [5, 5, 4] the 2nd largest is 5). Try to do better than sorting the whole list.

Inputnums = [3, 2, 1, 5, 6, 4], k = 2
Output5
Think first: what do you need to remember while scanning?

Only the k largest values seen so far. The kth largest of those is the smallest of them, so keep them in a min-heap of size k. A new value either loses to the root (it can't be in the top k, skip it) or beats it (the root is pushed out of the top k; replace it). At the end the root is the answer.

The top row is the input, with x on the current value. Below: the heap as an array and as a tree.

Problem 2 · Keep the best k, by count

K most frequent elements

Question

Given a list of integers and k, return the k values that appear most often, most frequent first. When two values have the same count, either may be chosen; this version keeps the larger value, because it compares (count, value) pairs.

Inputnums = [1, 1, 1, 2, 2, 3], k = 2
Output[1, 2]
Think first: what is the "size" you rank by?

Not the value, its count. First count every value with a hash map in one pass. Then it is Problem 1 again over the (count, value) pairs: a min-heap of size k keyed on count, so the rarest of the current top k is at the root, ready to be evicted.

In the heap, the big number is the value and ×c under it is its count. The heap is ordered by (count, value).

Counting exactly needs one map entry per distinct value. For a huge stream (say every search query of the day) that is too much memory, which is where approximate counters such as the count-min sketch come in.

Time O(n + d log k), d = distinct valuesSpace O(d)Bucket sort by count: O(n)
Problem 3 · Smallest of k candidates

Merge k sorted lists

Question

You are given k lists, each already sorted from small to large (some may be empty). Combine them into one sorted list.

Input[[1, 4, 5], [1, 3, 4], [2, 6]]
Output[1, 1, 2, 3, 4, 4, 5, 6]
Think first: where can the next smallest value be?

Only at the front of some list: every list is sorted, so anything behind a front is at least as big as that front. So you only ever compare k values. Keep the fronts in a min-heap as (value, list number, position). Pop the smallest, output it, and push the next value from the same list.

Lists: amber = the front waiting in the heap, crossed out = already output. In the heap, L0, L1, … under a value says which list it came from.

Time O(N log k), N = total valuesSpace O(k) for the heapConcatenate and sort: O(N log N)
Problem 4 · Two heaps

Median of a stream

Question

Numbers arrive one at a time. After each one, report the median of everything so far: the middle value when the count is odd, the average of the two middle values when it is even.

Input5, 15, 1, 3
Output5, 10, 5, 4
Think first: what do you need to see at any moment?

Only the one or two values in the middle. Split the numbers into a lower half and an upper half. The middle is the largest of the lower half and the smallest of the upper half, so store the lower half in a max-heap and the upper half in a min-heap. After each insert, move one root across if the sizes drift more than one apart.

low is a max-heap (largest on top), high is a min-heap (smallest on top). The median is read from their two roots.

add: O(log n)median: O(1)Re-sorting each time: O(n log n) per number
Correctness

The invariants behind each heap

Root is the minimum

Every parent is no larger than its children, so by following parents upward from any node the values only shrink until the root. Nothing is smaller than the root. A sift only swaps a node with a parent or child that is out of order, and stops once the one moving node fits, so the rule holds everywhere again after each push or pop.

Size-k heap

Invariant: after reading some prefix of the input, the heap holds exactly the k largest values of that prefix (or all of them, if fewer than k). A new value bigger than the root belongs in the top k and pushes the root out; a value no bigger than the root does not belong. So at the end the heap is the top k, and its root, the smallest of them, is the kth largest.

Merging

The heap holds the front of every list that still has values. Each list is sorted, so the smallest remaining value overall is one of those fronts: the heap's root. Popping it and pushing its successor keeps the invariant, so values come out in sorted order.

Two heaps

Two invariants: everything in low is ≤ everything in high, and len(low) is len(high) or len(high) + 1. Moving a root across keeps the first, because it is the boundary value. With both true, low's root is the middle value for an odd count, and the two roots are the middle pair for an even count.

Cost

Each push or pop on a heap of size k is O(log k), and each input value causes a constant number of them: O(n log k) in total. Sorting is O(n log n). With n = 1,000,000 and k = 10, log₂ k ≈ 3.3 against log₂ n ≈ 20, about six times fewer steps, and the heap needs room for only 10 values. When k approaches n, the two converge.

In an interview

Name what sits at the root and why it is the item to evict or return. "Min-heap of size k, because its root is the weakest of the current top k." Then give O(n log k) and mention the alternatives: sorting, and quickselect for a one-off answer.
