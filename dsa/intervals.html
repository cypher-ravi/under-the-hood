Interval Merging and Overlap

An interval is a start and an end, like a meeting from 2 to 6. Sort a pile of them by start time and each one can only collide with the block just before it, so one left-to-right pass untangles them.

In 30 seconds
  • What: sort intervals (by start, or by end), then walk them once, comparing each with the last block you kept.
  • When: the input is a list of start/end pairs and the question says overlap, merge, conflict, free time or "how many at once".
  • Why it's fast: after sorting, overlap is a one-number check against the last block. Sorting costs O(n log n), the pass O(n), instead of comparing every pair.
  • The one thing to get right: the edge case. Do [1, 3] and [3, 5] overlap? Decide, then pick ≤ or < to match.

The idea, by example

Merge four meetings into blocks

Here are four intervals: [8, 10], [1, 3], [2, 6], [15, 18]. Some overlap. We want the busy blocks you'd get if you shaded them all on one line.

First, sort them by start. Now walk left to right and keep a list of blocks. For each interval, ask one question: does it start before the last block ends?

NextLast blockWhat it tells us
[1, 3]noneNothing yet. It starts the first block.
[2, 6][1, 3]2 ≤ 3, so it overlaps. Stretch the block's end to 6: [1, 6].
[8, 10][1, 6]8 > 6, a gap. Start a new block [8, 10].
[15, 18][8, 10]15 > 10, a gap. Start a new block.
3 blocks[1, 6], [8, 10], [15, 18]

Why only the last block? Every interval after [8, 10] starts at 8 or later. The block [1, 6] ended at 6, so nothing that comes next can reach back to it. Once a gap opens, it stays open.

Sorting by start turns "does this overlap anything?" into "does this overlap the last block?", one comparison instead of n.

Recognizing the pattern

Signals in the problem statement

Reach for intervals when you see one or more of these:

  • The input is a list of pairs with a start and an end: times, dates, page ranges, segments on a line.
  • The question says overlap, conflict, merge, free time or how many at once.
  • Brute force compares every pair, but the expected answer is O(n log n). That hints that sorting comes first.
  • You must keep the most non-clashing intervals or remove the fewest. Sort by end and be greedy.

Watch the edges: for ranges of numbers, [1, 3] and [3, 5] usually overlap (both contain 3). For meetings, they usually don't (one ends as the other starts). Ask, then use ≤ or < to match. Each problem below says which it uses.

When not to: if intervals keep arriving and you must answer after each one, re-sorting every time is slow. Keep them in an ordered structure instead, like a balanced tree or a heap of end times.

Template

The skeleton you adapt

iv.sort(key=lambda x: x[0])  # by start
out = [iv[0]]
for s, e in iv[1:]:
    last = out[-1]
    if s <= last[1]:     # overlaps
        last[1] = max(last[1], e)
    else:                # a gap
        out.append([s, e])

To adapt it to a new problem, answer three questions:

  1. What do you sort by? Start, to build blocks. End, to keep as many as possible. Or turn everything into events for counting.
  2. When do two intervals clash? Decide whether touching ends count, and write ≤ or < accordingly.
  3. What happens on a clash? Stretch the block (merge), add to a count (rooms), or throw one away (removals).
Problem 1 · Merge

Merge overlapping intervals

Question

Given a list of intervals in any order, combine every group that overlaps or touches, and return the resulting intervals sorted by start.

Input[[8, 10], [1, 3], [2, 6], [15, 18]]
Output[[1, 6], [8, 10], [15, 18]]

After sorting, which earlier interval can the next one possibly collide with?

The obvious way

Compare every pair, merge any two that overlap, and repeat until nothing changes. Each round is O(n²), and one merge can create a new overlap, so you may need several rounds.

Key insight

After sorting by start, the next interval can only touch the last block in the output. Every earlier block ended before the last one began, and the next interval starts even later.

The plan

  1. Sort by start. The first interval is the first block.
  2. For each next interval, compare its start with the last block's end.
  3. Start ≤ end: overlap. Set the block's end to the larger of the two ends.
  4. Start > end: a gap. Append the interval as a new block.

Writing last[1] = e instead of max(last[1], e). When one interval sits fully inside another, like [3, 6] inside [1, 9], the block shrinks by mistake.

Problem 2 · Insert

Insert an interval

Question

You have a calendar of busy intervals that are already sorted and don't overlap. Add one new interval, merging wherever needed, and return the calendar still sorted and non-overlapping.

Inputbusy = [[1, 2], [3, 5], [6, 7], [8, 10], [12, 16]], new = [4, 8]
Output[[1, 2], [3, 10], [12, 16]]

The list is already sorted. Do you really need to sort again?

The obvious way

Append the new interval and run Problem 1 on the whole list. It works, but the sort costs O(n log n) when the list was already in order.

Key insight

The busy list splits into three runs: blocks that end before the new interval starts, blocks that overlap it, and blocks that start after it ends. Only the middle run needs any work, and you can find all three in one pass.

The plan

  1. Copy every block that ends before the new interval starts.
  2. While a block starts at or before the new interval's end, swallow it: widen the new interval to cover both.
  3. Place the widened interval.
  4. Copy everything that's left unchanged.

Watch it run

The amber bar is the new interval; watch it widen as it swallows blocks. Green blocks were swallowed, dashed blocks were copied unchanged. The bottom row is the output.

Time O(n)Space O(n) for the outputAppend and re-merge: O(n log n)

Widening only the end. A swallowed block can start before the new interval does, so take the smaller start too.

Problem 3 · Sweep

How many meeting rooms?

Question

Each interval is a meeting [start, end). A room is free again the moment a meeting ends, so [1, 4) and [4, 6) can share. What's the smallest number of rooms that fits every meeting?

Input[[0, 30], [5, 10], [15, 20], [10, 15]]
Output2

Freeze time at one moment. How many rooms do you need right then?

The obvious way

For every time point, count how many meetings are running, and take the largest count. That's O(n × range), and the range of times can be huge.

Key insight

The rooms you need equals the most meetings running at the same moment. That count only changes when a meeting starts (+1) or ends (−1), so you only need to look at those moments, in time order.

The plan

  1. Turn each meeting into two events: (start, +1) and (end, −1).
  2. Sort the events by time. At a tie, put the −1 first so a freed room can be reused.
  3. Walk the events, adding each one to a running count.
  4. The highest the count ever reaches is the answer.

Watch it run

The red line sweeps left to right through time. Blue meetings are running at the line, dashed ones have ended. The counters below show rooms in use now and the most so far.

Time O(n log n)Space O(n) for the eventsCheck every time point: O(n × range)

Putting starts before ends at the same time. Then [1, 4) and [4, 6) look like they overlap at 4, and you count one room too many.

Problem 4 · Greedy by end

Fewest intervals to remove

Question

Remove as few intervals as possible so that the rest don't overlap. Intervals that only touch, like [1, 2] and [2, 3], are fine. Return how many you removed.

Input[[1, 2], [2, 3], [3, 4], [1, 3]]
Output1 (remove [1, 3])

Of all the intervals, which one is always safe to keep?

The obvious way

Try every subset, keep the ones with no overlaps, and pick the largest. There are 2ⁿ subsets, so this is hopeless past about 20 intervals.

Key insight

Keep the interval that ends earliest. It leaves the most room for everything after it. Whatever a best answer keeps first, swapping in the earliest-ending one can't cause a new clash, because it ends no later.

The plan

  1. Sort by end. The last kept end starts at −∞.
  2. If the next interval starts at or after the last kept end, keep it and update the end.
  3. Otherwise it clashes: remove it and add one to the count.

Watch it run

Bars are sorted by end. Green bars are kept, red is the one being removed now, dashed bars were removed. The red line marks the last kept end.

Time O(n log n)Space O(1) besides sortingTry every subset: O(2ⁿ)

Sorting by start instead of end. A long interval that starts early, like [1, 10], gets kept and blocks everything else.

Correctness

Why one pass after sorting is enough

For the merge pass, the argument fits in three sentences:

Always true

After handling the first k intervals in sorted order, the output holds the right blocks for those k, and only the last block can still grow.

Each step

The next interval starts at or after every earlier start. If it starts after the last block ends, there's a gap, and later intervals start even further right, so nothing can ever close it.

It ends

Each interval is looked at once, so the pass is O(n). The sort before it is the O(n log n).

Sweep

The number of running meetings only changes at a start or an end, so checking just those moments finds the true maximum. Ends go first at a tie because a half-open meeting has already finished.

Greedy

Swap the first interval of any best answer for the earliest-ending one. The answer stays valid and the same size. Repeat on what's left.

In an interview: say why you sort, and by what, before writing code. Then state your edge rule out loud ("touching counts as overlap"). The idea of sweeping a line across objects as sorted events goes back to Michael Shamos and Dan Hoey's 1976 work on geometric intersection; the rooms problem is that sweep in one dimension.

Recap

Cheat sheet

Merge

Sort by start. Start ≤ last end → stretch with max(). Else new block.

Insert

Copy before, swallow overlaps (min start, max end), copy after.

Meeting rooms

+1 at starts, −1 at ends, ends first at ties. Answer = peak count.

Fewest removals

Sort by end. Keep if it starts at or after the last kept end.
