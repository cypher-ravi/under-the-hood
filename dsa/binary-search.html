Binary Search on the Answer

Look at the middle of what's left, and use one yes/no answer to throw away half of it. The same loop finds a number in a sorted array, or the smallest setting that works, in about 20 looks for a million options.

In 30 seconds
  • What: keep a range that must contain the answer. Check its middle. Keep the half the answer is in.
  • When: sorted data, or any yes/no question whose answers go "no, no, no, yes, yes" as the value grows.
  • Why it's fast: each look halves the range. n options need about log₂ n looks: 1,000,000 → 20.
  • The one thing to get right: whether mid stays in the range (hi = mid) or not (hi = mid − 1).

Pattern-first structure inspired by Codeintuition's curriculum. Problems, explanations and visualizations on this page are our own.

The idea, by example

The higher-or-lower game

I'm thinking of a number from 1 to 100. You guess, and I say "higher" or "lower". The smart first guess is 50: whatever I answer, 50 numbers are gone. Then 25 or 75, and so on. You'll always win within 7 guesses.

Binary search is that game played on a sorted array. Below we look for 56 among 11 sorted numbers. Each look checks the middle of what's left (the dark cell) and greys out the half that can't hold 56.

One look at the middle tells you more than "is this it?". Because the array is sorted, it tells you which side the answer is on, so half the candidates disappear at once.

The idea, continued

You don't need a sorted array. You need a flip.

Sorted order is one way to know which side to keep. The more general version: ask the same yes/no question about every position. If the answers look like this, binary search works.

nonononoyesyesyes

All the "no"s come first, then all the "yes"es. Binary search finds the first yes. Some examples of the question:

  • "Is a[i] ≥ 3?" on a sorted array: the first yes is where 3 starts (Problem 2).
  • "Is build number v broken?": the first yes is the first bad build.
  • "Can I eat all the bananas in time at speed k?": the first yes is the slowest speed that works (Problem 4).

The last example has no array to search at all. You search the possible answers, which is where the page gets its name.

Recognizing the pattern

Signals in the problem statement

  • The input is sorted (or sorted and then rotated) and you need a position or a nearest value.
  • The limits hint at O(log n): n up to 109, or "do better than linear".
  • You're asked for the smallest value that works or the largest that still works: least speed, least capacity, largest gap.
  • If you guess an answer, you can check it quickly, and anything bigger than a working answer also works.
  • Words like "first", "last", "earliest", "insert position", "first bad version".

When not to: if the yes/no answers can flip back and forth, halving can jump right past the answer. And sorting an unsorted array first costs O(n log n), which only pays off if you'll search it many times.

Template

Two skeletons

Learn the second one well. Almost every harder problem turns into it.

Exact match

lo, hi = 0, len(a) - 1
while lo <= hi:
    mid = (lo + hi) // 2
    if a[mid] == target:
        return mid
    if a[mid] < target:
        lo = mid + 1  # left half out
    else:
        hi = mid - 1  # right half out
return -1             # nothing left

First yes

lo, hi = 0, n     # n = "no yes"
while lo < hi:
    mid = (lo + hi) // 2
    if ok(mid):
        hi = mid      # mid may be it
    else:
        lo = mid + 1  # mid is a no
return lo

Two habits prevent almost every bug:

  1. Say what the range means before writing the loop: "the answer is always somewhere in lo..hi". Then check each update keeps that true. If mid might be the answer, keep it: hi = mid, not mid − 1.
  2. Make sure every round shrinks the range, or the loop never ends. With lo < hi, mid is always below hi, so both branches make progress.

In Java or C++, write lo + (hi − lo) / 2 so the sum can't overflow.

Problem 1 · Exact match

Find a target in a sorted array

Question

You get an array of integers in non-decreasing order and a target value. Return an index where the target appears, or −1 if it isn't in the array. Use O(log n) comparisons.

Input[3, 8, 12, 17, 21, 26, 30, 34, 41], target 26
Output5

The middle is 21 and you want 26. Which half can you throw away?

The obvious way

Scan from the left until you find it. Up to n looks, and it ignores the sorting.

Key insight

Everything at or left of 21 is at most 21, so none of it can be 26. One comparison at the middle rules out that whole half.

The plan

  1. lo = first index, hi = last index.
  2. Look at the middle. Equal to the target? Return it.
  3. Middle too small: lo = mid + 1. Too big: hi = mid − 1.
  4. If lo passes hi, nothing is left: return −1.

Watch it run

L = lo, R = hi, mid = the middle being checked. Grey cells are ruled out.

Time O(log n)Space O(1)Linear scan: O(n)

Writing hi = mid here. The middle was already checked, so it must leave the range, or the loop can spin forever.

Problem 2 · First yes

Where would the target go?

Question

You get an array in non-decreasing order and a target. Return the smallest index i with a[i] ≥ target. That's where the target should be inserted to keep the array sorted, and its first copy if it's already there. If every element is smaller, return the length of the array.

Input[1, 3, 3, 3, 5, 8, 9], target 3
Output1 (the first 3)
Target 65 (between 5 and 8)

The middle is a 3 and the target is 3. Why can't you stop there?

The obvious way

Scan from the left until you hit something ≥ target. O(n).

Key insight

There may be more 3s to the left, so finding one isn't enough. Ask "is a[i] ≥ target?" at each index instead. On a sorted array the answers go no, no, yes, yes, yes, and you want the first yes.

The plan

  1. lo = 0, hi = n (n stands for "every element is smaller").
  2. Middle says yes? It could be the first yes, so keep it: hi = mid.
  3. Middle says no? It and everything left of it are no: lo = mid + 1.
  4. When lo meets hi, that's the first yes.

Watch it run

The second row is the yes/no question: F cells are proven "no" (left of lo), T cells are proven "yes" (from hi on), and ? cells aren't decided yet.

Time O(log n)Space O(1)Scan from the left: O(n)

Returning as soon as a[mid] == target. That finds a copy, not the first one.

Problem 3 · Halve with a twist

Search in a rotated sorted array

Question

An array of distinct integers was sorted and then rotated: a front chunk was cut off and moved to the end, so [2, 5, 9, 14, 20] might now read [14, 20, 2, 5, 9]. Given the rotated array and a target, return the target's index or −1, in O(log n) time.

Input[15, 18, 22, 27, 3, 6, 9, 11], target 6
Output5

Cut the array in half at the middle. Can both halves contain the "drop" from 27 to 3?

The obvious way

Scan every element. O(n). Plain binary search fails because the array isn't sorted as a whole.

Key insight

The drop is in only one half, so at least one half is properly sorted. For a sorted half, its two ends tell you whether the target could be inside. If yes, keep that half. If no, the target can only be in the other one.

The plan

  1. Look at the middle. Is it the target? Done.
  2. If a[lo] ≤ a[mid], the left half is sorted. Otherwise the right half is.
  3. Is the target between the sorted half's two ends? Keep that half. If not, keep the other.
  4. Repeat until found, or nothing is left.

Watch it run

Amber outline = the half known to be sorted at this step. Grey = ruled out.

Time O(log n)Space O(1)Linear scan: O(n)

Checking only one end of the sorted half. The target must be at least its left end and below its right end (or the middle).

Problem 4 · Search the answers

The slowest eating speed that still finishes in time

Question

There are piles of bananas and a guard returns in h hours. Each hour you pick one pile and eat up to k bananas from it. If the pile has fewer than k left, you finish it and wait out the rest of that hour. Find the smallest whole number k that lets you finish every pile within h hours. (h is at least the number of piles, so some speed always works.)

Inputpiles [3, 6, 7, 11], h = 8
Output4
Whyat k = 4: 1 + 2 + 2 + 3 = 8 hours; at k = 3: 1 + 2 + 3 + 4 = 10

If speed 5 finishes in time, does speed 6?

The obvious way

Try k = 1, 2, 3, … until one finishes in time. Each try costs a pass over the piles, and the biggest pile could be huge.

Key insight

Eating faster never takes longer. So "does speed k finish in time?" goes no, no, …, yes, yes as k grows. That's a first-yes search, over speeds instead of array positions.

The plan

  1. The answer is between 1 and the biggest pile (at that speed every pile takes one hour).
  2. Guess the middle speed k. Hours needed = sum of ⌈pile / k⌉.
  3. Fits in h hours? k might be the answer: hi = k. Too slow? lo = k + 1.
  4. When lo meets hi, that's the slowest speed that works.

Watch it run

The top line is every possible speed. The shaded band is the range still in play and the dot is the guess. Green ticks are proven fast enough, red ticks too slow. Below, each pile shows its hours at speed k.

Time O(n log max)Space O(1)Try every speed: O(n · max)

Searching from 0. Speed 0 divides by zero; the smallest real speed is 1.

Correctness

Why halving is safe, why it stops, and why it's fast

Using the "first yes" skeleton:

Always true

Everything left of lo is a known "no", and everything from hi on is a known "yes". At the start nothing is known, so this holds.

Each step

If mid says yes, so does everything after it, so hi = mid keeps the rule. If mid says no, so does everything before it, so lo = mid + 1 keeps it.

It stops

While lo < hi, mid sits in lo..hi−1, so each branch shrinks the range by at least one.

The answer

At the end lo = hi. Everything before is "no" and everything from there is "yes", so lo is the first yes (or n if there is none).

O(log n)

Each round keeps at most half, so about log₂ n rounds. When searching answers, n is the size of the answer range, and each round also pays for one check.

size after k rounds ≤ n / 2^k ⇒ rounds ≈ log₂ n (10⁶ → 20, 10⁹ → 30)

Recap

Cheat sheet

Find a target

lo ≤ hi; mid leaves the range on both sides.

First yes

lo < hi; yes → hi = mid, no → lo = mid + 1.

Rotated

One half is sorted. Is the target inside it? Keep it, else the other.

Search the answers

Range = possible answers. Check one guess per round.
