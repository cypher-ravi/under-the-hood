Binary Search on the Answer

Keep a range that is guaranteed to contain the answer, look at its middle, and use one comparison to throw away half of it. The range can be positions in a sorted array, or it can be every value the answer could possibly take, like every eating speed from 1 to the biggest pile. As long as a single yes/no question splits the range cleanly into "no" then "yes", halving finds the boundary in O(log n) checks.

Pattern-first structure inspired by Codeintuition's curriculum. Problems, explanations and visualizations on this page are our own.

The idea, from first principles

Every look rules out half of what's left

Looking for 56 in a sorted list of 15 numbers, you could check them one by one: up to 15 looks. But one look at the middle tells you much more than "is this it?". If the middle value is 37, then 56 can't be at or before it, because everything there is at most 37. Eight positions vanish in one comparison. Look at the middle of what's left, and repeat.

After k looks at most n / 2k positions remain, so 15 positions take at most 4 looks and a million take at most 20. The only thing that matters is that one comparison at the middle tells you which side the answer must be on. Sorted order gives you that for free. So does any yes/no question whose answers go "no, no, no, yes, yes" as the value grows, which is how the same loop ends up searching over answers instead of array positions.

Recognizing the pattern

Signals in the problem statement

  • The input is sorted (or sorted and then rotated), and you need a position, a count, or a nearest value.
  • The constraints hint at O(log n): n up to 109, or "do better than linear".
  • The question asks for the minimum value that works or the maximum value that still works: smallest speed, least capacity, largest minimum distance.
  • If you guess an answer x, you can check whether x is good enough in roughly linear time, and anything bigger than a good x is also good (or anything smaller is).
  • Phrases like "first", "last", "earliest day", "insert position", "first bad version".

Counter-signal: binary search needs monotonic answers. If "x works" doesn't imply "x + 1 works" (for example the check can flip back and forth), halving can jump past the answer. Then you need a scan, a DP, or a different structure. And on an unsorted array, sorting first costs O(n log n), which only pays off if you will search many times.

Template

Two skeletons, one invariant each

Exact match (closed range)

lo, hi = 0, len(a) - 1
# invariant: if target is in a,
# it is somewhere in a[lo..hi]
while lo <= hi:
    mid = (lo + hi) // 2
    if a[mid] == target:
        return mid
    if a[mid] < target:
        lo = mid + 1   # mid and left: too small
    else:
        hi = mid - 1   # mid and right: too big
return -1          # range is empty

First true (lower bound)

lo, hi = 0, n      # n means "none is true"
# invariant: ok(i) is false for i < lo
#            ok(i) is true  for i >= hi
while lo < hi:
    mid = (lo + hi) // 2
    if ok(mid):
        hi = mid       # mid may be the first true
    else:
        lo = mid + 1   # mid is false, skip it
return lo          # lo == hi: the boundary

The exact version is for "is it here?". The first-true version is the one to memorise, because almost every harder problem reduces to it: pick a predicate ok that is false, false, …, true, true over the range, and the loop finds where it flips. ok(i) = a[i] >= target gives the insert position; ok(k) = "speed k finishes in time" gives the slowest speed that works.

Two habits prevent most bugs. Write the invariant down before the loop, then check that each update keeps it true: hi = mid (not mid - 1) when mid might be the answer. And make sure every update shrinks the range: with mid = (lo + hi) // 2 and lo < hi, mid is always below hi, so both branches make progress. In languages with fixed-size integers, write lo + (hi - lo) / 2 to avoid overflow.

Problem 1 · Exact match

Find a target in a sorted array

Question

You get an array of integers in non-decreasing order and a target value. Return an index where the target appears, or −1 if it isn't in the array. Use O(log n) comparisons.

Input[3, 8, 12, 17, 21, 26, 30, 34, 41], target 26
Output5
Think first: the middle is 21 and you want 26. What's ruled out?

Everything at or left of the middle is at most 21, so none of it can be 26. Move lo to mid + 1. If the middle were bigger than the target, the right side would go instead. If the range ever becomes empty (lo > hi), the target isn't there.

L = lo, R = hi, mid = the middle being checked. Grey cells are ruled out.

Problem 2 · First true

Where would the target go?

Question

You get an array in non-decreasing order and a target. Return the smallest index i with a[i] ≥ target. That is where the target should be inserted to keep the array sorted, and if the target is already present it is its first occurrence. If every element is smaller, return the length of the array.

Input[1, 3, 3, 3, 5, 8, 9], target 3
Output1 (the first 3)
Target 65 (between 5 and 8)
Think first: why can't you stop as soon as a[mid] equals the target?

There may be more copies to the left. Instead, ask a yes/no question at every index: "is a[i] ≥ target?". Along a sorted array the answers go F, F, T, T, T. You want the first T. If mid says T, it could be the first one, so keep it: hi = mid. If it says F, it and everything left of it are F: lo = mid + 1.

Same shape, different story: "versions 1 to n, and from some version on every build is broken; find the first broken one with few checks" is this problem with ok(v) = is_bad(v). The second row of the picture is the predicate: F cells are proven false (left of lo), T cells are proven true (from hi on), and ? cells haven't been decided yet.

Problem 3 · Halve with a twist

Search in a rotated sorted array

Question

An array of distinct integers was sorted in increasing order and then rotated: some prefix was cut off and moved to the end, so [2, 5, 9, 14, 20] might now read [14, 20, 2, 5, 9]. Given the rotated array and a target, return the target's index or −1, in O(log n) time.

Input[15, 18, 22, 27, 3, 6, 9, 11], target 6
Output5
Think first: cut the range at mid. What is always true of the two halves?

The rotation point can only be on one side, so at least one half is sorted. Compare a[lo] with a[mid] to see which. For the sorted half you can tell from its two ends whether the target could be inside it. If it could, keep that half; if not, the target can only be in the other half.

Amber outline = the half that is known to be sorted at this step. Grey = ruled out.

Time O(log n)Space O(1)Linear scan: O(n)
Problem 4 · Search the answer space

The slowest eating speed that still finishes in time

Question

There are several piles of bananas and a guard returns in h hours. Each hour you pick one pile and eat up to k bananas from it; if the pile has fewer than k left, you finish it and wait out the rest of that hour. Find the smallest whole number k that lets you finish every pile within h hours. (h is at least the number of piles, so some speed always works.)

Inputpiles [3, 6, 7, 11], h = 8
Output4
Whyat k = 4: 1 + 2 + 2 + 3 = 8 hours; at k = 3: 1 + 2 + 3 + 4 = 10
Think first: if speed k finishes in time, what about k + 1?

Eating faster never takes more hours, so once a speed works, every faster speed works too. The question "does speed k finish?" goes no, no, …, yes, yes as k runs from 1 to the largest pile (at that speed each pile takes one hour). That's a first-true search over speeds, not over the array. Checking one speed costs one pass: sum(ceil(p / k)).

Correctness

Why halving is safe, why it stops, and why it's fast

Invariant

For first true: every index below lo is known false, and every index from hi on is known true (with hi = n standing for "nothing true yet"). At the start nothing is below lo = 0 and nothing is at or above hi = n, so it holds trivially. If ok(mid) is true, setting hi = mid keeps "from hi on is true" because the predicate is monotonic. If it's false, everything up to mid is false, so lo = mid + 1 keeps "below lo is false".

Termination

While lo < hi, the floor of the average satisfies lo ≤ mid < hi. So hi = mid strictly lowers hi and lo = mid + 1 strictly raises lo: the range shrinks every round and the loop must end. The classic exact search shrinks too, because both updates skip mid itself.

The answer

The loop ends with lo = hi. Everything below is false and everything from there on is true, so lo is exactly the first true position, or n if there is none. No final check is needed.

O(log n)

Each round keeps at most half of the range (rounded up), so after k rounds at most n / 2k + 1 positions remain. The range hits size one after about log₂ n rounds. For answer-space searches the "n" is the size of the answer range, and each round also pays for one feasibility check.

In an interview

Say what the range means ("the answer is always inside [lo, hi]") and what the predicate is, then show that both branches keep that true and shrink the range. For answer-space problems, argue monotonicity out loud ("faster never takes longer") before writing the loop.

size after k rounds ≤ n / 2^k ⇒ rounds ≈ log₂ n (10⁶ → 20, 10⁹ → 30)
