DFS and BFS on Trees

Almost every tree question is "visit each node once, in a useful order". Go deep down one branch first (DFS), or sweep across one level at a time (BFS), and pick the order that hands each node what it needs.

In 30 seconds
  • What: a function that handles one node and calls itself on the left and right children (DFS), or a queue that hands out nodes row by row (BFS).
  • When: the input is a tree, or anything tree-shaped like folders or an org chart.
  • Why it's fast: every node is visited exactly once, so n nodes take O(n) time. Extra memory is the height of the tree (DFS) or its widest row (BFS).
  • The one thing to get right: when you do the work for a node: before its children, between them, after them, or row by row.

Pattern-first structure inspired by Codeintuition's curriculum. Problems, explanations and visualizations on this page are our own.

The idea, by example

One tree, four orders

A binary tree is either empty, or a node with a value and two smaller trees hanging off it: a left subtree and a right subtree. Here is one with six nodes.

Because a tree is "a node plus two smaller trees", the natural way to walk it is the same: handle the node, then ask the same function to handle each subtree. An empty tree is where it stops. Walking down one branch before trying the next is called depth-first search (DFS).

The walk itself never changes. The only choice is when you write the node down:

OrderWrite the nodeResult
Prebefore its children1 2 4 5 3 6
Inbetween left and right4 2 5 1 3 6
Postafter both children4 5 2 6 3 1
Levelrow by row, top down1 | 2 3 | 4 5 6

The last row is breadth-first search (BFS). It ignores subtrees and sweeps across each row before going lower.

Pick the order by asking what a node needs. Needs its children's answers? Do the work after them (post). Needs something from above? Pass it down before the children (pre). Needs rows? Use BFS.

Recognizing the pattern

Signals in the problem statement

Reach for a tree walk when you see one or more of these:

  • The input is a tree, or tree-shaped (folders, an org chart, a parsed expression), and the answer needs every node or every root-to-leaf path.
  • A node's answer is built from its children's answers: height, size, sum, balanced or not. Postorder, returning a value.
  • A node needs something from above: the path so far, a running sum, a range its value must fit. Pass it down as an argument.
  • The words level, row, depth from the top, closest to the root, or "the view from the right side". BFS with a queue.
  • A binary search tree and you need values in sorted order, or the k-th smallest. Inorder.

When not to recurse: each recursive call waits on a stack, one per level. A balanced tree of a million nodes is about 20 levels deep, but a lopsided tree shaped like a list can be a million deep, and Python stops at about 1,000. For inputs like that, use the loop version with your own stack.

Template

Two skeletons

Start with the DFS one. Reach for BFS when the question talks about levels.

DFS (recursive)

def dfs(node):
    if node is None:
        return    # empty: stop
    # pre: work here
    dfs(node.left)
    # in: work here
    dfs(node.right)
    # post: work here

BFS (one level at a time)

q = deque([root])
while q:
    # q holds exactly one level
    for _ in range(len(q)):
        node = q.popleft()
        visit(node)
        for c in (node.left, node.right):
            if c: q.append(c)

To adapt it to a new problem, answer three questions:

  1. What does the empty tree return? 0 for a height, True for "is it valid", nothing for a list. Get this first; it stops the recursion.
  2. Which way does the information flow? Up from the children means work after the calls. Down from the parent means extra arguments.
  3. DFS or BFS? Rows or "nearest to the root" means BFS. For BFS, read len(q) before the inner loop so children added now wait for the next level.

The recursive DFS can also be written as a loop with your own list as a stack. It does exactly what the call stack does for you.

Problem 1 · Order is the answer

Preorder, inorder and postorder

Question

Given the root of a binary tree, return its node values in preorder (node, then left subtree, then right subtree), inorder (left, node, right) and postorder (left, right, node).

Input[1, 2, 3, 4, 5, null, 6]
Preorder[1, 2, 4, 5, 3, 6]
Inorder[4, 2, 5, 1, 3, 6]
Postorder[4, 5, 2, 6, 3, 1]

Do you need three different functions, or one function with the "write it down" line in three places?

The obvious way

Write three separate functions and learn each one by heart. It works, but you end up memorising three things when there is really one.

Key insight

All three orders make the same calls in the same sequence: the node, then everything on its left, then everything on its right. Only the line that records the value moves: before the left call, between the calls, or after the right call.

The plan

  1. If the node is empty, return.
  2. Preorder: record the node now.
  3. Walk the left subtree. Inorder: record the node now.
  4. Walk the right subtree. Postorder: record the node now.

Watch it run

Switch between the presets and watch the call stack: it is identical for all three orders, only the output changes. Blue is the running call, amber calls are paused waiting for a child, a green ring means finished, and a dashed ∅ is a call on an empty child.

Time O(n)Space O(h), h = heightLopsided tree: h = n

Forgetting the empty-tree check, so the code reads node.left on None and crashes at the first leaf.

Problem 2 · Level by level

Level order traversal

Question

Given the root of a non-empty binary tree, return its values level by level: a list of lists where the first list holds the root, the next holds its children from left to right, and so on.

Input[3, 9, 20, null, null, 15, 7]
Output[[3], [9, 20], [15, 7]]

If you line nodes up in a queue, how can you tell where one level ends and the next begins?

The obvious way

Run a DFS that also passes down the depth, and append each value to levels[depth]. That works too, but it's easy to get wrong, and it doesn't extend to "stop at the first level where X happens".

Key insight

A queue is first in, first out. When you start a level, the queue holds exactly that level's nodes and nothing else, so its length is the level's size. Pop that many; their children pile up behind and become the next level.

The plan

  1. Put the root in a queue.
  2. Read the queue's length: that's the size of this level.
  3. Pop that many nodes. Record each, and push its children to the back.
  4. Save the level. Repeat until the queue is empty.

Watch it run

Blue is the node just popped, amber nodes are waiting in the queue, and a green ring means the node is already in a level. Watch the queue between levels: it holds exactly the next row.

Time O(n)Space O(w), w = widest levelFull tree: w ≈ n / 2

Using while q: as the inner loop instead of range(len(q)). The children you just added get popped too, and every level merges into one.

Problem 3 · Facts flow up

Maximum depth of a binary tree

Question

Return the number of nodes on the longest path from the root down to a leaf. An empty tree has depth 0 and a single node has depth 1.

Input[3, 9, 20, null, null, 15, 7]
Output3 (3 → 20 → 15)

If someone told you the depths of the left and right subtrees, what would the answer be?

The obvious way

List every root-to-leaf path and measure each. That repeats the top part of the tree for every leaf, and storing all the paths costs memory too.

Key insight

The depth of a tree is one more than the deeper of its two subtrees. So ask each child for its depth, wait for both answers, then return 1 + max(left, right). The work comes after both calls: a postorder walk.

The plan

  1. Empty tree: return 0. This stops the recursion.
  2. Ask the left child for its depth.
  3. Ask the right child for its depth.
  4. Return 1 + the larger of the two.

Watch it run

The number under a finished node is the depth its call returned. Answers travel up the tree one node at a time. At the end, filled green nodes mark one deepest path.

Time O(n)Space O(h)BFS also works: count the levels

Returning 1 for an empty tree, which counts a phantom node under every leaf and makes every answer one too big.

Problem 4 · Facts flow down

Is it a valid binary search tree?

Question

Decide whether a binary tree is a binary search tree: for every node, all values in its left subtree are strictly smaller than it and all values in its right subtree are strictly larger. Duplicates are not allowed.

Input[8, 4, 12, 2, 9, 10, 14]
Outputfalse
Why9 sits in 8's left subtree but is bigger than 8

In the example, 9 is a fine right child of 4. So why is the tree still wrong?

The obvious way

For every node, scan its whole left subtree for a bigger value and its whole right subtree for a smaller one. Each scan can touch most of the tree, so it's O(n²) on a lopsided tree.

Key insight

A node isn't just limited by its parent but by every ancestor. Those limits add up to one allowed range (lo, hi). Pass it down: going left, the parent's value becomes the new upper limit; going right, it becomes the new lower limit.

The plan

  1. Start at the root with the range (−∞, ∞).
  2. Empty tree: valid.
  3. If the node's value is not strictly inside (lo, hi), return False.
  4. Check the left child with (lo, value) and the right child with (value, hi).

Watch it run

Each stack frame shows the node and its allowed range (lo, hi). Watch the range tighten as you go down. A red ring means the value fell outside its range.

Time O(n)Space O(h)Scan each subtree: O(n²)

Only comparing each node with its two children. That passes the example above, which is not a search tree.

Correctness

Why every node is handled once, in the right order

The whole argument fits in four short claims:

Always true

If the function handles any smaller tree correctly, it handles this one: the two subtrees are smaller, so the two calls cover them, and the node gets its one line of work. The empty tree is where it starts.

Each step

At any moment the paused calls on the stack are exactly the path from the root to where you are. So the extra memory is the height h: about log₂ n for a balanced tree, n for a lopsided one.

It ends

Every call moves to a smaller tree, and each node is called once. n nodes, O(n) time.

BFS goes by depth

A node only adds children one level lower, to the back of the queue. So a whole level leaves the queue before any of the next level. That's why BFS reaches each node along the shortest path from the root.

In an interview: say which way the information flows. "The answer needs both children's results, so I do the work after the calls" or "each node needs a range from above, so I pass it down". Then name the base case and the stack depth.

Recap

Cheat sheet

Traversal orders

Same walk. Record before (pre), between (in) or after (post) the calls.

Level order

Queue. Pop len(q) nodes per level, push their children.

Maximum depth

Empty is 0. Return 1 + max(left, right).

Valid search tree

Pass (lo, hi) down. Left tightens hi, right tightens lo.
