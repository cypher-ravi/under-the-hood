Simultaneous Traversal

Walk two sorted sequences at once, one finger in each. Compare the two fronts, deal with the smaller one, and move only that finger, so two arrays are combined in a single pass.

In 30 seconds
  • What: one pointer in each of two sequences, i in A and j in B, usually both moving forward.
  • When: two sorted inputs you need to merge, compare, or check that one appears inside the other in order.
  • Why it's fast: each comparison uses up at least one element, so it takes at most n + m steps instead of n × m.
  • The one thing to get right: the leftovers. When one side runs out, decide what happens to the rest of the other.

Pattern-first structure inspired by Codeintuition's curriculum. Problems, explanations and visualizations on this page are our own.

The idea, by example

Merge two sorted piles

Picture two sorted piles of cards, smallest on top. The smallest card left anywhere must be on top of one of the piles. So to know what comes next, you only ever compare two cards: the two tops.

Let's merge A = [1, 4, 7, 9] and B = [2, 3, 8] by hand:

A[i]B[j]TakeOutput so far
1211
4221, 2
4331, 2, 3
4841, 2, 3, 4
7871, 2, 3, 4, 7
9881, 2, 3, 4, 7, 8
9–9B is empty, copy the rest of A. Done.

Six comparisons for seven numbers. Comparing every element of A with every element of B would take n × m. Gluing them together and sorting again takes (n + m) log(n + m) and throws away the order you already had.

Because both inputs are sorted, the answer to "what's next?" is always at one of the two fronts. One comparison, one element used up, never look back.

Recognizing the pattern

Signals in the problem statement

Reach for simultaneous traversal when you see one or more of these:

  • There are two inputs (arrays, strings or lists), and both are sorted or have a fixed order.
  • The task is to combine them (merge), compare them (common elements, differences) or check that one follows the other (subsequence).
  • The statement says the inputs are already sorted. That's a hint not to sort again and to aim for O(n + m).
  • You must write into one input in place, and it has spare room at the end.

When not to: if the inputs aren't sorted and you only need "is x in both?", a hash set does it in O(n + m) without sorting. Also, don't confuse this with Two Pointers: there both pointers live in one array and move toward each other. Here each pointer owns its own sequence.

Template

The skeleton you adapt

i, j = 0, 0
while i < len(A) and j < len(B):
    if A[i] == B[j]:
        use both; i += 1; j += 1
    elif A[i] < B[j]:
        use or skip A[i]; i += 1
    else:
        use or skip B[j]; j += 1
# one side ran out:
# handle the other's leftovers

To adapt it to a new problem, answer three questions:

  1. What does "use" mean? Append to an output, record a match, or just count.
  2. When the fronts differ, which side moves? Usually the smaller one, because it can't match anything later in the other array.
  3. What happens to the leftovers? Merge copies them. Intersect drops them. Subsequence checks which side ran out. Forgetting this is the most common bug.
Problem 1 · Merge

Merge two sorted arrays

Question

Given two arrays, each sorted in increasing order, return a single array with every element from both, also sorted.

InputA = [1, 4, 7, 9], B = [2, 3, 8]
Output[1, 2, 3, 4, 7, 8, 9]

Of everything not yet written, where must the smallest value be?

The obvious way

Glue the two arrays together and sort. That's O((n + m) log(n + m)), and it ignores the fact that each half is already sorted.

Key insight

The next output is the smaller of the two fronts, A[i] or B[j]. Take it and move only that pointer. When one array runs out, the rest of the other is sorted and larger than everything written, so copy it straight across.

The plan

  1. i = 0 in A, j = 0 in B, empty output.
  2. Append the smaller of A[i] and B[j]. Move that pointer.
  3. Repeat until one array runs out.
  4. Copy whatever is left of the other array.

Watch it run

Press Next to step through, or try your own arrays. Green: the value just taken. Grey: already used. The bottom row is the output so far.

Time O(n + m)Space O(n + m) for the outputConcatenate and sort: O((n + m) log(n + m))

Stopping when one array runs out and losing the rest of the other. Always copy the leftovers.

Problem 2 · Match

Is it a subsequence?

Question

Given a short string s and a longer string t, return true if you can delete some characters of t (possibly none), without reordering the rest, and get s.

Inputs = "ace", t = "abcde"
Outputtrue (a, c, e appear in order)

If s[i] matches t[j] right now, is there ever a reason to wait for a later match?

The obvious way

Try every way of choosing characters from t and see if any spells s. The number of choices grows exponentially with the length of t.

Key insight

Matching early never hurts. If s[i] equals t[j], taking it now leaves the most of t for the rest of s. So one scan of t is enough, and i moves only on a match.

The plan

  1. i = 0 in s, j = 0 in t.
  2. If s[i] equals t[j], move i.
  3. Move j every time, match or not.
  4. Stop when either runs out. Return whether i reached the end of s.

Watch it run

In s, green means matched and blue is the character we're looking for. In t, green is a match and red is a character we skipped.

Time O(len t)Space O(1)

Returning true just because the loop finished. The loop also stops when t runs out, so check that i reached the end of s.

Problem 3 · Intersect

Common elements of two sorted arrays

Question

Given two sorted arrays, return the elements they share. If a value appears twice in both, include it twice.

InputA = [1, 2, 2, 4, 6, 8], B = [2, 2, 3, 6, 9]
Output[2, 2, 6]

The fronts differ. Can the smaller one still match anything?

The obvious way

For each element of A, scan B for an unused equal value. Nested loops: O(n × m).

Key insight

If A[i] is smaller than B[j], it's smaller than everything left in B too, because B is sorted. It can't match anything, so skip it. Equal fronts are a match: record it and move both.

The plan

  1. i = 0 in A, j = 0 in B.
  2. Equal? Record the value, move both.
  3. Otherwise move the pointer on the smaller value.
  4. Stop when either runs out. Nothing left can match.

Watch it run

Green: a matched pair. Grey: skipped, because it was too small to match anything left. The bottom row is the common elements found so far.

Time O(n + m)Space O(1) besides the outputNested loops: O(n × m)

Moving only one pointer on a match. The same value then matches again and repeats get counted too many times.

Problem 4 · Backwards

Merge into the first array, in place

Question

Array A holds m sorted values followed by n empty slots. Array B holds n sorted values. Merge B into A so that A ends up fully sorted, without using another array.

InputA = [1, 4, 7, _, _, _], B = [2, 5, 6]
OutputA = [1, 2, 4, 5, 6, 7]

Where is the free space, and why does merging from the front go wrong?

The obvious way

Merge into a new array and copy it back. That works, but costs O(n + m) extra memory, which the question forbids.

Key insight

Writing at the front would overwrite values of A you haven't placed yet. The empty space is at the end, so fill from the end: put the larger of the two last values into the last free slot. The write pointer can never overtake the read pointer in A.

The plan

  1. i on A's last value, j on B's last value, k on the last slot.
  2. Write the larger of A[i] and B[j] into A[k]. Move that pointer left.
  3. Move k left. Repeat while B has values left.
  4. Once B is used up, A's remaining values are already in place.

Watch it run

The top row is A: its values, then the empty slots. Blue: the two values being compared. Green: slots holding their final value. Grey: old copies about to be overwritten.

Time O(n + m)Space O(1)

Stopping when A's values run out. B may still hold small values; keep going until j drops below 0.

Correctness

Why a single pass is enough

The whole argument fits in three sentences:

Always true

Everything before i in A and before j in B has been handled correctly, and nothing after them has been touched.

Each step

Both arrays are sorted, so the smaller front can't pair with anything later in the other array. Handling it now keeps the first sentence true.

It ends

Every step moves at least one pointer forward, so there are at most n + m steps. That's the O(n + m).

In an interview: say why the smaller front is safe to handle now, then say out loud what you do with the leftovers. Interviewers watch for that second part.

This merge step is the heart of merge sort, usually credited to John von Neumann in 1945. Sorting on tape drives relied on it for decades, because tapes can only be read in order.

Recap

Cheat sheet

Merge

Take the smaller front. Copy the leftovers.

Subsequence

j always moves; i moves on a match. True if i reaches the end.

Common elements

Equal → record, move both. Else move the smaller.

Merge in place

Fill from the back with the larger value.
